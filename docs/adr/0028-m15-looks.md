# ADR 0028: M15, looks: Console as a second look

## Status

Status: Proposed (2026-11-14). The owner's brief for M15: Console as a second look, chosen in the account menu and saved on the account (R82d, A74). Built on the branch `m15`, stacked on `phone-integrations` (pull request 40) while that is open, since both change the account menu's pages. `VERSION` and the compose image stay as they are (ADR 0024); the PowerShell module doesn't change.

## Context

M13 made every style value a token in `web/src/app.css` (R82c) and built Harbour only (ADR 0015). Console was the owner's second favourite of M13's three prototypes; its token values are in commit 881107d (`:root[data-proto='console']`), and ADR 0015's table describes it: ink on white or white on ink, square and dense, no accent colour, priority the only colour as an edge down every row and an outlined capital label, system type with times, groups and labels in monospace.

R82d: users choose Harbour (the default) or Console in the account menu, beside Auto / Light / Dark; the look is saved on the account, so it follows the user to every browser and device; a change applies at once without reloading, and a page never shows the default look first and then switches; pages before sign-in use Harbour; every look meets WCAG 2.1 AA in light and dark. R82e: the favicon doesn't change.

## Decisions

### 1. Console as tokens

- **One block**, `:root[data-look='console']`, after Harbour's `:root` block in `app.css`. Its selector is more specific than `:root`, so on a page with `data-look="console"` on the root it wins token by token; nothing else in the stylesheet or any component changes.
- **Complete.** It sets **every token Harbour's block sets**, 176 of them, the same values where Console doesn't differ (the map's and scrubber's sizes, the measures, the layers of the type scale it keeps), so no Harbour value can show through, now or after a token is added. `web/scripts/check-tokens.mjs` checks it: every `:root[data-look='…']` block sets exactly the tokens of the default look's block (the top-level `:root` rule that sets `--bg`), and CI fails naming the token missing or extra. Two tokens that aren't look values move to the block shared by every look: `--target` (the look's `--target-min`, or its `--target-coarse` on a touch screen) and `--scrollbar-gap` (measured by the scrubber).
- **Where the values come from.** The prototype's colours, type, corners, density, edges and labels, unchanged: `--bg` `#ffffff` / `#141414`, ink `#111111` / `#ededed`, the accent the ink, the focus ring `#1d5bd6` / `#7ea8ff`, 2 px corners, 36 px controls (44 px on touch screens), row padding 0.5 × 0.875 rem, a 4 px edge, labels in capitals with 0.06 em tracking and no dot, `system-ui` with monospace for times, groups and labels, the prototype's smaller type scale (`--text-xs` 0.8 rem and so on), icons at stroke 2, a 15 rem menu.
- **Added since the prototype** (tokens M13 and M14 made later): the danger colours (`--danger`, `-fg`, `-hover`, `-text`) from Console's Emergency red; each priority's own colour (`--emergency-bg` and the rest, also the map's marker) as its edge colour; `--ok-fg` (the Live dot) as the ink, since Console's only colour is priority; rows `transparent`, as Harbour's, so a row is the list's own background; the scrubber's halo on `--bg`; slightly smaller map points; denser spacing (`--space-xs` to `--space-3xl`, the page's padding).

### 2. Choosing it: the account menu

- **Look** sits in the account menu under Colour theme, a select of Harbour and Console with its own icon (Tabler `palette`, added to `scripts/icons.mjs` as `look`). On a phone the account menu is in the top bar, as before, so it's there too.
- **At once, without reloading.** Choosing sets `data-look` on the page's root straight away (the layout's effect), which restyles everything through the tokens, and saves it with `PATCH /api/v1/me`. If saving fails, the old look comes back and the menu says "Couldn't save the look. Try again."
- The map, which draws in tokens read from the root, follows a change of look as it follows a change of theme; it restyles only when the theme or look really changed.

### 3. Saved on the account (`00020_looks.sql`, the API)

- `users.look`: `text NOT NULL DEFAULT 'harbour' CHECK (look IN ('harbour', 'console'))`. Existing accounts get Harbour. Deleting an account (R43c) sets it back to `harbour`, so the placeholder keeps nothing of the user. An upgrade from the latest release adds the column (A77).
- `GET /api/v1/me` gains `look`. `PATCH /api/v1/me` with `{"look": "console"}` saves it for the signed-in user and answers with the account, as `GET` does; any other look, an empty body or an unknown field (`role`, say) is 400 and changes nothing. It needs a signed-in user like the rest (A29's list includes it), and the browser's same-site check, like every change.

### 4. No flash: the page is sent in the user's look

The app is one static page (`index.html`, SvelteKit's adapter-static) served by the API, with its stylesheets as `<link rel="stylesheet">` in its head, so the browser draws nothing before they're loaded. **The server writes the user's look into that page before sending it**: `web.Serve` puts `data-look="<look>"` on the `<html>` element, the look coming from `Server.PageLook`, which reads the session cookie (the same lookup every API request does) and returns the user's `look`. So the first paint is already the user's look, on every device, as soon as they've signed in: nothing has to load first, no script has to run, and a look chosen on a PC is what a phone's very next page load gets.

- **Before sign-in** (no session, or one that's expired or ended), and on the sign-in page whatever the cookie, `PageLook` is empty and the page goes out as built: Harbour. The layout also takes `data-look` off on the sign-in pages.
- **Only a name is ever written**: `WithLook` writes a look only if it's 1 to 32 lower-case letters (the database's check allows two), so nothing from a request can reach the page's markup.
- **Caching.** The page now depends on who asks, so it goes out with `Cache-Control: no-cache, private` and `Vary: Cookie` (it was `no-cache`), and no shared cache keeps one user's page for another. The other files (scripts, styles, icons) are the same for everyone and keep their caching.
- **Why not a cookie read by a script**: the session cookie is `HttpOnly`, so a script can't see whose page it is; a second cookie holding the look would be per browser, so a phone that already had the app would show its old look first after a change on the PC, until the account was read. The server knows the account on every page load.
- The cost is one session lookup per load of the page itself (not per API call or file): a single indexed query, renewing the session at most hourly as the API does.

## Tests

- **API** (`internal/acceptance/m15_test.go`, `TestA74LookSavedOnTheAccount`): every account starts on Harbour; B chooses Console and `GET /api/v1/me` says so; a second session for B (signing in on a phone) is sent the page with `data-look="console"` on every route; C and the admin keep Harbour; no session, an unknown session and `/signin` get the page as built; `""`, `Console`, `ledger`, a quoted attribute and a body with `role` are refused; back to Harbour; C's deleted account keeps no look. A29 includes `PATCH /api/v1/me`.
- **The page** (`web/web_test.go`, `TestPageIsSentWithTheLook`): the attribute on `/`, `/index.html` and deep links, with `Vary` and `Cache-Control`; no look, or anything but a plain name, leaves the page as built; other files are untouched.
- **Browser** (`web/tests/e2e.spec.ts`), in Chromium, Firefox and WebKit:
  - **A74**: B on Harbour at 1,280 px opens the account menu and chooses Console; the root says `console`, the account button's corners go from 10 px to 2 px, the type and background change, a value set on the window before is still there (no reload), the account says `console`, and axe passes with the menu open. Then B gets a new session (as signing in on a phone does), and a new browser at 375 px in dark mode, with a script recording every change of `data-look` from before the page's own scripts run: the page as sent says `console`, the first frame's root says `console`, nothing ever changes it to anything else, and the body is Console's dark `#141414`. User C, in dark mode, is on Harbour (`#0f1614`).
  - **axe: every view** runs in both looks: Harbour as before, and Console, light and dark, at 375 and 1,280 px, on all 40 views, each checked to be drawn in the look it should be (the sign-in pages in Harbour).
  - **Contrast** ("M13, M15: WCAG AA contrast of every look, light and dark"): the same pairs for both looks, each token as the browser resolves it; where a look draws no dot (Console), the dot isn't measured, and where a label has a border (Console's), it's measured as a mark (3:1).
- **Screenshots**: `PA_M15_SHOTS=<folder>` runs "M15 screenshots" (Chromium): Console, light and dark, at 1,280 and 375 px, the message list, a message open, the map, Administration and the account menu with the choice, 20 files named `console-<theme>-<width>-<view>.png`, delivered with the report.

## Not changed

- Harbour's values, and every component: Console is tokens only (R82c).
- The favicon (R82e): Harbour's green, the same in both looks, loaded before sign-in.
- The colour theme (Auto / Light / Dark) is still kept per browser, as before; only the look is on the account, as R82d says.
