# ADR 0052: Signing in beside RadioArchive: a shared look cookie, a silent check and back-channel logout

## Status

Proposed (the implementer's calls, 2026-11-25), for the owner's review on the pull request. #106, items 5, 6 and 7, and what PagerArchive's coordinator agreed with RadioArchive on its issue #128. SPEC.md R92b-R92e; A148-A152.

## Context

RadioArchive runs beside PagerArchive on a sibling subdomain and signs in through PagerArchive's Authentik, as a second OIDC client. Its spec (R103, R104, R107) asks for one look across both apps, a silent sign-in check on a browser session's first visit, and sign-out and disabling in either app reaching the other. It plans to receive OIDC back-channel logout. Before building on that, PagerArchive had to find out whether the Authentik it pins (2026.8) sends back-channel logout at all, and when.

## What Authentik 2026.8 does (read in its source, proved in the stack checks)

- An OAuth2 provider has `logout_uri` and `logout_method` (`backchannel` or `frontchannel`). With `backchannel`, Authentik posts `logout_token=<JWT>` to `logout_uri` from its worker, form-encoded. The token is signed with the provider's key, typed `logout+jwt`, with `iss`, `aud` (the client), `iat`, `exp` (now plus the provider's access token validity), `jti`, `events` holding the back-channel logout event, `sub` and `sid` (a hash of the Authentik session's key, the same as the `sid` in that session's ID tokens).
- It's sent from a `pre_delete` signal on `AuthenticatedSession`: whenever an Authentik session is deleted, however. That covers (a) the end-session endpoint's invalidation flow (its user logout stage), and (b) a session revoked (Authentik's admin pages, the API, the models) and a user disabled, since saving a user inactive deletes all their sessions (`user_deactivated_delete_sessions`). A150 shows all three reaching a made-up second client within seconds, including PagerArchive's own deactivation of a user.
- **It's sent only to clients that hold an unexpired access token bound to that session.** The signal finds the session's access tokens through the default manager, which leaves out expired ones. A client with Authentik's usual 5-minute access tokens is told nothing about a sign-out more than 5 minutes after it signed in. A150 shows it: a client with 5-second tokens gets no logout token after they've expired, while the 30-day client does.

So no shared-secret fallback is needed for (b): disabling and revoking reach other clients by back-channel logout. What each client needs is access tokens that last as long as its own session.

## Decisions

1. **The look cookie follows ArchiveUx's rule exactly** (its `look.js` and ADR 0002, decision 11). `LOOK_COOKIE_DOMAIN` set, the server reads the `look` cookie as `lookFromCookies` does and picks the first paint's look as `pickLook` does, with the Go tests taking `look.test.mjs`'s cases. It writes the cookie at sign-in and in the answer to a look change, so the browser app never writes `document.cookie` itself; it reads it with `look.js`'s `pickLook` when the account loads, so a page served by the service worker with an older look still ends up on the cookie's. The page carries `data-look-shared` so the script knows the cookie is in use: without it, standalone is exactly as before, a stray `look` cookie included. The sign-in page follows the cookie too, as the radio's signed-out pages do. APP_URL's host must be in the domain, or the API stops at start: a browser would refuse the cookie anyway.
2. **The silent check is in the server's `/auth/login`**, not the page: it's the only place every sign-in passes. With `RADIOARCHIVE_URL` set and no `pa_silent` cookie, it sets that cookie (a browser-session cookie, on `/auth/`) and adds `prompt=none`; the callback sends `login_required`, and any other failure of a check (a code exchange or ID token that fails), to `/auth/login?checked=1`, which never checks. The query parameter means a browser that drops cookies still can't loop. Since the browser app's sign-in already signs in silently whenever Authentik has a session (its consent is implicit), the check changes nothing a PagerArchive user sees; it keeps the two apps symmetrical, as #106 asks.
3. **Back-channel logout into PagerArchive, by `sid`.** `POST /auth/backchannel-logout` validates the token with the browser client's ID token verifier (signature, `iss`, `aud`, `exp`) and then as the specification's section 2.6 says: an `iat`, the event in `events` as an object, a `sub` or `sid`, no `nonce`. It then ends the user's browser sessions whose stored ID token (kept since ADR 0038) has that `sid`, so only the browser whose Authentik session ended is signed out and the person's other browsers keep theirs (R40b). No migration: the `sid` is read from the ID token kept with each session. A token without a `sid` ends all the user's browser sessions; one for no known user is answered 200 (there's nothing left to end), as the specification wants for a session already gone. The user's live connections are closed; their other browsers' streams reconnect. `jti` replay isn't tracked: a replayed token can only end sessions that are already ended.
4. **PagerArchive's browser client's access tokens last 30 days**, as its sessions do, so Authentik tells PagerArchive about a sign-out or a disabling in the radio for as long as a PagerArchive session from that Authentik session can live. PagerArchive never keeps the access token or sends it anywhere (it signs in with the ID token), and the API accepts no browser client's token as a bearer (R60's checks are for the module's and service accounts' clients only, by issuer and audience). The blueprint sets `logout_uri` to `http://api:8080/auth/backchannel-logout`, the API's address inside the compose network, so Authentik's worker needn't reach the public URL. RadioArchive's blueprint has to set its own client's `access_token_validity` as long as its sessions, or it hears nothing after the first minutes; docs/deploy.md says so.
5. **Deactivation is left to Authentik.** PagerArchive already disables a deactivated user in Authentik (R43b), and Authentik deletes all of a disabled user's sessions, sending each one's logout tokens. Revoking the sessions through the API as well would need the API's Authentik role to see and delete sessions, for nothing more. A150 checks that no session is left and the other client is told; if a later Authentik stops doing it, that check fails on the upgrade.
6. **The group and the proven address are the enrolment's last step**, in the blueprint's activation policy: it puts `pagerarchive-users` in the plan's `groups` (the user write stage adds plan groups on every write) and `email_proven` (the confirmed email device's address) in the attributes it writes. The blueprint makes the group and gives the API's role only `view_group` and `add_user_to_group` on that one group. Users from before are added by the API on every start (`JoinUsersGroup`): one call for the group's members, one per missing user, retried while Authentik isn't up yet, as the R44c check is. People only: service accounts aren't added. A user Authentik no longer has is skipped.

## Consequences

- Standalone (no `RADIOARCHIVE_URL`, no `LOOK_COOKIE_DOMAIN`): no check, no look cookie read or written, and the pages are as before. The back-channel endpoint is there, and Authentik posts to it after PagerArchive's own sign-outs and deactivations; those sessions have already ended, so it ends nothing.
- A sign-out in either app signs that browser out of both, and only that browser; disabling someone in either app signs them out of both everywhere.
- Authentik's back-channel logout depends on a detail of Authentik's (the unexpired access token) that isn't documented as a contract. A150 runs it against the pinned version on every pull request that touches the stack, so an Authentik upgrade that changes it fails there.
- The stack checks have a made-up companion app (deploy/test/companion.yaml): two OIDC clients and a receiver for their logout tokens, in the tests only.
