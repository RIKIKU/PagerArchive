# ADR 0015: M13 UI redesign: the prototypes, the choice, and the build

## Status

Accepted (2026-11-02): the owner chose **Harbour**, unchanged, and answered the questions below (see "Decision"). Proposed 2026-11-01. Built on branch `m13` (R77-R81a, R33a, R82c): see "Build", at the end. The sections up to "Decision" describe the prototypes as they were; the prototype route is gone.

## Context

M13 redesigns the browser app (SPEC.md 7.17, R77-R81a, with R33a's single search box). The look and palette are to be chosen by the owner from prototypes (section 12). The owner's brief, from main at 59f40ff:

- **Patterns to take, not looks to copy.** Grafana's side menu with an icon per page and per group, groups that open and close, and breadcrumbs; Immich's use of the whole width on a desktop and its own phone layout with a bottom bar. No prototype may resemble either app's styling, colours or icons.
- **What's wrong today.** Too much empty space on a PC (the layout is capped at 64rem); buttons are small, rounded and don't react to the mouse; the colour scheme clashes; the big solid red Emergency badges feel unpolished.
- **The prototypes** share one structure, R77-R81a's, so the owner compares looks, not layouts. They differ in palette, type, spacing, button style and how Emergency stands out. Each is a set of token values in `web/src/app.css` (light and dark), passes axe and WCAG AA contrast in both modes, and uses one icon set chosen here.

## Before the prototypes: two test fixes

The reviewer's mutations on a33-flake survived the stack-free tests (`internal/stacktest/outcome_unit_test.go`), so both tests now catch them (587474c), and both mutations are in `scripts/mutation-checks.sh`:

- `TestOnlyTransientRepliesAreRetried` expected `transientTries` requests for "5xx every time", so `const transientTries = 10` passed. It now expects a literal 3.
- `judge` counts `ak-stage-access-denied` as the lock's refusal only with the too-many-attempts message, but no test showed it. `TestRepliesThatAreNotAnswers` now has an access-denied reply saying "Flow does not apply to current user.", which must be no answer (a test error), not "refused by the lock".

With main's tests, both mutations survived (`-> SURVIVED: no test failed`); with these, both fail (`-> the test fails: the check is guarded`), and the unmutated package passes (`ok github.com/RIKIKU/PagerArchive/internal/stacktest 7.330s`). The run used the mutation script's own `mutate` function, cut down to the ADR 0014 block.

## The prototypes

**Where.** `/prototype` (881107d), in `web/src/routes/prototype/`. The root layout renders that route bare: no real header and no API calls, so it needs no sign-in. Everything is in the address, so each view can be linked: `look` (`ledger`, the default; `console`; `harbour`), `theme` (`light`, `dark`; none follows the system), `role=user` (no Administration), `menu=shrunk`, `page` (a menu page), `m` (an open message), `more=1` (the phone's More menu) and `bare=1` (hides the prototype's own controls, bottom right).

**The structure (the same in every look):**

- **Side menu (R77, R77a).** Messages, then Albums (two example albums), Tools, Reports, Account and, for admins, Administration with its waiting-requests count. Each group opens and closes under its heading. "Shrink menu" leaves only the group icons (and Messages'); hovering over one or focusing it opens a panel of its pages, and each icon has a tooltip and an accessible name.
- **Top bar (R77a).** Breadcrumbs, the search box with From and To beside it (R33a; not working yet: its behaviour is part of the real build) and the account menu.
- **Breadcrumbs (R79).** Built from the menu's tree, not from history: a message is `Messages / Station 1, 1 Nov 2026 13:41:17`; a template is `Administration / Templates / Example Fire`. Each level above the current page is a link, so each group has a page of its own listing its pages (see question 4).
- **Using the width (R80).** At 1,280 px and wider, the list and the detail view sit side by side, each scrolling on its own, so the list keeps its place. Below 1,280 px the detail view replaces the list, with a "Messages" link back. The detail view has its own address (`?m=3`). There's no centre column: at 1,920 px the list fills the width beside the menu.
- **Phones (R81).** Under 768 px: no side menu; a bottom bar with Messages, Map, Albums and More; More opens the rest of the menu without the print sheet and Administration. The integrations page shows a Pause/Resume switch per integration; "Set up an integration" is desktop only. The map comes right after the text in the detail view (R35c, P2).
- **The real content (R31, R35c, R66).** The list and detail view on made-up pages from the example network (`data.ts`, SPEC.md section 10): Emergency, Non-emergency, Admin, heartbeat and unmarked pages; two templates with made-up icons on a light tile; an unaliased capcode; a long Emergency page that wraps. The detail view has every field, the receivers and a stand-in for the small map (the real one needs the API's tiles, which need a sign-in).

**Throwaway.** The route, its components and `prototype.css` are deleted when the real build starts; the chosen look's tokens are kept.

### The three looks

| | **Ledger** | **Console** | **Harbour** |

| Type | Humanist stack (Seravek, Gill Sans Nova, Ubuntu, Calibri, DejaVu Sans) | System UI; times, groups and labels in monospace | Geometric stack (Avenir Next, Avenir, Montserrat, Corbel, URW Gothic), slightly larger |
| Spacing | Medium (row 0.75 x 1 rem) | Dense (0.5 x 0.875 rem) | Airy (1 x 1.25 rem) |
| Buttons | 6 px corners, 40 px high; filled teal, outlined, or plain | 2 px corners, 36 px high; filled ink, outlined, or plain | 10 px corners, 44 px high; filled green, outlined, or plain |

**Buttons in every look** have a visible hover (a darker or tinted fill), focus (a 3 px ring in the focus colour, 2 px out) and pressed state (darker fill or the soft accent, and a 1 px push down, off with reduced motion). Every button, menu item and link-button is at least the look's target size, and at least 44 px (2.75rem) on a touch screen (`pointer: coarse`).

### Tokens

Each look is one block in `app.css`, `:root[data-proto='ledger']` and so on, used only when the prototype sets `data-proto` on the root. Each colour is written once as `light-dark(light, dark)`; the root's `color-scheme` picks one, following the system unless `data-proto-theme` says otherwise. That needs Chrome 123, Firefox 120 or Safari 17.5 (2024), within R36's "current" browsers, and it halves the colour section: today's `app.css` writes every dark colour twice. **Proposal for the real build:** do the same there.

New tokens, beyond today's: `--surface-2` (panes and cards), `--control-border` (input and outlined-button borders, 3:1), `--accent-fg`, `--accent-hover`, `--accent-pressed`, `--accent-soft`, `--accent-soft-fg`, `--hover`, `--focus`, `--scrim`, and per priority (`emergency`, `nonemergency`, `admin`) `-edge`, `-dot`, `-row`, `-row-hover`, `-badge-bg`, `-badge-fg`, `-badge-border`; non-colour ones: `--font-ui`, `--font-meta`, `--font-page`, `--text-page`, `--weight-strong`, `--radius`, `--radius-button`, `--radius-badge`, `--row-pad-y`, `--row-pad-x`, `--edge-width`, `--badge-dot`, `--badge-case`, `--badge-tracking`, `--badge-pad-x`, `--button-pad-x`, `--target-min`, `--target` (larger on touch screens), `--icon-stroke`, `--menu-width`, `--menu-width-shrunk`. The template icon's tile stays white in both themes (R66). `prototype.css` holds the shared structure and names no colour, font or size of its own.

Fonts are system stacks: nothing is downloaded, but the type differs by system. The screenshots, from Linux, show DejaVu Sans for Ledger and fallbacks for Harbour; on Windows, Ledger is Calibri and Harbour Corbel; on Apple devices, Seravek and Avenir Next. See question 3.

## Accessibility

**axe** (WCAG 2.0 and 2.1, A and AA) passes in seven views of each look, light and dark, in Chromium, Firefox and WebKit: the list with a message in the pane (1,280 px), the shrunk menu with a group's panel open by keyboard focus (1,920 px), the integrations page with its switches, a page three levels deep, and on a phone (375 px) the list, a message and the More menu. The first run found one fault, in every look: in the shrunk menu, the "PA" mark (hidden from assistive technology) left the home link with no name. It now has one.

**Contrast** is measured by the browser from the resolved tokens (`web/tests/prototype.spec.ts`), so what's checked is what's drawn. ## Questions for the owner

1. **Which look?** Ledger, Console or Harbour, or one with parts of another (for example Console's edges with Harbour's spacing). Please say what you'd change about it: colours, density, button shape, how Emergency stands out, the type.
2. **The icon set:** is Tabler Icons acceptable? (Recommended above; Lucide is the alternative.)
3. **Type:** keep system font stacks (nothing downloaded, but the type differs between Windows, Apple and Linux), or serve one open-licensed typeface from PagerArchive itself (about 50-100 KB for two weights, the same everywhere)?
4. **Group pages:** R79 makes each level above a page a link, so `Account / Profile` needs an Account page. The prototype gives every group a page listing its pages, as Administration's start page does (R44b). Is that right for Albums, Tools, Reports and Account too?
5. **The theme switch:** R77a keeps only the search box, breadcrumbs and account menu in the top bar, so the Auto / Light / Dark switch moves into the account menu. Agreed?
6. **`light-dark()`:** write the real `app.css` the same way, each colour once (needs browsers from 2024)?

## Decision

The owner's answers (2026-11-02), which the real build follows:

1. **Harbour**, with nothing changed: its palette, geometric type stack, airy spacing, 44 px buttons with 10 px corners, and Emergency as a soft tinted label with a dot on a plain row. Console was the owner's second favourite; nothing of it is taken.
2. **Tabler Icons**, as mapped above, generated from the pinned package with its MIT notice.
3. **System font stacks**: no typeface is downloaded.
4. **Every group gets a start page** listing its pages (Albums, Tools, Reports, Account, as Administration's already does), so every breadcrumb level is a link and behaves the same.
5. **The theme switch** (Auto / Light / Dark) moves into the account menu.
6. **`light-dark()`**: the real `app.css` writes each colour once, with `color-scheme` choosing light or dark.

The prototype route, its components, `prototype.css` and the Ledger and Console token blocks are removed in the real build; Harbour's tokens become the real ones.

## Build

Built on branch `m13` (from `m13-prototypes`, with main merged in), in Harbour as chosen. VERSION is 0.13.0 (a milestone, SPEC 12.1); the PowerShell module and the client didn't change, so `ModuleVersion` stays as it is.

### What was built

- **The frame** (`web/src/routes/+layout.svelte`). On a desktop: the side menu, and a top bar with the breadcrumbs, the search box and the account menu (R77a: nothing else). The page uses the full width; the 64rem centre column is gone (R80). The page itself scrolls, with the top bar and the menu staying in place, so the sticky top bar still covers rows scrolled under it.
- **The side menu** (R77, `lib/Menu.svelte`, `lib/nav.ts`). Messages, then Tools (Print sheet, Unknown capcodes), Reports (Capcode report), Account (Profile, Integrations, My requests, Invite someone) and, for admins, Administration (Users, Aliases, Templates, Alias requests, Receiving clients, Retention, Integration addresses). Each group heading links to its group's start page, and a chevron beside it opens and closes the group. "Shrink menu" leaves the group icons, each with an accessible name. Hovering over one or focusing it shows a tooltip, which says in a few words what's there rather than repeating the name (owner, 2026-11-02): Messages "Every page, newest first, as it arrives", "Widen the menu" "Show the pages' names again", the quiet-receivers warning "No pages from a receiver for 30 minutes". A group opens its panel instead, which starts with that description ("Printing for training, and capcodes with no alias"). Administration carries R55's count, in its name too ("Administration, 2 alias requests waiting"), and so does Alias requests; Print sheet carries the sheet's count (R67). R39's "1 receiver not receiving" is now at the foot of the menu, for admins. Albums (R82) come in M14: they're left out of the menu and the bottom bar until then.
- **A start page for every group** (decision 4, `lib/GroupPage.svelte`): `/menu/tools`, `/menu/reports`, `/menu/account`, and Administration's own `/admin`, which R44b already had. Each lists its pages with their icons and what they're for; Administration's still notes the waiting requests and quiet receivers.
- **Breadcrumbs** (R79, `lib/Crumbs.svelte`). Built from the page's route and the menu's tree, never from history, so a page has the same breadcrumbs however it was reached; each level above the page is a link. Pages reached from Messages sit under it: `Messages / Station 1`, `Messages / Job EX0000001`, `Messages / Map`, `Messages / Capcode 0999999`, and a message, `Messages / Station 1, 2 Nov 2026 04:13:48`. Names that come from data (an alias, a user, a template) are set by the page once loaded. The Messages link goes back to the list as it was left (R81a). On phones they show only below the top level.
- **The pane** (R80, `routes/(list)/+layout.svelte`). The list and a message's view share a layout, so from 1,280 px the message opens beside the list without the list reloading: it keeps its search, its live updates and its place, and the opened row is marked. The message still has its own address (`/messages/7`); opened from a bookmark, it has the unfiltered list beside it. Narrower, the message has the page to itself, as before. Width alone decides (`lib/screen.svelte.ts`, R81).
- **Phones** (R81, under 768 px). No side menu; a bottom bar with Messages, Map and More. More is a dialog with the rest of the menu, without the print sheet or Administration. On a phone, Integrations shows each integration with a Pause/Resume switch and nothing else (no "New integration", no editing). Every page still opens from its address.
- **Coming back to the list** (R81a, `lib/listState.svelte.ts`). The search and dates are in the address, and the links back (breadcrumb, menu, bottom bar, Close) carry the list's last search. What the list had loaded, and its place, are kept in memory when it's left: its place is the first row in view and where that row was on the screen, so it's found again even when the list is wider or narrower than when it was left (a message beside it, or not). Then anything newer is added. Nothing is written to the browser's storage (P1; A60 checks it). The back button is left to SvelteKit, which puts the page back itself.
- **One search box** (R33a, A61, `lib/SearchBox.svelte`, `lib/search.ts`). The ARIA combobox pattern: typing the start of a key suggests the key; typing a value suggests values (alias, agency and group from the API; priority, category, `is:` and, for admins, `flag:` from what the app already knows); arrow keys move, Enter picks (or, with nothing picked, searches), Escape closes, and the number of suggestions is announced. A help control lists every key with an example. From and To sit beside the box (behind "Dates" on a phone). The box searches the view it's on when that view lists messages (the list, the map, an alias, a capcode, a job, the print page); elsewhere it searches the message list. The job view now follows the search too, and gets live updates.
- **The account menu**: who's signed in, Profile, the Auto / Light / Dark switch (decision 5) and Sign out.
- **Invite someone** has its own page, `/account/invite` (owner, 2026-11-02): the invitation form and the invitations you've sent, moved from the Profile page, which links to it. Its breadcrumbs are `Account / Invite someone`. Old links to `/account#invite` go there.
- **Icons** (R77a). `web/scripts/icons.mjs` writes `web/src/lib/icons.ts` from the pinned `@tabler/icons` 3.50.0 package (a dev dependency), with its MIT notice; CI checks the file is what the script writes (`node scripts/icons.mjs --check`). 39 icons, keyed by meaning: the 35 of the comparison, less albums, plus help (info-circle), hosts (server), auto (device-desktop), list and warning (alert-triangle). They're compiled into the app's JavaScript: nothing is fetched from anywhere (A68 checks every request's origin).
- **System fonts** (decision 3): Harbour's stack, nothing downloaded.
- **Template icons** (R66). In a row: the size of the text, on its light tile, just before the alias name, after the priority and the time. Large beside the name on the alias view and the message view.

### The API

One endpoint, for R33a's suggestions: `GET /api/v1/search/suggest?key=alias|agency|group&q=…` gives the alias names, template agencies or paging groups containing `q`, ignoring case, at most 10, in order. It needs a signed-in user like the rest (A29's list includes it). Paging groups are found with a loose index scan of `messages_group_idx`, one step per group, so it doesn't read every message. Tested by `TestSearchSuggestions`. Nothing else changed: the filters the box makes are parameters the API already had (`alias`, `alias_like`, `group_like` and the rest, several values each).

### Harbour as tokens (R82c)

`web/src/app.css` is now the one place for style values: a block that's the same in every look (stacking layers, and R68's print values: black on white, the heavy border), then Harbour's tokens, each colour written once with `light-dark()` (decision 6), then the base rules for elements (body, links, buttons, inputs), which use the tokens too. Tokens cover colours; type sizes, fonts, weights and line heights; spacing; borders, focus rings and corner radii; target sizes and the other sizes (the menu's width, the map's height, a form's measure); and how each priority is shown (`--<priority>-badge-bg`, `-badge-fg`, `-badge-border`, `-dot`, `-row`, `-row-hover`, `-edge`, and `--badge-dot`, `--badge-case`, `--edge-width`). Buttons have a visible hover, focus and pressed state, and are at least 44 px. The map draws its markers in the priority tokens, which it now reads through an element's computed colour, since a `light-dark()` token only resolves there.

Breakpoints aren't tokens: CSS can't use a custom property in a `@media` or `@container` condition. They're 47.99rem (phones, R81) and 80rem (the pane, R80), and `lib/screen.svelte.ts` uses the same two.

### The token check (A73)

`web/scripts/check-tokens.mjs`: plain Node, with Svelte's own parser (`parse` from `svelte/compiler`), so it reads a file exactly as Svelte does. CI runs it in the browser job, right after svelte-check (`node scripts/check-tokens.mjs`, step "Style tokens only (A73)"). It reads every `.svelte` file under `web/src`:

- the `<style>` block: every declaration's value, nested ones and those inside `@media` included;
- inline styles: `style="…"` attributes and `style:property` directives with a fixed value (`style:--agency={m.colour}` takes its value from data, so it passes);
- class strings: a `class` attribute's fixed text, for a colour or a length written into a class name (as utility CSS would: `p-[4px]`);

and `web/src/app.css`, where a fixed value is allowed only as a token's own value (`--name: value`). It fails on a colour (hex, `rgb()` and the other colour functions, and the CSS colour names), any length with a unit other than zero (px, rem, em, vh, dvh and the rest: sizes, spacing, radii, borders, targets), a font size keyword or percentage, and a font family, font weight, line height or z-index that isn't `var(--…)`. It also fails on a `var(--…)` naming a token app.css doesn't define. Unitless numbers (`flex: 1`, opacity), percentages, `fr`, times and angles are layout, not look, and pass, as do selectors and `@media` conditions. Each problem is one line naming the file, line and value.
