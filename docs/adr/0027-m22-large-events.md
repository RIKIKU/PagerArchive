# ADR 0027: M22, large events

## Status

Status: Proposed (2026-11-13). The owner's brief for M22: large events (R87-R87e, A84-A86) and R5's deployment code pattern, on the branch `m22` from main. The PowerShell module's display and help call the units field Appliances (owner, 2026-11-13), so its `ModuleVersion` goes from 0.13.0 (v1.7.9's) to 0.13.1; `VERSION` and the compose image stay as they are (ADR 0024).

Changed (owner, 2026-11-13, on the branch `events-simple`, before any release): "Deployments isn't the right word, we just call them jobs and the number that represents them Job Numbers", and "I honestly don't think we need to tag them with these levels. It's just meant as a means of alerting users to something big happening so they know where to look." So an event has **no levels**; users see **jobs and job numbers**, never a count or list of codes; and a large-event integration is told of an event **once, when it opens**. What opens an event, joining, merging, out-of-order pages and retention are unchanged. Migration 00019 takes out what the levels and codes needed (section 1).

## Context

R87-R87e (owner, 2026-11-12; simplified 2026-11-13) add **large events**: PagerArchive notices when something big is happening and groups the pages into an event, so users know where to look; for more they listen to the radio or look at other systems. Emergency pages to aliased capcodes open one when they carry a code matching an optional pattern in the network profile (R5's `deployment_code_pattern`, a machine name that stays), or when one job has 20 or more Emergency pages to aliased capcodes (admins set the 20; owner, 2026-11-13: it was 20 distinct units). Pages within 12 hours of an event's latest page join it, with the other pages of their jobs, and 12 quiet hours end it (R87a). An event is simply a large event (R87b: no levels). A Large events page under Tools lists them, with their jobs and Emergency pages, and an event's view shows its job numbers and pages (R87c); an integration may select large events and is told once per event, when it opens, with a summary and never page text (R87d); retention thins and deletes events with their pages (R87e).

Detection sits on the ingest path, which R51a holds to 5 seconds from a page to its deliveries, and it must be right when pages arrive late, out of order, or from several receivers.

## Decisions

### 1. The data model (`00018_large_events.sql`, `00019_large_events_simple.sql`)

- `large_events`: `first_at` and `last_at`, the sent times of its earliest and latest pages: the window that joins pages to it, and its start and end in the app. Nothing else: no levels (00019 drops 00018's `deployment_at`, `several_deployments_at` and `big_job_at`).
- `large_event_messages`: `(message_id, event_id)`, with `message_id` the key, so **a page is in one event at most**. Both columns cascade, so retention takes a page out of its event (R87e) and a deleted event takes its rows. 00019 drops 00018's `deployment_codes`: the codes open an event as a page arrives (read from its text then) and are never counted or shown afterwards.
- Every number the app shows (jobs, Emergency pages) is **counted from the pages the event still holds** when it's asked for (`ListLargeEvents`, `LargeEventJobs`, `LargeEventPages`), so it follows retention with nothing to keep in step. Events are about one a week; counting each one's few hundred rows at most is cheap.
- `integrations.large_events`: `boolean NOT NULL DEFAULT false`, whether an integration selects large events instead of pages. 00018 had it as the level (text, NULL for a page integration); 00019 drops its check and turns it into `large_events IS NOT NULL`, so an integration at any level selects large events and a page integration stays one. `deliveries.event_id`: the event a delivery is about (section 4).
- **Upgrades.** From the latest release (v1.7.9, A77), 00018 and 00019 run in turn: two new tables and two new columns, nothing else changed. From main with 00018 (never released, but main is shared, so 00018 is left as it is), 00019 keeps every event, page and delivery and drops only the columns above (`TestM22UpgradeFromLevels`: an event with levels and codes, four integrations, a delivered and a pending delivery, upgraded, then down to 00018 and up again). Its down migration puts the columns back, empty, and an integration that selected large events back at level deployment.

### 2. Where detection runs, and what it costs

- **In the ingest transaction, after the page is stored** (`ingest.Service.Events`, `events.Detector.Stored`), for a new page only: a duplicate copy (R19) never gets there, so several receivers count once. The event, its pages and the deliveries it fires commit with the page that made them, as the page's own deliveries do (ADR 0006 §3), and the delivery worker is woken as before, so R51a's 5 seconds hold.
- **Nothing is read for a page that can't count.** The detector first checks, from the values ingest already has, that the page is Emergency, to an aliased capcode and not a heartbeat (R87), and carries a code or a job number. Any other page returns before any query.
- **A page that might** takes a transaction-level advisory lock (`LockLargeEvents`), so two pages can't both open an event or join one being merged; the API already stores one page at a time (ADR 0010 §3), so the lock is uncontended. Then: its job's counting pages, with the event each is in (`JobEventPages`, by `messages_job_idx`; a job is tens of pages), the threshold (one settings row), and the events within 12 hours of it (`LargeEventsNear`, by `large_events_last_idx`). A page that doesn't open or join an event stops there. One that does adds its rows and updates one event.
- **Measured** (`TestLargeEventsCost`, cld01, the API through HTTP with the database in Docker; again with no levels, 2026-11-13): 200 Emergency pages to aliased capcodes, each on its own job, stored in 5.40 ms each with detection off and 6.56 ms with it on (the slowest 10.57 ms); 200 pages each joining one open event, 7.11 ms (the slowest 12.70 ms). A86's deliveries came 51 ms after the page that opened the event.
- **Imported pages aren't grouped** (R83): the import's own service has no detector, so R83f's 500 pages a second is untouched, and an imported page fires nothing anyway (R83b). See question 1.

### 3. How pages group (R87, R87a)

- **A page opens or joins an event** (it "would open an event", R87a) when it counts and carries a code, or its job has the threshold's number of Emergency pages (below). It joins **every event it's within 12 hours of**: from 12 hours before the event's first page (a page that arrived late) to 12 hours after its last. If there are none, it opens one; if there are several, they're merged into the oldest (below).
- **What a job counts** (owner, 2026-11-13; it was distinct units before). A job opens an event once it has the threshold's number (20) of **stored Emergency messages that count**: the rows of `messages` with that `job_number`, `priority` Emergency, an `alias_id` (an aliased capcode; ignored aliases' too, as R87 counts them, question 3) and not `heartbeat` (`JobEventPages`, the same pages R87 counts everywhere else; `events.Reached`). It counts messages, not receptions: a copy from a second receiver, or a repeat within R19's 10 seconds, is the same message and adds a reception, not a row, so it counts once; the same page to two aliased capcodes is two messages (R20), so it counts twice. Non-emergency pages, pages to capcodes with no alias, and heartbeats never count. What a page says doesn't matter: its appliances (R8's `units`) aren't read. The job's pages are counted wherever they are (in this event, another, or none), so the count is the job's, not the event's.
- **"And so do the other pages of its job"**: the job's counting pages that aren't in an event yet join with it, earlier ones included, so a job's event holds the job's pages (A85). A job's pages already in another event stay there.
- **A page that doesn't open an event** joins one only if it's within 12 hours of an event that holds one of its job's pages, so a job's later pages follow it into its event and ordinary pages from elsewhere on a busy day don't.
- **Out of order and late.** Everything is in sent time, not arrival time. A late page earlier than an event's first page joins it and moves its start. A late page within 12 hours of two events **merges** them: the oldest keeps its ID and takes the other's pages and deliveries. So the events that pages make don't depend on the order they arrive in (`TestLargeEventsOutOfOrder`: three orders, each page from two receivers, give what pages in order give; `TestJobOutOfOrder`: a job's 21 pages in order, newest first and shuffled, each from two receivers, all give one event of 21 pages from the first).
- **Ending** (R87a): an event takes pages until 12 hours after its last page; a page after that opens a new one (A84's 04:00). Nothing is written when an event ends, and the app never shows whether an event is "ongoing" or "ended": the window only decides which pages join, and the app can't know whether an incident is over (owner, 2026-11-13).
- **No levels** (R87b; owner, 2026-11-13). Nothing records what opened an event or what it has met since; 00018's levels (deployment, several deployments, big job) and the codes kept per page are gone.
- **The threshold** is "Emergency pages on one job that open a large event" in Administration → Large event settings, beside the other settings: default 20, 2 to 1,000, read and set as `job_pages` by `GET`/`PUT /api/v1/admin/large-events` (`big_job_pages` before, never released). It's still stored under the key `large_event_units`, and the range is unchanged: 2 is the least that makes a job's pages a group, and 1,000 is fifty times the default (`JobEventPages` reads up to 5,000 of a job's pages), so a value stored when it counted units is a valid number of pages and an upgrade changes nothing (A77). A change judges new pages; events already recorded stay as they are (A85).

### 4. Large-event integrations (R87d)

- **Selection.** An integration selects capcodes and aliases, or large events (`"large_events": true`), never both (refused with the reason). There is nothing more to choose: no level (a level, as the API took before, is refused as a bad request). Its content is always summary, whatever was asked for, and it has no filter. In the form, "What it sends" chooses between pages and "Large events: a summary when one opens"; large events hides the selection, filter and content and says what's sent and when.
- **Firing once, when the event opens.** The detector calls `EnqueueEvent` in one place only: the branch that creates the event (`CreateLargeEvent`), in that page's transaction, under the advisory lock. It queues one delivery for each active integration that selects large events. An event is created once, so each integration gets one delivery per event. Pages, codes and jobs joining an event, and merges, never reach that branch, so they send nothing (A86, `TestLargeEventMergeFiresNothing`). An event that opened before the integration was made never fires it.
- **Merged events.** Each of the merged events was told of when it opened, so the merged event already fired and nothing is sent for the merge (owner, 2026-11-13: "don't fire twice"). Their deliveries move to the event that's kept, so an owner's delivery list still shows both, each about that event. That is the one way an integration's list can show two deliveries about one event: one for each opening, never one for the merge. (A unique index on `(integration_id, event_id)` was considered and left out: it would have to delete one of those two delivery records at each merge.)
- **The same queue, timing and safety as pages** (R50-R51b). The delivery's row is keyed by the integration and **the page that opened the event**, with `event_id` beside it: the 5-minute cut-off and the "within 5 seconds" are counted from that page (R87d), the primary key is still "never twice" (R51b), retries, pausing after 3 failures, the address guard and the secrets are unchanged. A page that arrives already 5 minutes old and opens an event is "skipped: too old", as a page is. A pending delivery whose integration has since been changed to select pages is cancelled.
- **The payload** is built when sent, from the event as it is then (jobs and Emergency pages "so far"): `event_type` `large_event`, `id` and `sent_at` of the page that opened it, `url` the event's view, and `large_event`: `id`, `started_at`, `opened_by` (`id` and `sent_at`), `jobs`, `emergency_pages` and `url`. **No page text, address, location, alias, fields, appliances, codes or levels**, for webhook, MQTT and the presets alike (`TestEventPayloadIsASummary` checks the summary has exactly those six keys, and A86 checks the bodies against every posted text, the address, the codes and the words). Presets show "Large event", then when it started and opened, the jobs, "5 Emergency pages" and the link. Home Assistant discovery declares `large_event` and `test` as the entity's event types. Send test sends a made-up event marked `"test": true`, whose `id` and `opened_by.id` are null. Documented in `docs/integrations.md`.

### 5. Retention (R87e)

The nightly run, after retention's batches, deletes every event left with no pages (`DeleteEmptyLargeEvents`) and sets the start and end of the others from the pages they still hold (`RefreshLargeEventSpans`); their numbers are counted as they're shown (`TestLargeEventRetention`).

### 6. The API and the browser

- `GET /api/v1/large-events` (newest first by start, 50 a page with a cursor): each event's `id`, `start`, `end`, `jobs` and `emergency_pages`. `GET /api/v1/large-events/{id}` adds `job_list`, its job numbers by first page. No levels, codes or appliances (A84, A85 check the JSON's keys). For every signed-in user (A29's rule: 401 without a session). `GET /api/v1/messages?event=<id>` lists an event's pages as the message list does (the search's own query, `SearchMessages`, keeps a page with a `large_event_messages` row; unset, it is one more condition that holds, as the album's is in ADR 0026, and CI's A75 speed check runs on it), and the scrubber's counts and the live stream take `event` too. With no dates chosen, the scrubber in an event's view covers the event's own days, so an old event's pages are on it. `GET` and `PUT /api/v1/admin/large-events`: the threshold, admins only.
- **Tools → Large events** (`/large-events`): one card per event, newest first: its first and last pages' times, each on its own labelled line ("First page", "Last page"; one bold run of both read as a single time; owner, 2026-11-13), and its numbers: "2 jobs · 5 Emergency pages" (never an appliance count, a level or codes; owner, 2026-11-13). Cards, not a table, so a phone needs no sideways scroll. The words "deployment" and "deployment code" appear nowhere in the app's large events, its form or its settings (the browser test checks).
- **An event's view** (`/large-events/{id}`, breadcrumbs `Tools / Large events / Large event, <start>`): its first and last pages' times, its numbers, its **Job numbers** (each a link to the job view), the line that several incidents may share an event and the app doesn't track an incident, then its pages with `MessageList`: full text (P2), current redaction and aliases (P1, R23a), ignored aliases' pages included, live updates as pages join, and the scrubber.
- **Administration → Large event settings**: the threshold. Named apart from Tools' Large events, so the menu has one entry per name.
- New icon (R77a), from Tabler as before: large events `flame`, on the menu entry, the settings entry and each card. No new tokens.

### 7. The profile (R5)

`deployment_code_pattern`, optional, in the network profile's schema: an RE2 pattern; every match in the text a pager displays (the marker removed) is a code, each kept once, in order; with a group named `code`, the group is the code. A pattern that doesn't compile or matches empty text stops the server, as other patterns do. The example network's is `\bDG[0-9]{4}\b` (SPEC.md section 10). The key keeps its name, as a machine name the owner's private profile uses (owner, 2026-11-13); the docs and the schema describe it as a code in a page that opens a large event, and the app never calls these codes "deployment codes". Network golden rows may list `deployment_codes`, checked only when listed, so existing tables (and private profiles' tables) need nothing new. Three rows are **proposed** for the owner (a code; two codes and a repeat; 5 digits and a code run into a word); they pass. `docs/profiles.md` documents both.

### 8. Appliances (R8; owner, 2026-11-13)

The app calls R8's `units` field **Appliances** wherever people see it: a message's detail (the only view in the browser that shows the field; the job view and the list show the text), the PowerShell module's list view of a message and its help, and the docs. Large events show and send no appliance count at all (R87c, R87d). The machine name stays `units` in profiles, golden tables, the schemas, the API's and the payload's JSON (`units`, `fields.units`) and the database, so existing and private profiles keep working; SPEC.md R8 and `docs/profiles.md` say so. The pages' own word (`UNITS` in the example network) is page text and is never changed. The PowerShell module's message objects keep their `Units` property, which a script may use: its list view labels it Appliances, and `Select-Object Units` still works.

## Questions for the owner

1. **Imported pages and events.** Pages imported from the old archive (R83) don't form events, so the Large events page starts at the switch-over. Grouping them would make the past events visible too (no integration would fire: R83b) but adds work to every imported Emergency page, against R83f's 500 a second. Should imported pages form events, perhaps by a one-off command after the import?
2. **Re-parsing.** Events are decided when a page arrives. A capcode aliased later, a template's profile changed, or a code pattern added doesn't regroup older pages (R23a re-parses them, but their events stay). Is that acceptable, or should a re-parse rebuild events?
3. **Ignored aliases.** A capcode whose alias is marked ignored (R27) still has an alias, so its Emergency pages count. Should ignored aliases' pages be left out?
4. **The end shown.** Decided (owner, 2026-11-13): an event's end in the app is its last page's time, and it's never shown as "ongoing" or "ended".
5. **A long job heard again.** A job that reached the threshold in an event that ended, then has another page after 12 quiet hours, opens a new event, which fires large-event integrations again. Is a long-running job meant to be one event however long it runs?
6. **Levels.** Decided (owner, 2026-11-13): no levels; an event is simply a large event, and an integration is told once, when it opens.
7. **Deployment codes in the app.** Decided (owner, 2026-11-13): users see jobs and job numbers; the app shows no count or list of codes and never says "deployment".
