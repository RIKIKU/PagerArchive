# ADR 0014: The A33 flake, and A67's missing log lines

## Status

Proposed (2026-11-01). The owner's brief after the M12 merge: ADR 0013's question 6 (A33 failed once on cld01) as its own piece of work, and A67's failure on main's CI after the merge.

## Context

On 2026-10-30, in a `scripts/stack-checks.sh` run on cld01 (`~/m12-stack-run1.log`), `TestA33WithinOneFlow` failed:

```
a33_test.go:256: A33: same flow, reset code attempt 5, wrong: ak-stage-authenticator-validate code: Invalid Token. …
a33_test.go:260: A33: same flow, reset code attempt 6, RIGHT:  
a33_test.go:262: right reset code not refused in the same flow after 5 wrong ones
```

ADR 0013 took it for slow recording of failed codes on a loaded machine. That would have been a fault in the lock (R44a), not in the test. The reviewer saw that the sixth reply's component and error text were both empty. An acceptance would have been the next stage (the new-password prompt), which has a component. The test's `executor` never looked at the HTTP status: any body that parsed as JSON became a challenge, empty if it had no `component`. And the test read "not access-denied" as "not refused". Their hypothesis: a busy Authentik answered with an error, and the test reported a security failure while throwing away the status and body that would have said so.

## A33: the cause

**The reply was not an acceptance, and not the lock letting a guess through.** The not-locked policy (blueprint) can only fail one way: it answers "not locked" when it should say "locked", and then the code stage runs. A right code there is accepted and the flow moves to the new-password prompt, `ak-stage-prompt`, which has a component. A reply with no component at all can't be that. So a failure not yet counted when the next attempt arrived would have shown up as an acceptance, and it didn't. Nothing points at the lock, so this ADR changes nothing in it.

**What gives a JSON reply with no component: Authentik's front server.** Authentik's container runs a Go server in front of its Python web server (gunicorn). When gunicorn isn't there to take a request, the Go server answers by itself, in JSON when the client asks for JSON, as the tests do (`Accept: application/json`). Probing the flow executor on a test stack every 0.1 s while gunicorn wasn't yet serving gave 400 replies, all of them:

```
{"error":"authentik starting"}  HTTP 503
```

`error` isn't the challenge's `error_message`, so the old executor made it an empty challenge: empty component, empty error text. That is exactly the sixth line above. The same Go handler sends `failed to connect to authentik backend: …` (HTTP 502) when the connection to gunicorn fails mid-request (`failed to proxy to backend` in its log); both strings are in the 2026.5.5 server binary.

**Why gunicorn wasn't there at that moment isn't proven.** The 2026-10-30 stack was removed at the end of its run, and its Authentik logs with it. What the runs below show is how Authentik's web side becomes unavailable on cld01:

- **30 runs of `TestA33WithinOneFlow` on one stack, all 4 cores loaded** (`stress-ng --cpu 4`, load average 5.5-7.3): 30 passed, no reply that wasn't a challenge. Authentik's two web workers ran the whole time (pids 322 and 323, no restarts). Its log had no warnings or errors apart from the routine `binding failed re-evaluation` (241, the lock's policy being re-evaluated) and one start-up error (the outpost's token).
- **Workers made to restart every 20 requests** (`AUTHENTIK_WEB__MAX_REQUESTS=20`; the default is 1000 ± 50, so a full stack run, with thousands of requests, sees a few) while an A67 run loaded the machine: 11 runs, 33 worker restarts. Five passed. Then gunicorn's workers hung on start (`WORKER TIMEOUT (pid:1326)`, `Worker (pid:1326) was sent SIGABRT!`, 9 times), and the Go server logged `failed to proxy to backend` while requests waited. The tests got 30-second timeouts (`no reply: … Client.Timeout exceeded while awaiting headers`), and the app answered `503 The sign-in service (Authentik) couldn't be reached` and `error=expired`. In every run where Authentik answered the attempts, the answers were the right ones (`refused as wrong` five times, then `refused by the lock`). That's an artificial setting and wasn't kept for the 50 runs below.
- **50 runs with the machine overloaded** (`stress-ng --cpu 8 --hdd 2 --hdd-bytes 256M` on cld01's 4 cores and 5 GB, load average 17-21; an export of e7fc8da), with no forced restarts. All 50 failed in setup, before any attempt at the lock: 43 at `no "invited" email to …` (Authentik's worker didn't send it in time), 3 at the app's `503 The sign-in service (Authentik) couldn't be reached` for the invite, and 4 at a request timing out (`Client.Timeout exceeded`). They checked nothing about A33 and don't count as its 50 runs. But they show the mechanism with nothing forced. gunicorn killed a hung web worker five times (`WORKER TIMEOUT (pid:4439)` at 17:46:57.892, `Worker (pid:4439) was sent SIGABRT!`), and twice a test request was in flight at that moment. The front server answered it itself, 12 ms and 18 ms later:

  ```
  17:46:57.904: not a flow challenge: HTTP 502 "{\"error\":\"failed to connect to authentik backend: EOF\"}\n"
  17:59:39.102: not a flow challenge: HTTP 502 "{\"error\":\"failed to connect to authentik backend: EOF\"}\n"
  ```

  Both were the owner's sign-in. The executor logged them, sent the same request again (`try 3 of 3`), and the sign-in went on.

So the likely cause, matching the evidence: for a moment on 2026-10-30, Authentik's front server had no web worker to hand the sixth request to and answered it itself, and the old test read that answer as a security failure. The overloaded runs above show that happening without anything forced: a worker that hangs under load is killed and the request in flight gets the front server's JSON error. What made a worker hang that day stays open; the stack was removed with its logs.

## A33: what changed

**Evidence first** (`internal/stacktest/flow_test.go`). A challenge keeps the reply's HTTP status and body, or why there was no reply. A body that isn't JSON no longer stops the test with a bare message; it becomes a reply that isn't a challenge, like any other. Every reply that isn't a flow challenge (non-2xx, or no component) is logged with both, and the time.

**Every check decides on a real answer** (`internal/stacktest/outcome_test.go`). `judge` reads the reply to an attempt at a checking stage as one of these outcomes:

- `refused by the lock`: `ak-stage-access-denied` with the deny stage's "Too many wrong attempts for this account."
- `refused as wrong`: the checking stage again with its wrong-answer message ("Invalid password", "Invalid Token", "Code does not match"), or Authentik ending the sign-in flow at the 5th wrong password.
- `accepted`: the stage after the check (the new-password prompt), or a redirect into the app.
- `refused by the app`: signing in, Authentik let the person through and the app's sign-in page refused them.
- `no answer`: anything else. That covers an error status, a body without a component, no reply, or a step that doesn't answer the attempt.

`expect` then decides. The outcome the check wants passes. `accepted`, when a refusal is wanted, fails as `SECURITY FAILURE`. Another real answer fails as `FAILED` (for example the lock refusing after only 4, or still refusing after 16 minutes). `no answer` is `TEST ERROR: … no answer, so nothing was checked:` with the status and body, whatever the check wanted. Nothing passes as "not refused" any more.

Every A33 assertion goes through them, and so does every other stack check that passed on "not signed in" or "not accepted":

- A33, all three tests: each wrong attempt must be `refused as wrong`, so the count the lock sees is known. Each right attempt after five wrong ones must be `refused by the lock`. 14 minutes later it must still be refused; 16 minutes later it must be `accepted`.
- The locked-accounts metric (R52): each wrong password must be `refused as wrong`.
- A26 (B and C deactivated) and A27 (B deleted): signing in must be refused (as wrong, by the lock or by the app).
- The password reset test: the old password must be `refused as wrong`.
- Checks that someone *can* sign in (the owner in A33 and in the akadmin test) must be `accepted`.

In `TestA33WithinOneFlow`, Authentik's own cancel at the 5th wrong password (`failed_attempts_before_cancel: 5`) ends the flow, so there is no 6th attempt in it. The old test sent one anyway and read the new flow's first page as "not accepted". Now it says so, and the next attempt, in a new flow, must be refused by the lock. The reset-code half has no such cancel and checks the 6th attempt in the same flow.

The check's addresses are made unique per run (`a33sameflow-<n>@example.com`), so it can run again and again on one stack (`go test -count`). That's how the runs here were made.

**A bounded retry, for transient replies only.** `executor` sends the same request again, up to 3 tries in all, 1 s and 2 s apart, each logged, only when the reply was a 5xx or there was none. Authentik's `authentik starting` (503) and `failed to connect to authentik backend` (502) are both 5xx. A 4xx, a body without a component and every real answer are never resent.

Why that's safe given how the lock counts. The lock counts an account's `login_failed` events plus the failure count on its email device, and nothing else. A request that carries a password or code is resent only after reading that count (`failureCount`, from Authentik's database). If it changed since before the first try, Authentik took the attempt, so it isn't sent again. The reply is returned as it came, and the check reports it as a test error. If it didn't change, the first try wasn't counted: the front server answered without reaching a worker, or the attempt never reached the check. The resend is then the only attempt that counts. So a retried attempt can't count twice, and a counted one can't be skipped. Where there's no database to ask, a password or code is never resent.

A retry can't turn an acceptance into a pass either. An accepted attempt moves the flow on, and that state is Authentik's, not the test's. A resend then reaches the next stage, and its reply is that stage (`accepted`). A refusal by the lock is recorded by Authentik too, so a resend can only be refused again or be no answer. Other requests (fetching a challenge, typing the address, choosing the email device) check nothing and change no count; resending them is harmless. Choosing the device again just sends a fresh code, and the test reads the newest one.

## A67 on main: no client lines in Loki

A67 failed on main's CI after the M12 merge (run 41185641768, b6404c4, "Example monitoring stack (A65, A67)"): `no Loki lines at all for radio-a-194855 (so nothing checked)`, and the same for the other two clients. The owner asked which it was: (a) the check looking once, too early, or (b) the client's lines not being exported, under R73.

**It was neither: Loki refused every write on that runner.** The job's artifact (`monitoring-41185641768-1`, `monitoring-stack.log`) has this from Loki at 08:43:47, five minutes before the clients started:

```
caller=wal.go:215 msg="disk usage exceeded threshold, throttling writes" usage_percent=90.55% threshold_percent=90.00% component=wal
```

From then on, 875 pushes were refused with `err="Ingester is shutting down"`. That is Loki's answer to every write while the disk under its write-ahead log is over 90% full. Alloy dropped 28 batches of log lines bound for Loki (`Exporting failed. Dropping data.` … `otelcol.exporter.otlphttp.loki` … `responded with HTTP Status Code 503, Message=… Ingester is shutting down`), the first at 08:48:36. It dropped none bound for Tempo or Prometheus, which is why everything else in A65 and A67 passed. Main's run hasn't been run again: on 2026-11-01, `gh run view 41185641768` gives `"attempt":1,"conclusion":"failure"`.

The runner's disk was 90.55% full: the job builds the API and client images and pulls the five monitoring images onto a runner image that comes with many toolchains. The branch's three CI runs, on the same code, have neither line in their artifacts (`grep -c "Ingester is shutting down"`: 0, 0, 0).

The clients did their part. Each logged its one start-up line at 08:48:56 (`level=INFO msg=receiving …`, `level=INFO msg="reading decoder output on stdin" …`), as the job's log shows, because the test prints each client's last lines when it fails. None logged `dropping telemetry`, so each line was exported to Alloy, which couldn't pass it on.

**The live copy's 13 lines** are every line the clients logged. I read them read-only: Loki through Grafana, and `docker logs --since 24h` of the two clients. Since their last start at 05:12:

- The replay client logged `reading decoder output on stdin` twice: at 05:12:07, and at 05:27:04, after the 370 s stop in the trial.
- radio-demo logged `receiving` once, at 05:12:08.

All three are in Loki, with the same timestamps. The other ten are from the containers before the upgrade: `server unreachable, will retry` eight times at 05:09-05:11 while the API was rebuilt, and two start-up lines. A client logs when it starts, when it can't reach the API or a page is refused or dropped, and when it stops. A page decoded or sent is a span and a metric, not a log line. So 13 a day is what healthy clients log.

**A real gap under R73, found on the way.** The last line a client logs is why it stopped, and that line was never exported. `main` logged `client stopped` with the error after `run` returned, when telemetry had already shut down. Now `run` logs it, through the exporting logger, before shutting telemetry down. `main` logs only errors from before telemetry started (bad settings), which can't be exported.

`TestR73EveryClientLineExported` (acceptance) runs the real client twice against a test collector. Once it can't reach the API and then runs out of input; once it has no `rtl_fm` to start. Every line it logged to stderr after telemetry started must arrive at the collector. The exceptions are the telemetry package's own lines (`telemetry on`, a signal being off, `dropping telemetry`): they're about the export itself and stay on stdout, as ADR 0013 decided for the dropping line. Against b6404c4's client the check says `logged by the client but not exported: ["ERROR client stopped"] (of 7 lines)`; with the fix, all 7 arrive.

**What changed in A67 and around it:**

- A67 waits up to 2 minutes for each client's start-up line to reach Loki, before searching Loki's lines for rtl_fm's text. If one never comes, it fails and says so, with what the client logged (`docker logs`) and whether Loki refused writes (counted from Loki's own log). It logs each client's lines in Loki, with when each was logged.
- `scripts/monitoring-checks.sh` prints the disk use under Docker's data before and after the checks. If it's 85% or more, the script stops at once and says why, rather than letting Loki refuse logs part-way.
- CI's monitoring job removes toolchains it never uses (.NET, Android, GHC, CodeQL) before the checks, and prints `df` before and after.
- docs/monitoring.md, "When something doesn't show up": Loki refusing logs over 90% disk use, and why a client has few log lines.

## Docs-only pushes don't run CI (owner, 2026-11-01)

Every spec or ADR commit to main ran the whole workflow (about 20 jobs, the stack and budget runs among them), and since M12 a green run on main also publishes.

**The filter.** The workflow's `push` and `pull_request` triggers have a path filter. GitHub doesn't allow `paths` and `paths-ignore` together, and `paths-ignore` can't make an exception, so it's `paths` with negations, in order:

```yaml
paths:
  - "**"
  - "!SPEC.md"
  - "!docs/**"
  - "!**.md"
  - "web/static/**"
```

A push or pull request whose changed files all match a negation starts no run at all; no job starts and exits. Any other file changed, including through a merge that brings code in, runs everything as before. `workflow_dispatch` has no filter.

**Docs a build or test reads, which must still run CI.** I searched the code, tests, scripts, Dockerfiles, `.dockerignore`, the module manifest and the workflow for anything that reads a file under `docs/` or a `.md` file. The checks were string literals and path joins naming `docs` or `.md`, `go:embed` patterns, `COPY` lines, the module's tests and manifest, and the workflow's steps. They found one:

- `web/static/map/sprites/LICENSE.md` (the map sprites' MIT licence). SvelteKit copies `web/static` into `web/build`, which `web/web.go` embeds in the server binary. `.dockerignore`'s `*.md` matches only files at the top, so the file is in the image. Checked: the stacktest image's binary contains the licence text (`grep -a -c "IMPLIED, INCLUDING BUT NOT LIMITED TO THE WARRANTIES OF MERCHANTABILITY, FITNESS"`: 1) and the path `map/sprites/LICENSE.md`. The last pattern, `web/static/**`, takes it back in: a later positive match includes a path again.

Nothing else is read. Every other mention of `docs/…` or `SPEC.md` in code is a comment, or a log message naming a page for the reader (`INTEGRATION_SECRETS_KEY is not set (docs/deploy.md)`). The PowerShell module's tests name sections of `docs/powershell-guidelines.md` but read only the module's own files (manifest, `Format.ps1xml`, `Types.ps1xml`, `about_PagerArchive.help.txt`, `PSScriptAnalyzerSettings.psd1`). The images leave out `docs/` and top-level Markdown (`.dockerignore`). The screenshots under `docs/monitoring/` are written by `monitoring-screenshots.sh`, never read. `CLAUDE.md` and `README.md` are read by people only.

**What depends on CI:**

- **Tags and releases** still run and publish as before. GitHub's "Workflow syntax for GitHub Actions", section `on.<push|pull_request|pull_request_target>.<paths|paths-ignore>`: "Path filters are not evaluated for pushes of tags."
- **Branch protection.** `gh api repos/RIKIKU/PagerArchive/branches/main/protection` answers `Branch not protected (HTTP 404)`. `gh api repos/RIKIKU/PagerArchive/rulesets` answers `[]`, and the branch's `required_status_checks` are empty (`enforcement_level: off`). So no pull request waits on a skipped run. The same section of GitHub's docs warns that "checks associated with that workflow will remain in a "Pending" state". If required checks are ever added, a docs-only pull request would be blocked, and the filter would have to change too.
- **Publishing.** A docs-only push to main publishes nothing, which is right: no image or module changed. The next push that changes code publishes as before.
- **GitHub's limits.** A push of more than 1,000 commits, or one whose diff times out, always runs, by GitHub's rule in the same section.

**Since 2026-11-12 (ADR 0025)** a run that does start runs only the checks its changed files affect, worked out by the first job; documentation in it runs nothing. This filter, for a push or pull request of documentation alone, stands. The "Branch protection" point above is out of date: main's ruleset now requires "All checks passed" (ADR 0022), so a pull request of documentation alone waits for a check that never reports (ADR 0025's question 1).

## Mutations

Added to `scripts/mutation-checks.sh`. A new runner, `stack:<regexp>`, runs account checks through `stack-checks.sh`. A mutation run with `must` set counts as caught only if the test fails with that text.

- **The lock allows a 6th attempt** (blueprint, `LIMIT, WINDOW = 6, …`): `TestA33WithinOneFlow` must fail with `SECURITY FAILURE`, not as a test error.
- **The executor's reply to a 500 is an empty challenge, its status and body dropped** (as before): `TestRepliesThatAreNotAnswers` must fail.
- **The executor retries any reply**, not only transient ones: `TestOnlyTransientRepliesAreRetried` must fail.
- **The executor resends a password or code without asking whether Authentik counted it**: the same test must fail.
- **The client logs why it stopped after telemetry has shut down**: `TestR73EveryClientLineExported` must fail.

A mutated run where no test failed used to print only `SURVIVED: no test failed`. The script now also prints the run's last lines, so a stack that never started shows as that, not as a survivor with no reason. It also prints the unmutated acceptance run's failures, not only its last line.
