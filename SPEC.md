# PagerArchive: Specification

**Status:** Draft 0.2 (2026-10-09), not yet approved for implementation
**Owner:** Kyle

## How to use this spec (implementing agent: read first)

1. Read this whole document and `CLAUDE.md` before doing anything.
2. **Principles (section 1) override every other section.** Where two principles conflict, the lower-numbered one wins.
3. **`OPEN` means undecided.** Don't guess. Stop and ask the owner. Work that doesn't depend on an OPEN item can continue.
4. **Before writing any code**, write `docs/adr/0001-technology-stack.md` recommending the stack against the constraints in section 8, and wait for the owner to approve it.
5. Golden tables (`profiles/**/golden-*.json`, in this repo and in any private profile repo) are **owned by the owner**. You may propose new rows, but never change an expected value to make a test pass.
6. "Done" means every acceptance check in section 9 passes, plus the end-to-end verification in section 11, with evidence (commands run and their output).
7. **Implementer discretion.** Where this spec is silent, choose the simplest option consistent with the principles, constraints and requirements, and record it in an ADR (`docs/adr/`). Ask the owner only when the choice changes what users see, what data is kept, privacy or security. **UI presentation details** (date and time formats, layouts, icon sets, the design of admin screens) are the implementer's choice within the requirements. The defaults in section 14 apply.
8. **ADR approval:** an ADR is approved when its status reads `Status: Accepted`, set by the owner or by Claude at the owner's explicit instruction, and committed.
9. **Repos:** this repo is `github.com/RIKIKU/PagerArchive`. The owner's private profile repo is checked out next to it at `../PagerArchive-profiles` on the build machine.
10. **Golden row status:** rows marked `"status": "proposed"` run in CI and are reported, but don't fail the build until the owner changes them to `"confirmed"`.

## 1. Principles

- **P1. Sensitive personal details are never stored.** Details matched by the network profile's redaction rules (for example patient age and gender, phone numbers, access codes) are removed before anything is stored, logged or shown. Retroactive redaction also covers derived data (dedup hashes, parsed fields, job links, search indexes), followed by routine database vacuuming. Database write-ahead logs and backups are out of scope. **No server-side log line, and no client error or diagnostic output, ever contains page text** (application, web server, reverse proxy, database or error logs, and OpenTelemetry traces, metrics and logs: R70). When a redaction rule is added or changed, it's applied to already-stored messages at the next nightly run (R45a). The one exception is the client's optional console output (R13a), which is never written to a file by the client.
- **P2. The full message is always shown.** Every page is stored and displayed in full, after the removals in P1. Parsed fields are extra metadata for search, filters, grouping, the map and reports. They never replace or hide the text. A parse failure, a missing alias or a wrong template can make a page harder to find, but never harder to read.
- **P3. The parser extracts; the display interprets.** Parsed fields hold the literal text from the page. Turning codes into labels is a separate display step driven by profiles.

## 2. Problem and users

Many emergency and organisational paging networks broadcast **POCSAG** pages that can be received with an inexpensive RTL-SDR dongle and decoded with `multimon-ng`. People who follow a network want to archive those pages, browse them live, search them, see them on a map, and look up what a given pager group has received.

PagerArchive is a self-hosted, resource-light archive for any POCSAG network. Network-specific knowledge (page formats, which capcodes to ignore, what must be redacted, how event types group into categories) lives in **configuration profiles**, not in code.

PagerArchive is for **people interested in what's happening on their network. It is not a tool for harassment.**

## 3. Glossary

| Term | Meaning |
|---|---|
| Page / message | One POCSAG transmission to one capcode |
| Capcode | The pager address a page was sent to, stored zero-padded to 7 digits (`0579064`) |
| Client / receiver | A machine with an RTL-SDR dongle that decodes pages and posts them to the server |
| Priority marker | The first 2 characters of a page's text, which some networks use to signal its priority (the receiving pager typically doesn't display them). Defined by the network profile |
| Priority | Emergency, Non-emergency, Admin, or `null`, derived from the priority marker |
| Network profile | One JSON file per deployment: rules that apply to every page on the network (section 6.3) |
| Agency profile | A JSON file describing one agency's page formats (section 6.4). Attached to alias templates |
| Alias | A human-readable name for a capcode or capcode pattern, linked to a template |
| Template | Shared alias settings: agency name, icon, colour, and optionally an agency profile |
| Job number | An identifier, extracted by a profile, that links pages about the same incident |
| Call sign | The call sign of the unit a copy was paged to, when the page names it (often a short code at the end). Not a group of brigades or stations: the field was called `group` until 2026-11-17 (R8) |
| Call signs | The call signs of the units a page dispatches, and the roles people hold that it names (a duty officer, say), kept apart from its appliances when its agency profile says which of its tokens they are (R7, R8; ADR 0047). The paged unit's own call sign is its Call sign |
| Heartbeat | A periodic page the network sends to show it's alive. Its capcodes are listed in the network profile |
| Golden table | A JSON file of real-format raw lines and the exact fields they must parse to |
| Album | A named list of messages one user keeps for later (R82), with an optional description and a note on each message (R82f). Only its creator sees it |
| Look | A named style for the whole UI: colours, type, spacing, corners and how priority is shown, each in light and dark (R82c). Harbour is the default |
| Area | A named polygon from one of the network profile's layers of areas, such as a district, outlined on the map; a located page is in the one of each layer its point falls in (R88) |
| Layer (of areas) | One file of areas the network profile names, such as one agency's districts, with what one is called, its credit and how the map outlines it; a profile may name several, which can overlap one another (R88) |
| Service account | A read-only account for a tool, not a person, owned by an admin and made only on the server; it reads what an admin reads, except people's personal details, and changes nothing (R62a) |

## 4. Scope

### In scope for v1
Receiving clients, ingest and redaction, profile-driven parsing, job grouping, map locations, aliases and templates, the browser UI with live updates and multi-criteria search, a per-group report, client liveness, invite-only accounts and retention.

### Out of scope
- **Incident state or resource tracking.** The app never infers or shows whether an incident is active, cancelled or finished, or where resources are. Pages carry too little information for that. Follow-up pages (cancellations, updates) are stored and grouped like any other page and never interpreted.
- **Operational alerting** (owner, 2026-10-16). PagerArchive is not critical infrastructure and must not replace issued pagers or an agency's official alerting. Integrations are a convenience: delivery is best-effort, and the app doesn't add features whose purpose is guaranteed alerting (e.g. repeat-until-acknowledged alarms, delivery receipts, escalation).
- **A native mobile app.** The browser UI must work well on phones instead, and can be installed on one's home screen (section 7.28).
- **Notifications from the installed app** (owner, 2026-11-17: "hold off on notifications ... I don't want people to use it as an alerting service for operational pages"). The installed app (R90) sends no push notifications, never asks permission to show them, and does no background sync. That would make it an alerting service, which it isn't (Operational alerting, above). Integrations (section 7.11) stay the way to forward pages.
- **Automatic client updates** (wanted later). v1 publishes multi-arch images and documents manual updates.
- **Managing clients in the browser** (wanted later, owner 2026-10-13). Until then they are changed by CLI. Aliases are managed in the browser from M6 (section 7.12, owner 2026-10-16), and templates from M10 (section 7.14, owner 2026-10-20).
- **API keys** (owner, 2026-10-20). Command-line work signs in as a person (R60). Unattended jobs, if ever wanted, would be a worker inside PagerArchive, not a script.
- **PowerShell access for users** (wanted later, owner 2026-10-20). Users would request access and an admin would grant it. The module would then work for them with their own role's permissions (R60).
- **Writing an identity provider.**
- **Linking several email addresses to one person.** Accepted risk: one person may hold more than one account. Invite attribution and invite-tree deactivation (section 7.9) are the remedy.
- **Public geocoding services** (section 8).
- **Code plugins.** Network knowledge is configuration (JSON profiles), not code.
- **System monitoring and alerting** (uptime, performance, a receiver going quiet). The app exposes metrics (R52) and telemetry (section 7.16) for an external stack to alert on, such as the example Grafana stack in `deploy/` (R76). The app itself sends no system alerts. Forwarding **pages** to users' own systems is in scope (section 7.11).
- **Anti-harassment features beyond invite-only access** (for example an audit log of searches) in v1.

## 5. Architecture (decided)

```
RTL-SDR → rtl_fm → multimon-ng → [client] ──HTTPS──▶ [server API] ──▶ PostgreSQL + PostGIS
                                                    ▲        │    ▲
                                       Authentik ───┘        │    └── network + agency profiles (JSON, mounted read-only)
                                                             └── live updates ──▶ browser UI
```

Many clients post to one server. Each client records its own receive time. The server sits behind the deployment's **own reverse proxy** (which handles TLS) and is reachable by remote clients. The docs include a working example configuration for a common nginx-based proxy (e.g. linuxserver/swag), including whatever live updates need. Profiles are files mounted into the server container. They aren't stored in the database, so a deployment can keep them in its own (private) repository.

## 6. Profiles

### 6.1 Format
- **R1.** Profiles are **JSON** files, validated against JSON Schemas shipped in the repo. An invalid profile stops the server from starting, with an error naming the file, path and problem.
- **R2.** The repo ships a complete **example profile** for a made-up network (`profiles/example/`), with golden tables. It's the documentation and the default test fixture. The implementer writes the example network and agency profile JSON, the JSON Schemas and a small example address dataset; they must pass the owner's example golden tables.

### 6.2 How a page finds its rules
- **R3.** capcode → alias (section 7.5) → template → agency profile. The agency profile's **formats are tried in order**. The first format that matches parses the page.
- **R4.** If the capcode has no alias, its template has no agency profile, or no format matches, the page is still stored and shown in full (P2). No format matching → flagged `parse_failed`. No alias or no agency profile → **text only**, not flagged. There is no default agency profile. Network-level rules (priority, redaction, job number patterns) still apply to every page.

### 6.3 Network profile (one per deployment)
- **R5.** Defines:
  - **priority markers**: which 2-character prefixes mean Emergency, Non-emergency and Admin
  - **ignored capcodes**: capcodes or ranges whose pages are dropped and never stored (network housekeeping traffic)
  - **heartbeat capcodes** (kept and shown; used for liveness)
  - **redaction rules**: ordered patterns, each with a name, replaced by `REDACTED` (P1), plus **must-not-match examples** that must survive unchanged
  - **event categories**: a table mapping event-type codes to report categories, with "Other" for unmapped codes
  - **address dataset**: the local open-data file used for geocoding, and how grid references are interpreted (section 7.4)
  - **job number patterns** that apply to every agency (e.g. a prefix letter plus digits)
  - **deployment code pattern** (optional; owner, 2026-11-12): a code in a page that opens a large event (R87), such as one naming a pre-formed group of appliances sent together; with no pattern, only a job's number of Emergency pages opens events. The key stays `deployment_code_pattern` (a machine name), but the app never calls these codes "deployment codes" and never counts or lists them (owner, 2026-11-13)
  - **areas** (optional; owner, 2026-11-16; several layers, owner, 2026-11-17): one or more **layers**, each a GeoJSON file of named polygons with its id, what one is called, the property naming each, the data's attribution and how the map outlines it (R88). Left out of what decides a re-parse (R88d)
- **R6.** The network profile has its own golden table covering priority markers, ignored capcodes and every redaction rule, including the must-not-match examples.

### 6.4 Agency profile (attached to templates)
- **R7.** Defines an ordered list of **formats**. Each format has a name, optionally the **priorities it applies to**, a match rule and extraction rules for fields. A format may extract nothing ("text-only format", e.g. freeform admin pages), which counts as a match, not a failure. Formats run on the redacted text with the priority marker removed. Optionally, **field values that open a large event** (R87; owner, 2026-11-14): one of the agency's text fields and the values of it that do, each listed, such as an alarm level high enough to mean something big (`large_event_fields`). Optionally, **level fields** (owner, 2026-11-18; ADR 0045): one of the agency's text fields whose values are levels in an order, such as an alarm level, with what the field is called and its values lowest first, each with a label (`levels`), so an integration can fire at or above one (R49a). A value not listed is no level: never at or above any. Levels and their labels are shown only in the integration form (R87b); a `labels` entry for the same field's values is separate and shows as any label does (R87b). They change nothing a page says, so they're left out of what decides a re-parse (R23a). Optionally, a split field's **tokens moved into another list** (owner, 2026-11-18: a call sign alone is a call sign, not an appliance; a call sign with a number or a suffix is an appliance; and the roles people hold go with the call signs, with no list of their own; ADR 0047): a field a format splits into a list (R8's `units`) can name a list field and which of its tokens go there instead (`into`), by **known values**, listed in the profile or in a file beside it, and by a **pattern** a whole token matches. A token that is one of the values or matches the pattern moves, in its order; any other token stays where it was split. Values are compared exactly as extracted (P3), so a known call sign with anything after it isn't that call sign. A network's list of its call signs is its profile's data, never the app's. The values, their file and the pattern change what pages say, so they count in what decides a re-parse (R23a).
- **R8.** Standard fields that core features rely on: `job_number` (grouping), `event_type` (reports), `description`, `address`, `locality` and `grid_ref` (map), `units` (list: the appliances a page names), `call_sign` (the paged unit's call sign), `call_signs` (list: the call signs of the units a page dispatches and the roles it names, apart from its appliances; owner, 2026-11-18; ADR 0047). A format may also define **extra fields** with any name; they're stored, searchable and shown. Fields not present in a page are `null`. Values are literal (P3). The app calls `units` **Appliances** wherever people see it (a message's detail, the PowerShell module's display and help, the docs); its machine name stays `units` in profiles, golden tables, schemas, the API's JSON and the database, so existing and private profiles keep working (owner, 2026-11-13). `call_sign` was called `group` until 2026-11-17, and its name changed everywhere, so that "group" stays free for a group of brigades (owner, 2026-11-17: "If we ever add a feature to list what group a brigade is a member of"; ADR 0040). The app shows it as **Call sign**. The old name still works where people and installs wrote it before: a profile's capture, `fields` option, label table or `large_event_fields` rule named `group`, and a golden row expecting `group`, are read as `call_sign`, and validate-profile and the server's log warn to rename them; the search box's `group:` and an address's `group=`, bookmarked or shared before, are read as `callsign:`, and new addresses say `callsign=` (R33a); and the API accepts `group` and `group_like` in a search and `group` in an integration's filter, but answers only with `call_sign`, and integrations' payloads carry `fields.call_sign` (payload version 2). Pages, integrations' filters and the module's `-Group` (now `-CallSign`) keep working across the upgrade, with their values. **Call signs** (owner, 2026-11-19, choosing ADR 0047's option (b) and its names; ADR 0047): `call_signs` is filled by a format that captures it or moves tokens into it (R7); otherwise it's `null`, as it is for every page until a profile does. `call_sign` stays one value: a page that names several call signs was still paged to one unit, and each copy keeps its own (R20, A1). The app shows `call_signs` as **Call signs**, after Appliances in a message's detail view; the message list's row doesn't show it (R31). The API's messages carry it beside `units`, a Full payload's `fields` carries it (`fields.call_signs`; the payload's version stays 2, as a key is only added; owner, 2026-11-19), and the module's messages carry it as `CallSigns`. The search box has no key for it and integrations no filter on it (owner, 2026-11-19: "I doubt anyone is going to want to search for the call sign or trigger an integration on it"): its tokens are in the page's text, so text search finds them, and `callsign:` stays the paged unit's call sign, so an integration filtered to a call sign isn't told twice of one page sent to two capcodes that both name it (R20, R49). Only `units` are appliances, in reports too (R38f, R38h).
- **R9.** Optional **label tables** map codes to display labels (e.g. an event-type code to a readable name).
- **R10.** Each agency profile ships a **golden table**: raw lines and their exact expected fields, one row per format variant. Every row must pass in CI. The repo ships a `validate-profile` command that runs any profile's golden tables, so private profile repos can test themselves. `validate-profile` runs without a database and pairs agency tables with a named network profile.
- **R11.** **Decided** (ADR 0001, accepted by the owner 2026-10-09): RE2 regular expressions with named groups, plus `address_split` anchored on the address dataset's street list. Original question: the extraction language. The ADR proposes one that can express ordered alternatives and optional segments. Regular expressions with named groups are the obvious candidate, but the hardest real format has unmarked boundaries between a description, an optional premises name and an address, so the ADR must show it can handle the private profile's golden rows. Those can't be copied into this repo: build sessions run on the owner's machine with the private profile repo checked out alongside (path given by the owner), and the ADR may describe its rows only in general terms.

## 7. Requirements

### 7.1 Clients
- **R12.** The client reads `multimon-ng` output lines on stdin, e.g. `POCSAG512: Address:  579064  Function: 0  Alpha:   <text>`, and posts each page to the server with: capcode (zero-padded to 7 digits), raw text, receive time (UTC) and client ID. POCSAG at 512, 1200 and 2400 baud. Numeric pages are stored as text. Tone-only pages (no text) are ignored. The client turns decoder output into an internal record (capcode, function code, baud rate, text, receive time) through a **decoder adapter**; v1 ships only the `multimon-ng` adapter, so other decoders can be added later without redesign.
- **R13.** Clients run as a Docker container with the USB dongle mapped through, or natively on a Raspberry Pi (arm64). The client container **runs the radio pipeline itself** (`rtl_fm` and `multimon-ng` in v1, configured by settings: frequency, gain, PPM, baud rates); reading lines from stdin stays supported. Clients must keep their clocks in sync with NTP.
- **R13a.** The client may print decoded page text to its console (stdout) for troubleshooting. This is **off by default** (setting `PRINT_PAGES=true`). The client never writes page text to a file. The docs warn that Docker's default logging driver stores container output on disk, and show how to limit or disable that.
- **R14.** Each client authenticates with **its own API key**, issued and revoked by an admin; the key determines the client ID (owner decision, 2026-10-09; details in ADR 0002).
- **R14a. A key sent in the clear** (owner, 2026-11-16: security review). A client whose `SERVER_URL` is plain `http://` to anywhere but its own machine (`localhost`, `127.0.0.0/8`, `::1`) logs a **warning** at every start: its key crosses the network unencrypted, and with it anyone on the way can post pages as that receiver. The warning says to use the server's `https://` URL. It isn't refused: the docs have told receivers on the server's own network to use its LAN address, so refusing would stop working receivers at their next upgrade. `ALLOW_PLAIN_HTTP=true` says the network is the owner's own, or a VPN, and stops the warning.
- **R15.** When the server is unreachable, the client buffers pages **in memory only** (never on disk, because client-side text isn't redacted) and retries with backoff, keeping the original receive times. The buffer is capped (implementer's choice), and its contents are lost if the client restarts.

### 7.2 Ingest (in this order, before storing)
- **R16.** Pages to the network profile's **ignored capcodes** are dropped. They still update the receiving client's last-seen time (no text is recorded).
- **R17.** Control tokens printed by `multimon-ng` (e.g. `<NUL>`) are removed.
- **R18.** The network profile's **redaction rules** are applied (P1).
- **R19.** **Deduplication:** the key is a hash of capcode + cleaned text. A page whose key was first stored no more than **10 seconds** earlier (by receive time, measured from the first copy) is the same transmission, whether it comes from another client or the same one (networks often repeat pages deliberately). It isn't stored again, but the extra client's receive time is recorded.
- **R20.** Every capcode's copy is stored as its own message, even when the text is otherwise identical.
- **R21.** A message's **sent time** is the earliest receive time among the clients that heard it.
- **R22.** The **raw text** (after R17–R18) is stored, including the priority marker. Priority comes from the marker (R5).

### 7.3 Job grouping
- **R23.** Messages with the same job number are grouped into one job, on a best-effort basis (one incident may have several job numbers; that's acceptable). **Any page containing a job number joins that job**, including follow-ups and admin pages that mention it. Pages without a job number are never grouped. If a format extracts a job number, that one is used; otherwise the first match of the network job pattern is written to `job_number`. Job numbers are grouped for all time (no time window).
- **R23a.** When an alias, template or profile changes, affected messages are **re-parsed (and re-geocoded) in the background**. Parsed fields are stored. Aliases are always shown as they are *now*, not as they were when a page arrived. Marking an alias ignored or not re-parses its pages too, and a re-parse rebuilds the large events around the pages it touched (R87f; owner, 2026-11-14). A re-parse of the whole archive takes days on a production-sized one, so it's a long job (R91). So what changes nothing a page says doesn't re-parse (owner, 2026-11-18; ADR 0045): an agency profile's labels, levels (R49a), description and comments are left out of what decides it, as the network profile's areas are (R88d); its formats (with any file of values a format's `into` reads, R7; ADR 0047) and `large_event_fields` count. The upgrade that made it so re-parses nothing for profiles unchanged since the last start.
- **R23b. Re-parse progress** (owner, 2026-11-18: "Let's add some more logging to the reparse so we can see the progress in Grafana next time"; ADR 0041). A re-parse of the whole archive takes hours on a large one, so how far it has got is shown, as counts only (P1-P3: never a page's text, capcode, address or locality, nor a capcode pattern). When a run starts, it counts the messages it has to do (once, for each pattern), and logs **"re-parse started"** with its requests' reasons (the code's own reasons as codes, such as `profiles_changed`; any other text is `other`), how many requests and patterns, and that total. While it runs, it logs **"re-parse progress"** every 30 seconds: done, total, percent, messages a minute since it started, and the seconds left at that rate; it does even when nothing has moved, so a stuck run shows. The finished line, "re-parsed messages", has the count, the requests, the seconds it took and the rate. R52's endpoint has whether a re-parse is running, its state (R23c), the run's total and done so far (the last run's while none runs, and a paused or stopped run's while it's held), when it started, and a counter of the messages re-parsed since the API started, with no labels. Pages stored while a run goes are re-parsed by it too, so it can do a few more than it counted; its total is then what it did. A run stays running while it rebuilds the large events after (R87f). The example monitoring stack shows it (R76). What is re-parsed, and how, doesn't change. A restart carries a run on from where it got to (R23c).
- **R23c. Re-parse: resumable, pauseable, stoppable and restartable** (owner, 2026-11-18; ADR 0043). The re-parse is a long job, and this brings it up to R91: restartable, resumable, pauseable and stoppable as R91 defines them. Observable is R23b. A re-parse is a **run** kept in the database: its reasons (R23b's codes, never a request's text), its capcode patterns and, for each, the last message it has done (each is walked by message ID), its total and done, when it started, and its state: **running**, **paused** or **stopped**, or **idle** when no run is unfinished. Each batch of pages (500) is re-parsed in one transaction with its run's place, so each page is done or not, never half done, and what the run says it has done, it has. What a re-parse does to a page doesn't change.
  - **Resumable.** After a crash, a restart or an upgrade, a run carries on from the last batch it finished, not from the start: no page is done twice beyond the batch in hand, and none is skipped. It rebuilds the large events around the pages it did when it finishes (R87f), from the days of their sent times kept with each batch. A batch that fails is rolled back and done again from the same place; nothing is queued again.
  - **The profiles change.** A run that hadn't finished when the start-up check finds the profiles or address dataset changed (section 14) has parsed its pages with the old ones, so it starts again from the beginning, over every message, in the state it was in (a paused or stopped run stays so, until an admin carries it on or starts it again). The new hash is saved in the same transaction. With no unfinished run, a full re-parse is queued, as before.
  - **Changes while a run is under way** (an alias, template or profile changed) wait for the next run, as they did: they aren't merged into the run, and wait while it's paused or stopped too. Start again takes them in.
  - **Pauseable.** An admin pauses a running run: it stops after the page in hand and finishes that batch. It stays paused across restarts and upgrades, and Resume carries it on from where it got to.
  - **Stoppable.** An admin stops a running or paused run: the pages it has done stay done, the rest stay as they were parsed before, and the large events around the pages it did are rebuilt. It shows as stopped, across restarts, until it's started again; a stopped run can't be resumed.
  - **Restartable.** An admin starts the run (the last one, while idle) again from the beginning, whatever its state, with the changes waiting. Before any re-parse there's nothing to start again.
  - **Where.** **Administration → Re-parse**, on phones and desktop: the state, done of total and percent, the rate and time left while it runs, when it started (or finished, or last changed state), why (its reasons in words) and the changes waiting, with **Pause**, **Resume**, **Stop** (asks first) and **Start again** (asks first) as the state allows; Administration's start page tags it while it isn't idle. The PowerShell module (R59): `Get-PagerArchiveReparse`, `Suspend-PagerArchiveReparse`, `Resume-PagerArchiveReparse`, `Stop-PagerArchiveReparse` and `Start-PagerArchiveReparse`. Both use the API, admins only: `GET /api/v1/admin/reparse` and `POST /api/v1/admin/reparse/pause`, `/resume`, `/stop` and `/start`; a change the state doesn't allow is refused (409) with a code (`reparse_not_running`, `reparse_not_paused`, `reparse_stopped`, `reparse_none`). Each admin's change is logged with their user ID, as other admin actions are.
  - **Observable.** R52's endpoint has the state as a number (0 idle, 1 running, 2 paused, 3 stopped); the example monitoring stack's Re-parse row (R76) says Idle, Running, Paused or Stopped, with the progress held while paused or stopped. Each change of state is logged: the admin's ("re-parse paused", "re-parse resumed", "re-parse stopped", "re-parse started again"), "re-parse carried on" when a run carries on, and the profile change's start from the beginning. Counts and codes only (P1-P3).
  - The re-parse of the pages retroactive redaction changes (P1) isn't this run: it's part of retroactive redaction's own (R45a), each page's in the same transaction as its new text, and it's paused, stopped and carried on with that one, not with this.


### 7.4 Location
- **R24.** The address (with its locality) is geocoded **locally** against the address dataset named in the network profile. If a profile doesn't extract `locality` separately, the geocoder matches the end of the address against the dataset's localities. The dataset's attribution is shown.
  - **A page's derived locality** (owner's report, 2026-11-15: Busiest localities showed only "No locality" for a network whose profile has no `locality` field; ADR 0034). The locality the geocoder settles on, as R25 finds it for the grid reference (the parsed address's, else the `locality` field's, else the end of the description when no address was split from it), is kept beside a page whose profile gives no `locality`, when the address dataset has that locality. It's derived, not parsed: the page's `locality` field stays `null` (P3), and it isn't shown, searched, exported or sent to integrations as one; reports count it (R38a). A profile's own field always wins. It's worked out again whenever the page is re-parsed (R23a), so a new dataset changes it, and it goes with the page (R45). Pages stored before it was kept get theirs once, in the background, after the upgrade, and the report counts are then made again: until then, reports count the localities pages had before.
- **R25.** If the address can't be geocoded and the page has a grid reference, the grid reference is resolved as the network profile describes. For the case that motivated this: a 6-digit MGRS easting/northing without zone or 100 km square, completed from the zone and square containing the page's locality, giving a point accurate to 100 m.
- **R26.** If both exist and are more than **1 km** apart (owner, 2026-10-13), the message is flagged `location_mismatch` (admins only, R35c). When the address has no house number and is placed at its street's centroid (section 14), the distance is from the grid reference's point to the **nearest address point on that street in that locality**, so a long road isn't flagged just for being long (owner, 2026-10-13).

### 7.5 Aliases and templates
- **R27.** An alias maps a capcode or capcode pattern to a name and a template. Patterns use `%` (any run of characters) and `_` (one character). Precedence: an exact capcode wins, then fewer wildcards; patterns starting with a wildcard come last. An alias can be marked **ignored**: its pages are still stored and shown in full (P2), but hidden from the default message list and live updates; a search filter shows them. They never count towards large events (R87; owner, 2026-11-14). Dropping pages stays the network profile's job (R16). (Owner decision, 2026-10-10.)
- **R27a.** Each capcode or pattern has **at most one alias** (owner, 2026-10-11). Capcodes are compared after zero-padding to 7 digits (`240241` and `0240241` are the same); patterns with wildcards are compared as written. The database enforces this with a unique constraint on the normalised value, not just the UI or CLI. Creating an alias for a capcode that already has one is rejected, with a message naming the existing alias and suggesting an edit instead. A wildcard pattern that overlaps an exact capcode (`0100%` and `0100001`) is not a duplicate; precedence (R27) decides. Alias names are unique too (R27b). The import (R30) never silently picks between CSV rows for the same capcode. If rows for the same capcode differ, the import stops, changes nothing and lists them, and the admin fixes the data and imports again. From M8, the fix happens in the PowerShell pipeline or the CSV, and there's no overrides file (owner, 2026-10-20). Rows identical in every imported field (name, agency, colour, ignore) are not a conflict: they are squashed automatically, keeping the first. By default an import doesn't change aliases that already exist: it adds new ones and reports how existing ones differ from the CSV, and applies those differences only with the update option (R58) (owner, 2026-10-11).
- **R27b. Alias names are unique, ignoring letter case** (owner, 2026-11-15: "Let's not have identical [names]. It makes searching ambiguous."). Adding an alias, or renaming one, is refused for a name another alias has, or one that differs from it only in case (`station 1` while `Station 1` exists), whichever way it's done: in the browser (R53), the API, the PowerShell module (R63), an alias request when it's submitted and again when it's approved (R54, R55), and the import (R30). The refusal names the alias that has the name, with its capcode or pattern. An alias may change its own name's case. A brigade with several pagers gives each its own name (`Brigade North`, `Brigade Tanker`), or one range alias covers them. In an import, a row that would give an alias a name that another alias has before the import, or that another row gives, is a **conflict**, listed with the alias or rows that have the name; as for rows that differ for one capcode (R27a), nothing is imported. A row that leaves an alias's name as it is never conflicts, so an export imports unchanged. (Swapping two aliases' names takes two imports.) The database enforces the rule with a unique index on the lower-case name. Names shared before this rule are kept: the upgrade neither fails nor renames them. Until all but one of each are renamed or deleted, the API logs them on every start (by capcode: names are never logged), Administration lists them (on Aliases, with a tag on each, and as a tag on its start page), and no new name can match them. Each can still be edited with its name unchanged; renaming one to a name no other alias has takes it off the list.
- **R28.** A **template** holds a name, agency name, icon (an image, R65), colour and optionally an agency profile. Aliases are **linked** to their template: editing the template updates every alias that uses it.
- **R29.** Templates enable parsing but never gate storage or display (P2).
- **R30.** Aliases can be **imported from a CSV file** in v1 (owner decision, 2026-10-10). The import creates one template per distinct agency name and attaches agency profiles from a mapping of agency name to profile name, which the admin supplies. From M8 the mapping is a hashtable, which can be loaded from a JSON file the deployment owns (R63). Unmapped agencies are text only. An ignore flag in the CSV marks the alias ignored (R27). The CSV's `icon` column (an icon name, as some older systems export) is accepted but ignored, because icons are images added to templates afterwards (R65). Export leaves it empty (owner, 2026-10-20).

### 7.6 Browser UI
- **R31.** The message list shows, for every message: the text **without the priority marker** (as a pager displays it), a priority badge, date and time, alias (or capcode), and call sign. On phone-width screens (375 px), date, time and alias stay visible with no horizontal scrolling.
- **R32.** **Live updates:** a new message appears in every open browser within **2 seconds** of a client posting it, with no refresh. Any mechanism is fine. A message that doesn't match a viewer's current filter isn't added to their list.
- **R33.** **Search** combines any of: text, capcode, alias, agency, call sign, priority, event category, job number, date range, and **"capcodes with no alias"**. The last one also lists each unknown capcode with its message count and last-seen time, so it can be identified and aliased. **Admins** can also filter by flag: `parse_failed`, `address_unsplit`, `location_mismatch`. (List confirmed by the owner, 2026-10-10.)
- **R33a. One search box** (owner, 2026-10-20; built with the UI redesign). The search criteria (R33) are typed into one box. The date range is chosen beside it (Dates, below).
  - **Filters and text:** a word that starts with a known key is a filter. The keys are `alias:`, `agency:`, `capcode:`, `callsign:` (its old spelling `group:` still works and isn't suggested, R8), `priority:`, `category:`, `job:`, `is:` (`unaliased`, `ignored`), `or:` (see Or, below) and, for admins only, `flag:`. Everything else is text search, including quoted text and words with any other colon. That way page text full of colons (`ADDR:`, `14:05`) still searches as text. A value with spaces is quoted (`alias:"Station 1"`).
  - **Text terms** (owner, 2026-11-02): the text is split into terms, and a page must contain **every** term, anywhere in its text or extra fields. Text in double quotes is one term, matched as typed: the same words in the same order (`"Check hoses"`). Each word outside quotes is a term of its own. So `"Check hoses" "Smoke"` finds pages holding both "Check hoses" and "Smoke", and `"Check hoses" smoke truck` pages holding all three. As for all text search, case is ignored and a term can be part of a longer word (section 14). A quote left open runs to the end of the box.
  - **Or:** a term written `or:` (a word, `or:fire`, or a quoted phrase, `or:"structure fire"`) is an alternative to all the other text terms together. A page matches if it holds every ordinary term, or any one `or:` term. So `"Smoke showing" or:fire` finds pages with "Smoke showing" or with "fire"; `"Smoke showing" or:fire or:alarm` any of the three; and `"Check hoses" "Smoke" or:fire` pages with both "Check hoses" and "Smoke", or with "fire". Filters still apply to every page listed: `alias:"Station 1" "Smoke showing" or:fire` lists only Station 1's pages. `or:` is a key (it's suggested and in the help, with no value suggestions), so page text that contains `or:` is searched by quoting it. The API applies the same rule to its text parameter, so the PowerShell module's text search does the same.
  - **Combining:** the same key more than once means any of those values; different keys must all match. The API accepts several values per filter. The PowerShell module's array parameters use the same thing (R63a).
  - **Partial values:** a typed `alias:`, `agency:`, `callsign:` or `category:` value matches every value containing it, ignoring case (`alias:hill` matches "Hillside North" and "Hillside South"). Picking a suggestion matches exactly that value. `capcode:` and `job:` match exactly, with capcodes zero-padded as in R27a.
  - **Suggestions** (owner, 2026-11-09; M21). Clicking into the box opens a list under it of every key, each with a few words; picking a key puts it in the box at the cursor (`alias:`), ready for its value. As a value is typed after a key, matching values are suggested for `alias:`, `agency:`, `callsign:`, `priority:`, `category:`, `is:` and `flag:`. There are none for `capcode:` or `job:`, which are too many to list and are only typed by someone who knows them (owner, 2026-10-20). A word typed **without a key** suggests, first, searching it as text (what Enter does), then the alias, agency, call sign and category values that contain it, with their key: typing `hill` suggests `alias:"Hillside North"`. Picking one replaces the word with the filter, quoted when the value has a space, and matches exactly that value. Plain words never suggest capcodes or job numbers.
  - **Help** (owner, 2026-11-09; M21). A help control lists every key with an example and explains text terms, quotes and `or:`. It's an icon only, with the accessible name "Search help" and a tooltip, placed straight after the search box, between it and the dates.
  - **Clear all** (owner, 2026-11-09; M21). One control resets the box and both dates and shows the plain message list; it's shown only when something is set. It's an icon only, with the accessible name "Clear all" and a tooltip. Clearing is a search change like any other, kept in the page's address, so Back restores it.
  - **Dates** (owner, 2026-11-09; M21). A calendar icon opens one month's calendar. The first day clicked is From, the second To; the days between are joined by a bar, previewed as the pointer moves. A second day before the first swaps them, the same day twice is one day, and a third click starts again. Whole days, as before. The chosen range shows as text beside the icon. Keyboard: arrow keys move the day, Enter picks, Escape closes. The capcode report's dates are the same control. The calendar's month-and-year title is a button (owner, 2026-11-12): it switches to that year's 12 months, with arrows that move a year, and the year there switches to a grid of years. Picking a year shows its months, and picking a month its days. Years with no pages (before the archive's first page or after its last) and months after this one are greyed out and can't be picked. The keys and accessible names work in the months and the years as in the days.
  - **Accessibility:** the box follows the ARIA combobox pattern. Arrow keys move through suggestions, Enter picks one, Escape closes the list, and the number of suggestions is announced.
  - **Where it applies:** the search is kept in the page's address (back button, bookmarks, shared links). The map, the alias and capcode views and the job view follow it. Its look is part of the redesign.
- **R33b. Search speed** (owner, 2026-11-02). With 10 years of pages at 1,250 a day (the default retention, R45; owner, 2026-11-02, sized to the archive being migrated), a search shows its first results within **1 second**. That includes a search that finds little or nothing, a search with several terms or `or:` terms (R33a), and a term found only in an extra field. This holds within the resource budget (section 8).
- **R34.** A **job view** shows all messages for a job number.

- **R35c.** A **message detail view** shows all parsed and extra fields and every client's receive time. The `parse_failed`, `location_mismatch` and `address_unsplit` flags are shown **to admins only**. (`address_unsplit`: a format matched, but no street from the address dataset ended the address text, so `address` is `null`; see ADR 0001.) If the message has a location, the detail view also shows a small map centred on it, using the same self-hosted tiles (R35), with the network's layers of areas and their "Map layers" control (R88c). - **R35f. Full screen on every map** (owner, 2026-11-15: "all maps, keep the strip"). Every map (the map page, a message's detail view, a report's map) has a button in its top-left corner: an expand icon (four corner arrows) with the accessible name "Full screen map" and a tooltip, at least a target's size, reached by keyboard. ### 7.7 Reports
- **R38.** A report shows, for a **capcode** or an **alias** and date range, the number of Emergency **messages** per **event category** (network profile, R5). Unmapped codes and parse failures are counted under "Other" (with the raw code shown where there is one). The alias or capcode is picked with the search box's suggestion control (R33a): typing part of an alias name or a capcode suggests them (owner, 2026-11-12). An alias's report counts every capcode it covers: for a pattern, each capcode that matches it and has no alias of its own (R27). One alias or capcode at a time. Picking an alias picks it by name, so aliases sharing that name from before names were unique (R27b) are reported together. The report's address names what was picked (`?alias=…` or `?capcode=…`), so it can be bookmarked; addresses naming a capcode from before keep working.

- **R38a. More reports** (owner, 2026-11-14; M24). Eight more reports under Reports, beside R38's (R38b-R38i). Network health (receiver coverage, quiet capcodes, unknown capcodes' trends) isn't among them: it belongs in Grafana (R76; owner, 2026-11-14).
  - **Counts only.** A report shows numbers and what they're grouped by (alias names, capcodes, agencies, event types with their labels and categories, localities, appliances, job numbers, times), never a page's text, description or address (P1). P2 and P3 are unaffected: a report shows no page at all, and its event types are the literal codes with their labels beside them (R9).
  - **Busy means jobs, of Emergency pages** (owner, 2026-11-14; 2026-11-15: "Pages with no job number is odd. If they are a job they will have a job number. Only Emergency pages should be counted."). A report counts jobs, not pages: a job number's **Emergency** pages (R23) are one job, however many pages, repeats or capcodes it has. Pages with no job number and pages of any other priority (Non-emergency, Admin, none) are left out of every report, and so are heartbeats (R35b) and pages to ignored aliases (R27), as from large events (R87). Imported pages (R83) count, as the archive's history (owner, 2026-11-15: the defaults stand).
  - **A job's values**, from the Emergency pages it counts. A job counts once, at its **first page's sent time**: on that day, in that week, month, weekday and hour, in the deployment's time zone (R35a). Its **event type** and **locality** are the first that its pages give, in sent order (a page's locality is its `locality` field, else its derived locality, R24); its **agency** is the agency (R28) of its first page to an aliased capcode, or none if it paged only capcodes with no alias (owner, 2026-11-15); its **appliances** are every appliance (R8) any of its pages names, each once; its **pages** are its stored messages (a second receiver's copy isn't another, R19; the same page to two capcodes is two, R20).
  - **Filters**, where a report applies them: agency (one, or every agency), event type (one, or every one), and a date range picked with R33a's calendar (M21): whole days, inclusive, in the deployment's time zone, counting the jobs that started in it. Every page counted is Emergency, so there's no priority filter. By default the last 30 days (the last 12 months for R38e and R38i), and nothing else (owner, 2026-11-15). A report's address holds its filters, so it can be bookmarked and shared.
  - **A table and a chart.** Each report has a table, and beside it (above it on a phone, or when the table is wide) a simple chart of the same numbers. The table is the whole answer: the chart shows nothing the table doesn't, and colour is never the only cue (every value is written on or beside its mark). The table downloads as a CSV file (a header line, then one line per row), and the chart as a PNG image, or is copied as one where the browser allows. Desktop and phone layouts (R80, R81: the page never scrolls sideways; a wide table scrolls in its own box), tokens only (R82c), the axe check passes, and icons come from R77a's set.
  - **Empty.** A range with no jobs says so ("No jobs in this range.") and shows no empty chart.
  - **Can be wrong** (owner, 2026-11-15: "add a note to each of the reports that states that these numbers can be wrong and are only based off of messages that were successfully stored"). Every report page, R38's capcode report included, says so on a desktop and a phone, in one line: "These numbers can be wrong: they count only the pages PagerArchive received and stored. Pages missed by the radio, or lost while it was down, aren't counted." The CSV holds the table only, so it stays a plain table.
  - **Ties.** Equal counts are ordered by name: alias names, then capcodes with no alias, by capcode; localities, event type codes and appliances alphabetically. Where a rank is shown, equal counts share it (1, 2, 2, 4).
  - **The jobs behind a number** (owner, 2026-11-17: "The `When it's busy` heatmap should make the cells clickable and that should take the user to the records that made up that value. Same with the appliance activity, We should be able to click on the appliances and get taken to a list of those jobs."). A number a report links (R38d's cells and R38h's appliances; other reports may link to it later) opens **Jobs** (`/reports/jobs`): the list of exactly the jobs that make up that number, so it lists as many jobs as the number says. It takes the report's filters (dates, agency, event type, and R38d's alias or capcode, whose agency is its own there too) and what the number is of: the day of the week and the hour the jobs started, or an appliance they name. Which jobs are in a number is decided once, by these rules and from the same counts, for the report's number and the list alike, so the two can't differ. Each job, newest first (by its first page's sent time, then job number): its job number, linking to the job view (R34), its first page's time, its pages, its event type (code and label) and its locality; counts only, never a page's text, description or address (P1). 50 jobs to a page of the list, with links to the next and previous. Its heading says what the jobs are, with the range and filters ("Jobs on Saturdays 14:00–14:59, 5 to 11 Oct 2026, Example Fire Service"), and a link goes back to the report it came from with the same filters. Its address holds all of it (`from`, `to`, `agency`, `event_type`, `alias` or `capcode`, `weekday` 1 Monday to 7 Sunday, `hour` 0 to 23, `appliance`, `page`, and `report`, the report to go back to), so it can be bookmarked and shared. It isn't a report of its own: no chart and no CSV; it says, as the reports do, that the numbers can be wrong, and when the counts are still being made. Every signed-in user sees it, as they see the reports. Desktop and phone layouts (R80, R81), tokens only (R82c), light and dark, and the axe check passes.
  - **Up to date and fast** (R33b). A page's change (stored, late, re-parsed, redacted, deleted by retention, its alias marked ignored or moved to another template) is in the reports within seconds, and in the next report asked for. On A75's 4,562,500 pages, every report answers within **1 second** for any range up to the whole 10 years, the first run after a cold start included, within the resource budget (section 8): reports read counts kept beside the pages (ADR 0031), never the pages themselves. While the counts are being made for the first time (the first start after the upgrade that adds them, or after the time zone changes), a report says its numbers are incomplete.
  - Every signed-in user sees the reports, as they see the pages.
- **R38b. Busiest capcodes** (the owner's idea). The top 10, 25 or 50 (10 by default) aliases and capcodes with no alias, by jobs: a job counts once for each alias or capcode it paged, and a capcode covered by a pattern alias counts as that alias (R27). When it's busy.** A grid of jobs by the **hour** they started (rows, 00:00 to 23:00) and the **day of the week** (columns, Monday to Sunday), each cell shaded by its count, in five steps, and showing it; the busiest hour is named above it. Longest first; equal times by the earlier start, then job number. A job whose counted pages were all sent at one time (a single page, say) isn't listed. Agency, event type and dates apply.
- **R38h. Appliance activity.** Each appliance (R8's `units`, shown as Appliances) by how many jobs name it on any of their pages, most first, with its share of the jobs the filters hold. Agency, event type and dates apply. Each appliance links to the jobs naming it (R38a's Jobs; owner, 2026-11-17). A call sign or role a profile moves into `call_signs` (R7, R8) isn't an appliance: once the pages are re-parsed it isn't counted here, in R38f's appliances per job, or in Jobs' `appliance` (ADR 0047).
- **R38i. Large events over time.** Large events (R87) that started in the range, per week (from Monday) or per calendar month (the month by default): how many, their typical duration (the median time from first to last page, R87c) and their typical number of jobs (the median of each one's job numbers, counted as the Large events page counts them), each median by nearest rank (the lower middle one of an even number); and the same over the whole range. Every week or month in the range is listed, an empty one as 0 with no typical values. An event isn't one agency's, so only the dates apply.

### 7.8 Client liveness
- **R39.** A client is flagged **not receiving** after **30 minutes with no message of any kind**, heartbeats included. (Networks may only send heartbeats at certain hours, so missing heartbeats alone must not raise an alarm.) The flag is **shown on screen** and exposed as a metric (R52), so an external monitoring stack can alert on it. The app doesn't send system alerts itself. Client status is visible **to admins only** (client names may reveal where receivers are).

### 7.9 Accounts and access
- **R40.** Sign-in is handled by **Authentik** (self-hosted, in the same compose file) via **OIDC**. The app never handles passwords. Authentik runs on **its own subdomain**, shares the app's PostgreSQL container (its own database), and is configured automatically from **blueprints** shipped in the repo.
- **R40a. Back to the page after signing in** (owner, 2026-11-15). A signed-out visitor sent to sign in returns, once signed in, to the page they asked for, with its query. The return path is honoured only if it is a plain path on the app's own site: it starts with a single `/` (not `//` or `/\`), and neither it nor its path decoded once holds a backslash, a control character, whitespace or a non-ASCII character; it has no scheme or host, and doesn't lead to the sign-in itself (`/auth/`). Anything else returns to the start page (`/`). The server checks it when sign-in starts and again before it redirects. Browsers drop tabs and newlines from a URL and read a backslash as a slash, so a looser check would let a link on the app's own domain send a freshly signed-in person to another site.
- **R40b. Signing out ends Authentik's session too** (owner, 2026-11-17: "when someone signs out, we don't want to secretly keep them signed in. It would make troubleshooting more difficult if we can't rely on that feature"). Signing out, in a browser or in the installed app on Android or iPhone (R90c), ends the person's PagerArchive session **and** their Authentik session in that browser, and ends on PagerArchive's own sign-in page (`/signin?signed_out=1`), saying they've signed out, not on a page of Authentik's. Going back into the app afterwards asks them to sign in again at Authentik, as for a new visitor. Authentik's session belongs to the browser, not only to PagerArchive: Authentik's own pages, and any other app that signs in through the same Authentik, ask that browser to sign in again too. Other browsers and devices, and the PowerShell module's sign-in (R61, which `Disconnect-PagerArchive` ends), keep theirs. If Authentik can't be reached when someone signs out, PagerArchive's session still ends, and the sign-in page says so: they're signed out of PagerArchive, but Authentik's sign-out couldn't be reached, so the next sign-in may not ask again. Sign-out waits for Authentik for a few seconds at most.
- **R41.** New users can only enrol with an **invitation** from an existing user **and** by verifying a code sent to an email address in one of the **allowed domains** (deployment setting `ALLOWED_EMAIL_DOMAINS`).
- **R42.** The app records **who invited whom**. Admins can deactivate any user, or a user **and everyone in their invite tree** (recursively).
- **R42a. Invite tree view** (owner, 2026-10-17). Each user's page in Administration shows their **invite tree** as an indented list: who invited them, and everyone they invited, recursively. Each person shows name, email, role, the date they joined, and whether they're deactivated. Deactivated people are greyed out, and the tree continues through them.
- **R42b. Preview before deactivating a tree** (owner, 2026-10-17). Deactivating a user and their tree first shows the tree with a tick beside everyone who will be deactivated, and totals ("12 people will be deactivated and 3 unused invitations cancelled"). The admin can **untick** anyone (which spares only that person) or use **"spare this branch"** (which unticks that person and everyone below them). Already-deactivated people and the last active admin (R44) can't be ticked. An optional **reason** can be entered. Confirming deactivates exactly the ticked people and cancels their unused invitations; spared people's invitations stay. If the tree changed since the preview (anyone joined, or anyone's status or trusted mark changed), confirming is **refused** and the updated preview is shown.
- **R42c. Trusted users** (owner, 2026-10-17). An admin can mark a user **trusted**, and remove the mark; who set it and when is recorded. Trusted users start **unticked** in every preview, though an admin can still tick one deliberately. The mark doesn't prevent deactivating that person on their own. Only admins see it.
- **R42d. Deactivation record** (owner, 2026-10-17). Each tree deactivation is recorded: who did it, when, the reason, who was deactivated and who was spared. Admins see the record on the affected users' pages. Spared people keep their recorded inviter.
- **R43.** A deactivated user can't be re-invited except by an admin. A non-admin who tries is told why: the person was deactivated and only an admin can re-invite them (owner, 2026-10-13).
- **R43a.** Invitations are created **in the app** (which records who invited whom, and creates them through Authentik's API) and are **single-use**, expiring after **7 days**. The inviter enters the invitee's email address, which must be in an allowed domain (admins included). The emailed link only works for that address. An invitation is **used up only when enrolment finishes** (the emailed code verified and the account made), never by opening the link (owner, 2026-11-08): mail providers' link scanners open links and run their pages before the invitee does, and that must neither use up nor spoil the invitation. A link opened but not finished still works until it expires, is cancelled or is used.
- **R43d. Resending an invitation** (owner, 2026-11-08). The inviter, or any admin, can **resend** an invitation that is waiting or expired, from the inviter's list of invitations (R43a) or, for admins, the user's page in Administration. Resending sends a new link to the same address and starts a new 7 days; the old link stops working. It is still the same invitation: the recorded inviter doesn't change, and it isn't a second pending invitation to that address. A resend follows the same rules as a new invitation (allowed domain, R43's re-invite block, and R43b and R43c's cancelling). A used or cancelled invitation can't be resent; the inviter invites again instead.
- **R43e. Limits on invitation emails** (owner, 2026-11-16: security review). Every invitation email counts, a new invitation's or a resend's, and none is sent past either limit: **one address** gets at most **3 an hour and 5 a day**, whoever sends them; **one sender**, admins included, sends at most **20 an hour and 50 a day** (`INVITATION_SENDER_LIMITS`, e.g. `20,50`, changes these two; the test stack raises them). A request past a limit is refused with `429`, a `Retry-After` header and a message saying which limit and when to try again, which the invite and resend screens show; nothing about the invitation changes. An email that couldn't be sent doesn't count. The counts are kept by the API in memory, as Send test's limit is (R51c), so a restart of the API starts them again.
- **R43b.** Deactivation takes effect **immediately**: the user is disabled in Authentik and their live sessions and connections are closed. Admins can reactivate users one at a time (reactivating doesn't reactivate their invite tree). The re-invite block (R43) goes by email address. A deactivated user's unused invitations are cancelled (owner, 2026-10-13).
- **R43c.** Users can delete their own account. People they invited keep their accounts, credited to "deleted user". Their unused invitations are cancelled (owner, 2026-10-13).
- **R44. Roles and the first admin** (owner, 2026-10-12). Two roles: `user` and `admin`. Users browse, search and invite (R41). Admins can also manage aliases, templates, users, clients and retention, and see flags (R35c) and receiver status (R39). The deployment setting `INITIAL_ADMIN_EMAIL` names the first admin: **while no admin exists**, that address may enrol without an invitation, still verifying the emailed code, and is exempt from `ALLOWED_EMAIL_DOMAINS`; it becomes admin. While that set-up is available, a signed-out visitor is sent to the app's sign-in page, which offers it, rather than straight to the identity provider (owner, 2026-10-13). Once any admin exists, the setting is ignored. That is the only exception to the allowed-domain rule: every invitation made in the app is to an allowed domain. Admins can promote users to admin and demote admins. The **last active admin** can't be demoted, deactivated or deleted, including through deactivating an invite tree that contains them.
- **R44a. Guessing protection** (owner, 2026-10-13). Sign-in passwords, enrolment codes and password-reset codes are protected against guessing: after 5 wrong attempts for one account, further attempts for it are refused for 15 minutes, even if the flow is restarted or a new code is requested. An invitation's enrolment sends at most **5 code emails an hour** (owner, 2026-11-08); a run past that is told to wait, with the time, and sends nothing. They are counted per invitation, across runs, restarts and addresses, and a resend doesn't reset the count.
- **R44c. The first admin's address and Authentik's administrator's differ** (owner, 2026-11-05). `INITIAL_ADMIN_EMAIL` and `AUTHENTIK_ADMIN_EMAIL` must be different addresses, because Authentik's sign-in and password-reset forms find one account per address, the older one, so a first admin sharing `akadmin`'s address could never sign in with a password or reset it. The API asks Authentik on every start whether another account holds `INITIAL_ADMIN_EMAIL` (ignoring case, as the forms match) and, if so, logs a warning saying what to do, without the address (R73). A failure to ask doesn't stop the API. While another account holds the address, first-admin set-up is refused with the reason, so enrolment doesn't make the duplicate.
- **R44b. Administration** (owner, 2026-10-16). Admin-only screens are grouped in one **Administration** area, reached by a single **Admin** link in the header that only admins see (from M13, the **Administration** group in the side menu, R77, which also carries R55's count). Its start page links to every admin screen. A signed-in user who isn't an admin sees no Admin link, and the admin pages refuse them. Each user's page in Administration lists their integrations (name, type, status, last delivery, Pause or Resume), never destinations or secrets. There is no list of every user's integrations. The users list shows each user's number of integrations and marks any that are paused for failing.

### 7.10 Retention
- **R45.** Messages are kept for a configurable period, set **in days** in the admin UI (default **3,650 days**, minimum 30), then deleted completely (text, metadata and everything linked to them) by a nightly job. **Backups are out of scope.** The docs must say that deleted messages may survive in a deployment's own backups. The cut-off is a **calendar date** in the deployment time zone. The nightly job runs at **03:00** (configurable).
- **R45a. Retroactive redaction: one unit, resumable, pauseable, stoppable and restartable** (owner, 2026-11-18; ADR 0044). The nightly job applies changed redaction rules to the stored pages (P1): a pass over every page, and a re-parse of each page whose text the rules change. On a production-sized archive that's a long job, and it meets R91. It's a **run** kept in the database: why it started (a code: `rules_changed`, or `started_again` by an admin), the rules it applies, its total (the stored pages, counted when it starts) and done (pages checked), how many pages' text it changed, the last page it checked (pages are walked by ID), and its state: **running**, **paused** or **stopped**, or **idle** when none is unfinished.
  - **One unit.** Each batch of pages (1,000) is done in one transaction with the run's place: each changed page's new text and dedup hash, and its re-parse (parsed fields, job, location, areas and derived locality: R23a), are written together or not at all. So no page ever has redacted text beside fields that still hold what the rules remove, across a crash, a restart, an upgrade, a pause or a stop; and what the run says it has done, it has. A page's parsed fields are written only beside the text they were parsed from, whatever writes them (a re-parse run included, R23c). What redaction and the re-parse do to a page doesn't change.
  - **Then**, the imported source IDs the rules now match are dropped (the copy stays, ADR 0018), in batches the same way; the large events around the re-parsed pages are rebuilt (R87f), from the days kept with each batch; and the rules are saved as applied in the same transaction as the run's finish. A run is running until then.
  - **The nightly run** starts a run when the rules in use aren't yet applied to every page (they changed, or a run didn't finish), and does it until it finishes or an admin pauses or stops it; then it goes on to the report counts and the vacuum as before. A stopped run is started again from the beginning by the next nightly run (the pages after where it stopped still hold what the rules remove: P1), and one under other rules too. A paused run stays paused: the nightly run leaves it, and logs that.
  - **Resumable.** After a crash, a restart or an upgrade, a run carries on from the last batch it finished as soon as the API starts, without waiting for a night; a vacuum follows when it finishes. No page is done twice beyond the batch in hand, and none is skipped. Rules changed at start-up start an unfinished run again from the beginning with the new rules, in the state it was in.
  - **Pauseable.** An admin pauses a running run: it stops after the page in hand and finishes that batch. It stays paused across restarts, upgrades and nightly runs until Resume carries it on from where it got to.
  - **Stoppable.** An admin stops a running or paused run: the pages it has done stay done, the large events around them are rebuilt, and it shows as stopped, across restarts, until the next nightly run or an admin's Start again starts it from the beginning. A stopped run can't be resumed.
  - **Restartable.** An admin starts it again from the beginning with the rules in use, whatever its state, and before any run too: every stored page is checked again.
  - **Where.** **Administration → Retroactive redaction**, on phones and desktop: the state, done of total and percent, the pages changed, the rate and time left while it runs, when it started (or finished, or last changed state), why, and whether the rules in use are applied to every page yet, with **Pause**, **Resume**, **Stop** (asks first) and **Start again** (asks first) as the state allows; Administration's start page tags it while it isn't idle. The PowerShell module (R59): `Get-PagerArchiveRedaction`, `Suspend-PagerArchiveRedaction`, `Resume-PagerArchiveRedaction`, `Stop-PagerArchiveRedaction` and `Start-PagerArchiveRedaction`. Both use the API, admins only: `GET /api/v1/admin/redaction` and `POST /api/v1/admin/redaction/pause`, `/resume`, `/stop` and `/start`; a change the state doesn't allow is refused (409) with a code (`redaction_not_running`, `redaction_not_paused`, `redaction_stopped`). Each admin's change is logged with their user ID, as other admin actions are.
  - **Observable.** R52's endpoint has whether a run is running, its state as a number (0 idle, 1 running, 2 paused, 3 stopped), its total and done (the last run's while none runs, and a paused or stopped run's while it's held), when it started, and a counter of pages checked since the API started, with no labels. The log has "retroactive redaction started" (its reason and total), "retroactive redaction progress" every 30 seconds (done, total, percent, pages a minute and seconds left), "retroactive redaction finished" (pages checked, pages changed, seconds and rate), "retroactive redaction carried on", the start again for changed rules, and each admin's change ("retroactive redaction paused", "… resumed", "… stopped", "… started again"). The example monitoring stack's Retroactive redaction row (R76) shows it as the Re-parse row shows the re-parse. Counts and codes only (P1-P3): never a page's text, a rule's terms, a capcode, an address or a locality.
- **R46.** Shortening the period requires confirming the cut-off date ("All messages older than 9 October 2024 will be deleted at the next nightly run. Confirm?"). No row count is shown. Deletion happens at the next nightly run.

### 7.11 Integrations (per user) and metrics
- **R47.** Each user can create their own **integrations**. An integration is a **selection**, a **filter** and a **destination**. Integrations belong to their owner: other users can't see them, and admins can see that they exist (and pause them) but never their secrets. A user can have several integrations for the same capcodes, for example one webhook for emergency pages and another for the rest; each page goes to every integration it matches (owner, 2026-10-16). The integrations screen and the integration docs say, in one line, that integrations are a convenience and not a replacement for a pager (see Out of scope: Operational alerting).
- **R48.** **Selection (required):** one or more capcodes and/or aliases. An integration with no selection can't be saved, so nobody forwards the whole network by accident. The selection is **one field** (owner, 2026-10-16): the user types an alias name or a capcode, and the suggestions show both. A capcode that has its own alias is selected as that alias. A capcode covered only by a range (pattern) alias stays a capcode, with the range alias's name shown beside it, so typing one capcode never selects a range.
- **R49.** **Filter (user-defined):** which **event types** to send, chosen by event category (R5) or by raw event-type code, optionally narrowed by priority and by any other search criterion (R33). Only **new** pages are sent (no backfill), after redaction (P1), and never including admin-only fields unless the owner is an admin.
- **R49a. At or above a level** (owner, 2026-11-18: "the integrations should be able to fire on [an agency's] alarm level", at or above a level; ADR 0045). The filter may also be "<field> at or above <level>" for one agency profile's level field (R7), such as "Alarm level at or above Second alarm". A page matches when its template's agency profile is that one and its field's value is that level or one after it in the profile's order, as the profile is now; pages of any other agency profile, with no value, or with a value the profile doesn't list don't. The level names its agency, so it needs no Agency criterion; one given still narrows, as every criterion does. A job's later page at a higher level matches by that page; nothing more than R51b's once per page (and R19's one page per repeat) stops it. The integration form offers each loaded agency profile's level fields ("Example Fire Service: Alarm level"), then that field's levels by label, lowest first: the **only** place levels are shown. Pages, the job view, events, the integration's card and the notifications and payloads show no level and no level's label (R87b); a Full payload carries the level's raw value as an extra field, as before (R8, R50). A level that isn't the profile's is refused when saving; one that stops being, when the profile changes, matches nothing until the integration is changed.
- **R50.** **Destinations in v1:** a **webhook** (HTTP POST of a documented JSON payload: text without the marker, priority, parsed and extra fields, alias, capcode, sent time, job number; optional custom auth header) and **MQTT publish** (broker URL, topic, optional username/password, TLS). Together these cover Home Assistant, Node-RED, n8n and most message queues. There are also **presets** for **Discord, Telegram, Pushover and ntfy**, each sending the message in that service's own format (owner, 2026-10-16). Detailed routing, such as quiet hours, is the receiver's job.
- **R50a. Content** (owner, 2026-10-16). Each integration chooses what it sends: **Full** (text and all fields, as in R50) or **Summary** (alias, capcode, event type and category, priority, sent time and job number; no page text, address, location or extra fields). Presets default to Summary, because those services are third parties; webhook and MQTT default to Full.
- **R50b. Home Assistant** (owner, 2026-10-16). An MQTT integration can turn on **Home Assistant discovery**: Home Assistant then shows a PagerArchive device with one **event entity** per integration, and each matching page fires it. The docs include an example Home Assistant automation for both the webhook and MQTT.
- **R51.** **Safety:** by default an integration may not reach private, loopback or link-local addresses (protection against server-side request forgery). An admin can allow specific hosts or ranges (e.g. the owner's Home Assistant). Secrets are encrypted when stored and never shown again after saving. Failed deliveries retry with backoff. An integration that keeps failing is **paused**, and its owner sees its status and last error (without page text). Deactivating a user stops their integrations.
- **R51a. On time or not at all** (owner, 2026-10-16). Delivery is attempted within **5 seconds** of the first client receiving the page. Failed deliveries retry until **5 minutes** after that; then the page is skipped for that integration and recorded as "skipped: too old". A page that arrives at the server already older than 5 minutes (e.g. stored by a client while offline) is not sent. A late automation, such as a gate opening long after the page, is worse than none.
- **R51b. No double firing.** Each delivery carries the page's ID. Once a page has been delivered to an integration, it is never sent to that integration again, even if several clients received it.
- **R51c. Send test.** An integration's owner can send a test delivery, marked `"test": true`, and sees whether it was delivered, the answer's status (such as `HTTP 200 OK`) or the app's own fixed reason it failed (such as `connection refused`), and how long it took: never any of the answer's body (owner, 2026-11-16: security review), since an allowed private address can be an internal service whose replies its owner never meant users to read.
- **R52.** **Metrics for external monitoring:** a Prometheus-format endpoint (access-controlled, no page text) exposing at least: each client's last-seen time and "not receiving" / "clock ahead" state, pages received and stored, `parse_failed` and `address_unsplit` counts, integration delivery successes, failures and "too old" skips, the number of accounts currently locked by guessing protection (R44a), and nightly-job results. System alerting (e.g. via Grafana) is the deployment's job, not the app's.
  - **A scrape stays cheap, whatever the archive's size** (owner, 2026-11-18: "The metrics endpoint has gotten slower over the last 2 days."). A scrape never runs a query whose cost grows with the archive: nothing it does reads `messages` or another table of pages. The flagged messages' counts (`pagerarchive_messages_flagged`) are counted in the background, at once when the API starts and then every 60 seconds, and a scrape shows the last counts, so they're at most 60 seconds old while counting works. `pagerarchive_messages_flagged_counted_timestamp_seconds` says when they were counted, so a stuck or failing count shows. Until the first count has worked, both are left out of the scrape. A count that fails, or takes longer than 60 seconds, is given up and logged as a WARN (its error, and when the kept counts were counted: counts only, P1-P3), and the last counts are kept. They're counted only while the metrics are on (`METRICS_TOKEN`). Their names, labels and meaning are unchanged.
  - **`messages` is vacuumed as it changes**, not only at night (R45): autovacuum vacuums it after at most 50,000 dead rows, rather than after a fifth of the table, and analyses it after 2 % of its rows change, rather than 10 %, so a mass rewrite such as a re-parse of the whole archive is vacuumed as it goes. These are the table's storage settings, set by a migration that rewrites nothing (R91a).

### 7.12 Aliases in the browser (owner, 2026-10-16)
- **R53. Admins manage aliases** in Administration: add, edit (name, capcode or pattern, template, ignored) and delete. The same rules apply as for import (R27, R27a, R27b). Admins' changes take effect at once, with no review. When an alias for one capcode is deleted, integrations that selected it select that capcode instead; a deleted range alias is removed from selections. The delete confirmation says how many integrations select the alias (owner, 2026-10-16).
- **R54. Change requests.** Any signed-in user can request a new alias, a change to an existing alias's name, template or ignored flag, or the deletion of an alias. A request can't change an alias's capcode or pattern (that's a deletion plus a new alias). Users choose from existing templates; only admins manage templates. A request is checked when it's submitted (e.g. R27a, R27b) and can carry a note for the admins.
- **R55. Review.** Admins see waiting requests in Administration (R44b), with a count on the Admin link. Each shows the current value beside the proposed one. **Approving** applies the request exactly as submitted, after checking R27a and R27b again; if it would now break either rule (another alias has taken the capcode or the name meanwhile), approval is refused with the reason. **Rejecting** requires one feedback text. Admins can't edit a request. A request whose alias has changed since it was submitted is marked **"changed since requested"**. Deleting an alias closes its waiting requests as "alias deleted".
- **R56. My requests.** Users see their requests' status (waiting, approved, rejected, withdrawn, alias deleted) and any feedback. They can edit or withdraw a request while it's waiting. A rejected request is final; they can submit a new one. Deactivating or deleting a user withdraws their waiting requests (as with invitations, R43b and R43c).
- **R57. History.** The alias view (R35e) lists the alias's changes **to admins only** (owner, 2026-10-16): what changed, who requested it, who approved or made it (as "name (email)"), and when. A deleted user shows as "deleted user" (R43c). Users see no history, and the API doesn't send it to them; they see their own requests in My requests (R56). When an alias is deleted, its history is kept, attached to its capcode or pattern, with no time limit.
- **R58. Import and export.** From M6, the database is the source of truth for aliases. Import (R30) only **adds** aliases for capcodes or patterns that have none; for existing ones, it lists the differences and changes nothing. The exception is the import's **update option** (R27a, A21), an admin's escape hatch that applies the differences and records them in the history. From M8 it's in the PowerShell module (R63); before that it was `alias import --update`. There's no import in the browser (owner, 2026-10-16). Admins can **export** all aliases as a CSV in the import format from the browser. From M8, `Get-PagerArchiveAlias | Export-Csv` writes the same format (R63).

### 7.13 PowerShell module (owner, 2026-10-20)
- **R59. Two command-line tools.** The `pagerarchive` program, run on the server, keeps only the jobs that need the server: running PagerArchive (`serve`), checking profiles (`validate-profile`), managing receiving clients (`client`), managing service accounts (`service-account`, R62a) and `version`. Receiving clients stay there on purpose: a client key can post pages, and pages can fire integrations, so creating one needs a shell on the server, not a sign-in. Service accounts stay there for the same reason: their credential reads the whole archive. Everything else an admin does from a command line goes through a **PowerShell module**. It uses PagerArchive's API, the same one the browser uses, so the same rules apply. The `template` and `alias` commands are removed from `pagerarchive`, so each job has one tool.
- **R60. Signing in.** `Connect-PagerArchive` with the app's URL opens the browser at the normal sign-in (Authentik, email and password). It uses OAuth's sign-in for native apps, with PKCE and a loopback redirect (RFC 8252). On a machine with no browser, a device-code option shows a code to enter on any device (RFC 8628). The module is its own public client in Authentik, with no client secret. The API accepts the module's access tokens alongside browser sessions, after checking their issuer, audience, signature and expiry. As for the browser, it checks the person's status and role on every request, so deactivating, deleting or demoting someone takes effect on their next command. There are **no API keys** (owner, 2026-10-20): a service account (R62a) gets short-lived tokens from Authentik, as the module does, with an app password Authentik holds.
- **R61. Staying signed in.** The module renews access tokens automatically. The sign-in is saved so it carries across PowerShell windows and restarts (owner, 2026-10-20), with nothing to install or set up on Windows (owner, 2026-10-21):
  - **On Windows**, it's saved in a file in the user's profile, encrypted with Windows' data protection (DPAPI), so only that Windows account on that machine can read it.
  - **On Linux and macOS**, it's saved in the user's default Microsoft SecretManagement vault. With no vault registered, the sign-in lasts for that PowerShell session only, and the module warns how to set one up.
  - **Anywhere**, `-Vault` names a SecretManagement vault to use instead.

  Neither the module nor the API ever writes tokens unencrypted, shows them or logs them. Disconnecting revokes the sign-in in Authentik and removes the saved copy. A sign-in that isn't used for 30 days ends. The connection `Connect-PagerArchive` outputs shows `ExpiresAt`: for a person, when the current access token expires (it renews as it goes, so it isn't when the sign-in ends); for a service account, when its credential expires (R62a).
- **R62. Admins only** for now (owner, 2026-10-20). The API refuses the module's tokens for a user who isn't an admin, with a message saying PowerShell access is for admins. A read-only service account (R62a) is the one exception.
- **R62a. Service accounts** (owner, 2026-11-19; ADR 0048). A **service account** is a read-only account for a tool, not a person: an agent querying PagerArchive over HTTPS, or running the PowerShell module regularly. It won't fit many jobs, and it skips the people's sign-in flows; both are accepted (owner, 2026-11-19).
  - **Not a person.** It has a name (3 to 40 lower-case letters, digits and hyphens, e.g. `report-bot`) and an owning admin, but no email, no password, no browser sign-in and no enrolment, so `ALLOWED_EMAIL_DOMAINS` (R41) doesn't apply to it, and people's enrolment is unchanged. It sits in its owner's invite tree (R42): deactivating the tree takes it too, and the preview (R42b) shows it, marked as a service account. Its owner deleting their account (R43c) revokes it.
  - **Made on the server only.** It's created, listed, revoked and re-keyed only from the server's shell, as receiving clients are (R59), because a credential that reads the archive needs a shell on the server: `pagerarchive service-account create <name> --owner <admin's ID or email>`, `list`, `revoke <name>` and `rotate <name>`. Admins see service accounts in Administration, marked, and can deactivate them there (on their own or with a tree), but not reactivate, promote or mark them trusted: those are refused with `service_account_shell_only`.
  - **Read-only.** It reads pages and everything else an admin may read through the API, and changes nothing: every request that isn't a read (no invitations, aliases, templates, flags, retention, users, integrations, albums or its own account) is refused with 403 and `service_account_read_only`, saying why. It can't read people's personal details either: the user list and users' pages (emails, invite trees, deactivation records), invitations and alias requests are refused with 403 and `service_account_personal_details`, and in what it may read, the people are hidden: its owner on `/api/v1/me`, who made or asked for each change in an alias's history, and who asked for an alias's waiting changes, with their notes and feedback (owner, 2026-11-19: "agreed, no personal details"). The rule fails closed: every signed-in read is classified, as allowed or personal, and one that isn't is refused; a check fails while any read is unclassified, so a new one can't land without a decision.
  - **Its credential.** Its credential is an Authentik app password, shown once by `create` and `rotate`, and never shown again or logged by PagerArchive or the module. The tool trades it for 5-minute access tokens with OAuth's client-credentials grant, against Authentik's `pagerarchive-service` client, a public client with no secret; the API checks those tokens as it checks the module's (R60): issuer, audience, signature and expiry, then the account's status, kind and credential's expiry on every request. The credential **expires after 90 days**; rotating gives a new one and ends the old one at once; revoking ends it at once. A live stream (R63b) on a token from before then ends when that token expires, within 5 minutes.
  - **Logged and traced.** Each of its requests is logged with its route pattern, its user ID and its name, and its spans carry its user ID, the role `service_account` and its name (nothing more, R70). It's under the same limits as a user.
  - **In the module.** `Connect-PagerArchive -Uri <URL> -ServiceAccount <credential>` (its name as the user name, the credential as the password) connects as it, without a browser. The credential is saved as a sign-in is (R61), so new windows use it, and a new access token is got whenever one is needed. The connection's `ExpiresAt` is when the credential expires, from `/api/v1/me` (`credential_expires_at`, a service account's only), not the 5-minute access token's, which renews itself and isn't shown (owner, 2026-11-20: "show the credential expiry instead"). Read commands work; a write command gets the API's refusal, with its reason. It's the one exception to R62: a service account, read-only.
- **R63. Commands** (M8, owner 2026-10-20).
  - **Names:** the module is named **PagerArchive**. Its nouns start with `PagerArchive` (`Get-PagerArchiveAlias`), and each command also has an alias that uses `Pa` instead (`Get-PaAlias`).
  - **What it covers:** what the removed `template` and `alias` commands did, i.e. listing, adding, changing and deleting templates and aliases, and importing aliases. Templates can also be renamed (`Rename-PagerArchiveTemplate`, matching `Rename-PagerArchiveAlias`; owner, 2026-10-23).
  - **Import input:** import takes alias objects from the pipeline (`Import-Csv aliases.csv | Import-PagerArchiveAlias`), not a file path, and accepts the import CSV's column names. It collects every row and applies them as one batch, so a conflict changes nothing (R27a).
  - **Import options:** the agency-to-profile mapping is a hashtable parameter (R30). `-WhatIf` is the dry run: it asks once for the whole batch and still outputs every row's result, marked as not applied, so the results can be filtered before the real import. `-Update` is the update option (R58) (owner, 2026-10-21).
  - **Import output:** a result object for each row (added, unchanged, different, squashed). A conflict (R27a, R27b) is an error for each row involved, saying why: the other rows for that capcode, or the alias or rows that have that name.
  - **Exporting:** `Get-PagerArchiveAlias` outputs objects whose properties match the import's parameters, so `Get-PagerArchiveAlias | Export-Csv` writes the import format. **`Export-PagerArchiveCsv`** (owner, 2026-11-16: security review, C2) works as `Export-Csv` (`-Path`, `-LiteralPath`, `-Append`), but writes any value that starts with `=`, `+`, `-`, `@`, a tab or a carriage return, as `Export-Csv` would write it, with a leading `'`: the rule of the browser's exports (R58), which the import reverses. Page text comes from the radio, so the docs and help export messages with it, never with a bare `Export-Csv`. The objects aren't changed.
  - **Choosing records:** a template or alias piped from `Get-PagerArchiveTemplate` or `Get-PagerArchiveAlias` (or any object with an Id) is chosen by its Id, so `Remove-`, `Set-` and `Rename-` act on exactly that record, even when another template's name differs only in case or other aliases share its name from before names were unique (R27b). Names typed or piped as text are matched as before (case-insensitively, with wildcards). Confirmations and `-WhatIf` name each record with its Id (owner, 2026-11-12).
  - **Renaming** (owner, 2026-11-19): `Set-` changes settings and never renames; `Rename-PagerArchiveAlias` and `Rename-PagerArchiveTemplate` rename (one command for each job, so `Set-` has no `-NewName`). `-NewName` takes pipeline input by property name, so a script block renames many at once: `Get-PagerArchiveAlias -Name 'Old *' | Rename-PagerArchiveAlias -NewName { $_.Name -replace '^Old\s+' }`. Confirmations and `-WhatIf` name each record with its own new name. `Set-PagerArchiveAlias` or `Set-PagerArchiveTemplate` given nothing to change is an error (`nothing_to_change`) saying nothing was changed and that renaming is the `Rename-` command; nothing is sent.
  - **Tab completion** (owner, 2026-11-19): only the small lists complete, from the connected server: template names (`-Template`, and `-Name` on the template commands), agencies (`-Agency`), agency profiles (`-AgencyProfile`) and event categories (`-Category`); `-Priority` is a fixed list. Alias names, call signs, capcodes and job numbers don't: there are too many. Each list is cached for the PowerShell session for 5 minutes, then fetched again; when what was typed matches nothing in the cache, the server is asked once more before nothing is offered, so a template made a moment ago shows up. Not connected, or the server can't be reached: nothing is offered, silently, and never an error while the user types. Values with spaces are quoted. Where a parameter takes wildcards, completion offers real values only, and a typed pattern still works. The lists come from the API's existing endpoints (templates, agency profiles, and meta's categories); agencies are the templates' agencies.
  - **Rules and history:** the same rules apply as in the browser (R27, R27a, R27b, R30, R53, R58). Changes are recorded in the alias history (R57) as made by the signed-in admin.
  - **Guidelines and publishing:** the module follows [`docs/powershell-guidelines.md`](docs/powershell-guidelines.md). It has **its own version**, in its manifest, separate from PagerArchive's. A branch that changes the module (`powershell/PagerArchive/`) raises that version above the previous release's, and CI fails a branch that changes the module without it; branches that change it before the same release share one raise (owner, 2026-11-12). CI publishes the module to the PowerShell Gallery from a release (section 12.1) whose checks all passed, **only when that release changed the module**, and only if its version isn't on the Gallery yet. A release that didn't change the module says it kept the version already there. A failed publish is caught up by re-running it (owner, 2026-11-01).
- **R63a. Messages** (owner, 2026-10-20). `Get-PagerArchiveMessage` returns messages as objects, newest first.
  - **Filters:** the same as search (R33): text, capcode, alias, agency, call sign (`-CallSign`, with `-Group` its old name), priority, event category, job number, a time range, capcodes with no alias, and admin flags. They can be combined.
  - **Ignored aliases:** their pages are included only when asked, as in the browser (R27).
  - **Pipeline input:** aliases and capcodes can be piped in, e.g. `Get-PagerArchiveAlias -Name 'Station*' | Get-PagerArchiveMessage -After (Get-Date).AddDays(-7)`.
  - **What each message holds:** what the detail view shows (R35c): the full text (P2), priority, sent time, capcode, alias, agency, call sign (`CallSign`), call signs (`CallSigns`, R8), job number, event category, parsed fields, location, flags, and each client's receive time.
  - **Paging:** the command fetches messages from the API page by page, only as the pipeline asks for more, so `-First 10` or `Select-Object -First 10` stops after the first page. With no filter, it returns every message.
- **R63b. Watching** (M9, owner 2026-10-20). `Watch-PagerArchiveMessage` (alias `Watch-PaMessage`) outputs new messages as they arrive, in arrival order, until it's stopped (Ctrl+C).
  - **Filters:** the same as `Get-PagerArchiveMessage` (R63a), except the time range and paging. Only matching messages come out.
  - **Speed:** a message comes out within 2 seconds of a client posting it, as in the browser (R32).
  - **Lost connection:** it keeps retrying, with a warning. When it's back, a second warning says how long it was down and how many messages follow (owner, 2026-10-22). Like every other command, it uses the system's proxy settings. Once reconnected, it first outputs the matching messages that arrived while it was disconnected, so a short outage doesn't skip pages.
  - **Account changes:** if the signed-in user is deactivated or loses admin, it stops with an error.
  - **Best-effort:** like integrations, it's a convenience, not an alerting system (see Out of scope, "Operational alerting").

### 7.14 Templates in the browser (owner, 2026-10-20)
- **R64. Admins manage templates** in Administration (R44b). They see a list showing each template's name, agency, icon, colour, agency profile and how many aliases use it, and can add, edit (name, agency, icon, colour, agency profile) and delete templates. Changes take effect at once for every alias using the template (R28), with no change requests and no history. The agency profile is chosen from the profiles loaded at start-up, or none; changing it re-parses the affected messages (R23a). A template still used by aliases can't be deleted, and the refusal says how many use it. **Names are unique ignoring letter case** (owner, 2026-11-14): adding or renaming a template, in the browser, the PowerShell module, the API or the alias import, is refused for a name that differs from another template's only in case (`emv` while `EMV` exists), and the refusal names that template. A template may change its own name's case. Names like that from before this rule are kept: the upgrade neither fails nor renames them; the API logs them on every start, Administration lists them (on Templates, and as a tag on its start page), and no new name can match them, until all but one of each is renamed or deleted. Alias names are unique ignoring case too (R27b). Users choose from existing templates (R54) and can't change them; the API refuses them.
- **R65. Template icons.** A template's icon is an **image stored in PagerArchive's database** with the template, never a link to another site, so browsers only ever fetch it from PagerArchive. Admins upload it in the browser, or with the PowerShell module (R63) from a file or a URL. The module downloads a URL on the admin's own machine and uploads the image, so PagerArchive's server never fetches anything from another site. Accepted: PNG, ICO, GIF, JPEG and WebP files of at most 100 KB. SVG and anything else are refused with the reason. Every icon is converted to a 64×64 PNG when it's added, and nothing else from the uploaded file is kept. An animated GIF gives its first frame; an animated WebP is refused with the reason (owner, 2026-10-23). If the module adds a template and its icon is then refused, the template stays without an icon and the error says so (owner, 2026-10-23). Admins can replace or remove an icon. The API applies these checks and the conversion, whether the icon comes from the browser or the module.
- **R66. Showing icons.** Wherever a page's sender is shown, its template's icon appears beside the alias name: message rows (the list, live updates, search results, the job view), the alias view (R35e), the message detail view and the map's list of messages (owner, 2026-10-23). The icon sits on a light tile, so dark artwork stays visible in both themes, and its text alternative is the agency name. With no icon, the row looks as it did before (the colour stays). Each browser fetches an icon once and reuses it until it changes. The icon's exact size and position are part of the UI redesign.

### 7.15 Printing for training (owner, 2026-10-20)
- **R67. Print sheet.** Any signed-in user has a **print page**, with its own search (the same criteria as R33, under the same rules) and the user's **print sheet**. They tick messages in the print page's search results to add them to the sheet, and can untick them there or remove them on the sheet. Ticking happens only on the print page: the message list, search results, the job view and the alias view have no tick boxes (owner, 2026-10-30, after trying them in the list). The sheet keeps messages in the order they were added and shows how many it holds. It's kept in that browser until the user clears it, and it stores message IDs only, never message text.
- **R68. Printing.** The print sheet prints as a plain layout for teaching recruits to read pages. Each message shows its text exactly as a pager displays it (R31), in full, and nothing else (no time, alias or priority badge). Each message sits inside a heavy border, with space between messages, so it's clear where one page ends and the next begins. A message is never split across two paper pages. The printout has no header or navigation, is black on white, and can be saved as a PDF through the browser's print dialog. The user documentation notes that printed pages are outside PagerArchive's control: retention and deactivation don't reach paper.

### 7.16 Telemetry (owner, 2026-10-30)
For troubleshooting incidents: following a page from the receiver to the database, finding where time goes, tying high load to what users were doing, and being told when a client stops sending.
- **R69. OpenTelemetry, off by default.** The API server and the client can each export traces, metrics and logs over OTLP to the deployment's collector (such as Grafana Alloy). It's off unless configured, with the standard `OTEL_*` environment variables (endpoint, service name, resource attributes). Every trace is kept unless sampling is configured, in the same standard way. A collector that's missing, slow or down never delays or loses a page, a request or a delivery: the telemetry is dropped instead, and the API or client logs that it's dropping it, at most once a minute. With telemetry on, the app stays within the resource budget (section 8).
- **R70. What telemetry may contain** (P1; owner, 2026-10-30). Nothing exported contains page text, search terms or other query values, redacted details, tokens, cookies, client keys, secrets, email addresses or names. HTTP spans and metrics name the **route pattern** (`/api/v1/messages/{id}`), never the real path or query string. Database spans name the query, never its values. Errors carry their kind, not values from the request. A signed-in request's span carries the user's **numeric ID and role**, and nothing else about the person; spans for what users do never carry message, alias or job IDs. The API continues a trace sent with a request only from a client (R14); browser and PowerShell requests start their own.
- **R71. A page's trace, end to end.** With telemetry on in both, the client starts a trace when it decodes a page and sends the trace context with it (W3C `traceparent`), and the API continues it. One trace then shows each step with its duration: decoding, buffering while the server was unreachable (R15), the post, ingest's steps (redaction, parsing, dedup, location), the database write, the live update, and each integration delivery with its retries (R51a). The ingest span records the outcome (stored, duplicate or refused) and the stored message's ID.
- **R72. Requests and load.** Every API request is a span with its route, status and duration, and database calls under it are child spans. The nightly jobs and re-parsing are traced too. Long-lived connections (live updates, R63b's watch) don't become hours-long spans; the ADR says how they're recorded. Metrics on R52's endpoint add: requests by route and status with their durations, abandoned requests by route (R73a), database pool use, open live-update connections, the Go runtime's memory and CPU, and how far a re-parse has got and its state (R23b, R23c), and retroactive redaction's (R45a).
- **R73. Logs.** With telemetry on, the API's and the client's log lines are also exported, each carrying the trace and span ID of the work it belongs to. stdout logging is unchanged. The client's console page text (R13a) is never exported.
- **R73a. Abandoned requests aren't errors** (owner, 2026-11-19). A request whose browser or client went away before the answer (its own context cancelled, so its work stopped) is **abandoned**, not failed: the API logs it at INFO as "request abandoned" with its route pattern (never the path or query, R70), answers it 499 ("client closed request", nginx's convention), so it's never a 5xx in the request metrics (R72) or an error on its span, and counts it once by route. Only the request's own cancellation counts: a time limit the API sets itself (a deadline, or the scrubber's counts' limit) isn't an abandonment, and a failure past it stays an ERROR. A live-update stream that's already set up was counted then, and isn't again when it ends. A rising abandoned rate means pages slow enough that people give up (docs/monitoring.md).
- **R74. Client telemetry.** The client's metrics, exported over OTLP, tell a stuck radio from a network problem: lines read from the decoder, pages decoded, pages sent, failed sends and retries, buffered and dropped pages (R15), the time of the last decoded line and of the last successful send, and whether the radio pipeline (R13) is running, plus radio health when it runs the radio itself (R74a). A client that's switched off can't report: the server's last-seen metric (R39, R52) is what raises the alarm.
- **R74a. Radio health** (owner, 2026-10-31). When the client runs `rtl_fm` and `multimon-ng` itself (R13), it passes the audio from one to the other and measures it on the way, without keeping or exporting any of it: **audio received per second** and the **audio level**. `rtl_fm` runs without squelch, so a working dongle always produces audio: audio stopping while `rtl_fm` keeps running means the dongle is stuck and needs a reset, whether or not the network is sending pages. `rtl_fm`'s status messages still go to the client's log as before, and are also **counted by kind** from a fixed list (no device found, device can't be opened, USB transfer failed, tuner not locked), with anything else counted as "other"; their text is never exported (R70). Measuring never slows or changes the audio multimon-ng gets. A client reading stdin reports no radio health.
- **R74b. A radio that stops decoding** (owner, 2026-11-17: "add that alert"). A client whose radio still gives audio (about the 44,100 bytes a second of R74a, so not a stalled radio) but which decodes far fewer pages than it usually does is told of, per client, as **"radio not decoding"**: a weak or detuned signal, a wrong gain, a decoder in trouble. "Usually" is the client's own count at that time of day on the days before, so the alert works on any network with no number about the network in the repo: a quiet night isn't a fault, and a network, or an hour of it, with too few pages to tell a fault from chance raises nothing. The busiest of those days is left out of the usual, so one busy day (a big incident) doesn't make the same hour's normal traffic the next day look like a fault (owner, 2026-11-19, on the history backtest: ADR 0039). A client with fewer than two days of history of its own (a new one) raises nothing either. Pages count as the client decoded them, garbled ones included. A short lull doesn't fire it, and it clears only once decoding is well back, so a client near the line doesn't fire and clear over and over. Its thresholds are settings, beside the other rules' (ADR 0039).
- **R75. `/metrics` stays** (owner, 2026-10-30). The API's metrics stay on R52's endpoint, scraped by the collector with the metrics role's credentials, so a dead API shows up as a failed scrape. They aren't also pushed over OTLP.
- **R76. Example monitoring stack** (owner, 2026-10-30). `deploy/` has an example compose stack (Grafana Alloy, Tempo, Loki, Prometheus and Grafana) with pinned versions. It's LAN-only, with Grafana's anonymous access off and short retention by default (traces and logs 7 days, metrics 30 days). It's a separate application that other apps can use too: it owns a Docker network named `monitoring`, and PagerArchive (or anything else to be monitored) joins it through its own `compose.override.yaml` (owner, 2026-11-03; M19). It comes provisioned with:
  - a data source for each store, linked so a log line opens its trace;
  - dashboards: a page's path (time in each step), requests and load (by route, status and user ID, and a re-parse's progress, pages a minute and time left while one runs, Paused or Stopped with its progress when an admin paused or stopped it, and Idle otherwise: R23b, R23c; and retroactive redaction's the same way: R45a), and clients (last seen, not receiving, the client metrics of R74 and radio health of R74a). A client that has stopped reporting still shows its last reported values and how long ago they came, rather than disappearing (owner, 2026-10-31). The dashboards' titles don't repeat "PagerArchive": they're in a folder of that name, and a phone cuts long titles off. Each dashboard says how to read it, in a short text at the top and a description on each panel: what it shows, what normal looks like, and what would be a reason to worry (owner, 2026-11-17);
  - links from the dashboards to Explore that keep the dashboard's time range (owner, 2026-11-17): on each graph from traces, a link per series that opens Explore with that series' spans (the clicked user ID, query, step, or kind and cause); in each table of spans and on each Prometheus exemplar, a link that opens the trace. Grafana's own links that can't carry the range (a TraceQL exemplar's) are named as such in the docs, and a trace opened by its ID is looked for across all of Tempo's retention, so it's found whatever range Explore opens at;
  - alert rules: **a client not receiving** (R39's 30 minutes; the threshold is a setting), which clears when the client is heard again; **a radio stalled** (R74a: a client running the radio reports no audio, or its pipeline not running, for 2 minutes; the threshold is a setting), which clears when audio flows again (owner, 2026-10-31); **a radio not decoding** (R74b: audio flowing, but under a quarter of the client's usual pages for that half hour, the busiest of the 7 days before left out, for 5 minutes; the thresholds are settings), which clears when decoding is back above half the usual (owner, 2026-11-17); and **the API unreachable** (failed scrapes). They go to a contact point the deployment sets up, such as email or Pushover, whose credentials live in Grafana, never in the repo.

  The docs explain how to run it alongside PagerArchive, how to point the API and client at it, and how much memory it uses. They also say that Grafana access is for the deployment's admins, because it shows client and user IDs. The stack isn't counted in the resource budget, like Authentik.

- **R77b. A new release is told once** (owner, 2026-11-18: "show the users that a new release has landed. It should be brief. It should just contain a message like new release! Check out the release log"**, "Check out the release log" a link to that release's notes, as the version's tag links (R77: the same address, a new tab, no opener or referrer). It contrasts clearly with the page in every look and theme: its text and link are at least 4.5:1 on its fill, and its edge at least 4.5:1 against the page (today the new-page highlight, `--highlight`, in an amber edge, `--notice-edge`). A countdown line along its foot shrinks, steadily, over the time it has left, and stops while it waits; it's kept with reduced motion, as it tells the time left. After 8 seconds it shrinks quickly (about a third of a second) and flies into the version's tag at the foot of the side menu (a menu scrolled so the tag is out of sight scrolls to show it first), which then briefly lights up (as the notice looked, its ring at least 3:1 against what it sits on); on a phone, where the tag is inside More (R81), it flies into the More button, which lights up. It waits while the pointer, a finger or keyboard focus is on it, and has at least a second left once they leave; a tap or click anywhere on it, or Esc, sends it there at once (it has no close button; so on a phone, a finger held on it holds it, and lifting the finger sends it); if focus was in it, focus goes to where it landed. It's announced politely (`aria-live="polite"`, not an alert), never takes focus, and blocks nothing but its own small box, which covers neither the side menu nor the bottom bar (it sits beside the menu, or above the bottom bar on a phone); its link is reached with Tab. With reduced motion (`prefers-reduced-motion: reduce`) it fades out quickly where it is instead of flying, and what it would have landed on still lights up. At 1,280 and 375 px, light and dark, tokens only (R82c).
  - **Once per user, on every device.** The account keeps the last version its user was told of; the server decides, not the browser. The notice shows when the version running isn't that one, and the server records it as told the moment it says to show it, so a reload, a second tab, browser or device doesn't show it again (of two opened at the same moment, only one shows it). Every installed version counts, patches too. A build that isn't a release (anything but `MAJOR.MINOR.PATCH`, such as `0.0.0-dev` or `1.9.1-dev+abc1234`) never shows it and records nothing. An account with no version recorded, a new user's at their first sign-in and every existing account the first time a release with this notice runs, records the running version silently, with no notice: it starts with the next release.
- **R78. Unknown capcodes page.** R33's "capcodes with no alias" list gets its own page under Tools. It lists the most messages first (counted over all time), then the latest seen. Capcodes with 5 or fewer messages are hidden: the page ends "and N more with 5 or fewer messages", with a control that lists them too, in the same order. The threshold is fixed at 5 (owner, 2026-11-12). The search filter `is:unaliased` stays, unchanged: it still finds every page to a capcode with no alias.
- **R79. Breadcrumbs show where a page is, not how you got there.** Every page below the top level shows its place in R77's tree (`Administration › Templates › Example Fire`). A page's breadcrumbs are the same whether it was reached from the menu, a search, a link or a bookmark. Each level above the current page is a link.
- **R80. Using the width.** At 1,280 px and wider, the page uses the full width: the side menu, the message list, and the selected message's detail view (R35c) in a pane beside the list instead of a page of its own. There's no fixed-width centre column with empty margins. The list keeps its place and filters while messages are opened in the pane. The detail view still has its own address, so it can be bookmarked and shared.
- **R81. Phones** (under 768 px wide). Phones get their own layout, not a squeezed desktop one:
  - a **bottom bar** with Messages, Map, Albums and More; More opens the rest of R77's menu;
  - **desktop-only pages** are left out of the phone menu: the print sheet and Administration. They still open from a link or bookmark, so nobody is locked out on a large phone or a tablet;
  - on phones, Integrations works as on a desktop (owner, 2026-11-14): setting one up, editing it, Send test, its deliveries and deleting it, with the same rules, checks and secrets (R47-R51c, R87d), in a form that fits the width and the finger; each integration's Pause/Resume is a **switch**;
  - R31's and R35c's phone rules still apply;
  - the version's tag (R77) is at the bottom of More (owner, 2026-11-14).

  Desktop or phone is decided by screen width, never by detecting the device.
- **R81a. Coming back to the list.** Leaving the message list and coming back (back button, breadcrumb or menu) restores its search, date range and scroll position.

### 7.18 Year scrubber (owner, 2026-11-01)
- **R81b. Scrubber** (owner, 2026-11-09; 2026-11-13). A strip down the right side of the message list (and the alias, capcode, job and large-event views) for **large jumps**; scrolling the list does the rest. **An album has none** (owner, 2026-11-13): an album is a hand-picked set, not a time range. It covers the **last 30 days**, or the **selected date range** when one is set, newest at the top: one mark per day, per week when the range is over 90 days, or per month when it's over a year. **Today and yesterday** are split into hours. It sits **over the list's right edge**, not in a column of its own, with nothing behind it, and the page's own scroll bar is hidden while it's there, so it owns the window's edge (nothing moves sideways between pages with and without one). **With a mouse it's hidden** until the pointer comes within **50 px of the window's right edge**, and while it's shown a line on it follows the list as it scrolls. Clicking jumps the list to that day, week, month or hour; holding the button and dragging moves the list as the pointer goes, naming the mark under the pointer; the strip stays shown until the button is let go. It never covers a row's links: they keep clear of the strip. **Keyboard:** Alt+J (Option+J on a Mac), or a skip link at the top of the page, goes to it and shows it; it's also in the tab order. Arrow keys move by one mark (by hour within today and yesterday), Page Up and Page Down by week; Escape goes back to the list. A window narrower than 768 px with a mouse has no scrubber.
- **R81c. How busy.** With a mouse, each mark on the scrubber shows how many messages it holds (more dots, more messages). The counts follow the current search and live updates, and working them out stays within the resource budget (section 8).
- **R81d. Zoom** (owner, 2026-11-09). With a mouse, when the list is at an hour of today or yesterday, a button at the top of the scrubber shows that hour as twelve **5-minute blocks**, each with its busy dots, with the hours before and after a click away. Clicking or dragging jumps the list to a block. Another button goes back. Older days have no zoom.
- **R81e. On a touch screen** (owner, 2026-11-13). A touch screen (no hover, or a coarse pointer), at any width, has no strip and no marks: a **grab tab** at the window's right edge appears while the list scrolls, placed by where the list is in time, and fades a moment after it stops. Dragging it moves the list as the finger goes, with a bubble naming the day it will land on; the tab stays under the finger, and the day doesn't flicker at a boundary. It covers the **last 7 days on a phone** (under 768 px) and the last 30 on a tablet, or the selected range; when a day would be too small for a thumb, it moves by weeks, months or years instead. The list scrolls on past the oldest day: the tab then waits at the bottom and says where the list is ("Earlier: Mon, 2 Nov"). The page's own scroll bar is hidden while the tab is there.

### 7.19 Albums (owner, 2026-11-01)
- **R82. Albums.** Any signed-in user can create albums, name and rename them, delete them, and add messages to them or remove them. An album is **private to its creator**: nobody else sees it, admins included, and the API refuses anyone else. Messages are added from the message detail view ("Add to album"); the message list keeps no tick boxes (R67). An album shows its messages newest first, as they are **now**: current aliases (R23a) and current redaction (P1), with no scrubber (R81b; owner, 2026-11-13).
- **R82a. Albums don't keep messages.** Retention (R45) deletes messages in albums like any others, and a deleted message leaves its albums. An album left with no messages is deleted too, unless it has a description (R82f): then it's kept, and says its messages have passed the retention period (owner, 2026-11-12). A message's note (R82f) goes with the message. The album screen says this in one line.
- **R82b. Albums and accounts.** A deactivated user's albums are kept, since they may be reactivated. Deleting an account deletes its albums (R43c).
- **R82f. Descriptions and notes** (owner, 2026-11-12). An album has an optional **description** (what it's for), up to 2,000 characters. Each message in an album has an optional **note** (why it was kept), up to 500 characters; the same message in two albums has a note in each. Both are plain text, set and changed by the album's owner, and shown in the album view: the description at the top, a note with its message. They're private like the album (R82). They're the user's own words, not page text, so the redaction rules (P1) don't apply to them: a user chooses what to write. They aren't searched by the search box (R33a).

### 7.20 Looks (owner, 2026-11-02)
- **R82c. Everything is a token.** From M13, every value that styles the UI is a token in one place: colours, type sizes, spacing, corner radii, target sizes, and how each priority is shown (edge, tint, dot or label). Components use tokens only, and CI fails a component with a hard-coded value. A look is one set of these tokens, in light and dark, so a look can be added or changed without touching a component. M13 builds Harbour only (ADR 0015). The tokens and the base styles come from **ArchiveUx**, the archive apps' shared design system (owner, 2026-11-19: its own repository, `RIKIKU/ArchiveUx`, so PagerArchive and RadioArchive feel like one application), pinned to one of its releases (ADR 0049); only the map's tokens (`--map-*`, `--detail-map-width`, `--area-tag-*`) are PagerArchive's own, in `web/src/app.css` (owner, 2026-11-20). ArchiveUx's rules (its `docs/design-system.md`) say which colour may be drawn on which, and its pattern for each element; PagerArchive follows them.
- **R82d. Choosing a look.** Users choose between **Harbour** (the default) and **Console** (M13's second prototype, ADR 0015) in the account menu, beside Auto / Light / Dark. The look is **saved on the account**, so it follows the user to every browser and device. A change applies at once, without reloading, and a page never shows the default look first and then switches. Pages before sign-in use Harbour. Every look meets WCAG 2.1 AA in light and dark (section 8). **The contrast rule** (owner, 2026-11-19: "WCAG AA it is"), for every look and theme: text at least 4.5:1 on its own background; edges and controls (focus rings, control borders, the marks that show priority) at least 3:1; and anything that must be noticed (a notice, an admin's alert, anything that appears on its own) an edge at least 4.5:1 against the page. ArchiveUx's CI measures every pairing its rules allow, and PagerArchive's browser test measures the tokens as drawn. So an admin's backup and upgrade alerts have a strong edge (`--alert-edge`), and the "When it's busy" grid writes each count in its shade's own text colour (`--heat-0-fg` to `--heat-4-fg`) (owner, 2026-11-20).
- **R82e. The favicon.** The app has a favicon, a white pager on a rounded square of Harbour's accent green, that's visible before sign-in: loading it needs no session (owner, 2026-11-05).

### 7.21 Importing messages (owner, 2026-11-02)
For moving an existing archive into PagerArchive. Users aren't imported; aliases come in through the alias import (R30, R63).
- **R83. The import.** A server-only command, `pagerarchive import-messages <file>`, reads pages from a JSON Lines file, one page per line: `received_at` (RFC 3339, with its offset), `capcode`, `text`, and optionally `source_id` (the page's ID in the archive it came from). The format is documented with an example.
- **R83a. The same path as a live page.** Each page goes through redaction (P1), cleaning (R17), parsing (R7), deduplication (R19) and job grouping, as if a client had sent it at its `received_at`. Duplicates in the file are merged by R19's 10-second rule, as live pages are. A page that fails to parse is still stored and shown in full (P2).
- **R83b. Quiet.** Imported pages set off no integration (R47), live update (R32) or alert, and don't count as a receiver being alive (R39). They're recorded as received by "import", not by a client.
- **R83c. Safe to repeat.** Importing the same file again stores nothing new: by `source_id` when it's given, otherwise by the dedup key and receive time. An import that stops part-way can be run again to finish.
- **R83d. Retention.** Pages older than the retention period (R45) are skipped and counted, not stored.
- **R83e. Dry run and report.** `--dry-run` reads and checks the whole file and stores nothing. Every run reports lines read, pages stored, duplicates merged, parse failures, pages skipped by retention, and refused lines by line number and reason. No report, log line or telemetry ever contains page text (P1, R70).
- **R83f. Speed and budget.** The import stores at least **500 pages a second** while the app keeps receiving and delivering live pages, within the resource budget (section 8). At that rate, 4.6 million pages take under 3 hours. An import is a one-off, so searches may be slower than R33b while it runs; it must not slow down live pages (owner, 2026-11-02). On a production-sized archive it takes about an hour and a half, so it's a long job (R91).

### 7.22 Installing and upgrading (owner, 2026-11-02)
- **R84. No checkout.** Running PagerArchive needs no copy of the source repository. A deployment holds `compose.yaml` and an `.env` example, both attached to every GitHub release, plus its own data: its network profile (mounted at runtime, section 6) and its map tiles. PagerArchive's own images hold everything PagerArchive needs: given an empty database and its own role (R84i), the API creates its tables and whatever else it needs on start; the database's first-start scripts make the roles. With no network profile mounted, it uses the example profile built into the image, and logs a warning on every start that the example's redaction rules aren't the network's (owner, 2026-11-03). Third-party services (PostGIS, Authentik, the optional monitoring stack) run their upstream images unchanged: the project never publishes its own builds of them (owner, 2026-11-03). `compose.yaml` names every image, PagerArchive's included, by its **major.minor** tag (such as `pagerarchive:0.15` or `postgis/postgis:18-3.6`), with no patch number and no digest, so `docker compose pull` gets every patch release. Keeping up with patches is the deployment's job (owner, 2026-11-03). Where an upstream image has no major.minor tag, the nearest tag that moves only within a minor version is used, and the ADR lists it. Their configuration (Authentik's blueprint and email templates, the database's first-start scripts for Authentik and the API's roles, the script that switches an older install to the API's own role, the monitoring stack's configs, dashboards and alert rules) is attached to every release as one archive, unpacked next to `compose.yaml`. The optional example monitoring stack's `compose.yaml` and `.env` example are attached the same way.
- **R84a. Upgrading is installing the latest release.** Upgrading from any earlier release is getting the new `compose.yaml` and configuration archive and running `docker compose pull && docker compose up -d`, and nothing else:
  - migrations run when the API starts, only go forward, and make only quick changes (R91a);
  - a new setting has a safe default, or the app creates it on first start (secrets included) and keeps it in its own volume, so `.env` never needs editing for an upgrade;
  - nothing is run by hand inside a container;
  - a changed third-party configuration file takes effect on `docker compose up -d`.

  A release that can't meet this (for example, a new major version of PostgreSQL) puts "Upgrade steps" at the top of its release notes, and needs the owner's approval.

  **Before 1.0.0** (owner, 2026-11-03), R84a and A77 bind loosely: a release may break the upgrade from an earlier one without the owner's approval, as long as its release notes give the "Upgrade steps" (which may be a fresh install). 1.0.0 is the first release after the existing archive's data is migrated and users are working on PagerArchive.
- **R84b. Docs.** The install is: download `compose.yaml`, the `.env` example and the configuration archive, unpack the archive, fill in `.env`, then `docker compose up -d`. The upgrade is the two commands above, and a patch release within the same minor version needs only those two commands, not a new `compose.yaml`; a minor release needs its own `compose.yaml` and archive first, and the docs say so plainly (12.1). The `git pull` instructions go.
- **R84c. PostGIS keeps up with its image** (owner, 2026-11-10). A newer `postgis/postgis` image updates PostGIS's library, but each database keeps the extension version it registered until `ALTER EXTENSION … UPDATE` runs, which the image does only for a new database. So on every start, after its migrations, the API updates each installed PostGIS extension whose version is behind the image's: `postgis` first, then whichever of `postgis_raster`, `postgis_topology`, `postgis_sfcgal` and `postgis_tiger_geocoder` are installed (it never creates one). One already at the image's version runs nothing. Each update is logged at INFO with the extension and its old and new versions. If one fails (for example, the API's role doesn't own it), a WARN names the extension and the fix (run `ALTER EXTENSION <name> UPDATE` as its owner), and the API starts anyway. One the image no longer provides (PostGIS 3.7 dropped `postgis_tiger_geocoder`) is left as it is, with a WARN saying so. A switched API (R84i) isn't the superuser, so it can't run the update: that stays a hand step for the operator, run as the superuser, and is alerted (owner, 2026-11-19: "option 1 plus the alert"; ADR 0033). R52's endpoint has `pagerarchive_db_extension_update_pending{extension}`, 1 for each installed PostGIS extension or `pg_trgm` whose registered version differs from the image's default and 0 for each that's current (one the image no longer provides has none), checked when the API starts, after the update above, and again every hour, as a db container can be recreated while the API runs. The example monitoring stack (R76) alerts on it with **Database extension update pending**, one alert per extension, saying exactly what to run (`docker compose exec db psql -U postgres -c 'ALTER EXTENSION <name> UPDATE;'`) and that it's a hand step; a 0, or no series, raises nothing. Nothing privileged runs the update on its own.
- **R84d. Automatic upgrades, if switched on** (owner, 2026-11-14; ADR 0030). A deployment installed with no checkout (R84) can upgrade itself. It's **off by default** and switched on per install, by a script in the configuration archive (`deploy/auto-upgrade/auto-upgrade.sh enable`), which runs on the host where the compose project lives, as the user who runs it, from that user's crontab (no root needed) or a systemd user timer. The API never runs Docker or upgrades anything (as R86a). Never two runs at once, and never while a backup is running or asked for (the backup service's own lock refuses it, and the run tries again the next hour). Switching it off (`disable`) stops the checks; a manual upgrade (R84a) works on or off.
- **R84e. What's installed, and verified first.** Every hour the script finds the newest **full** release on GitHub's releases API (not a draft, not a pre-release; no token, as the repository is public). It installs it only if it's newer than the version running, in the same major version, not marked failed (R84g), and its release notes don't start with "Upgrade steps" (R84a): those are left to the owner, and the status says why. First it **verifies** the release's attached files and PagerArchive's images (the server's, and the client's when the deployment's `compose.override.yaml` names it by a major.minor tag) by their attestations (12.1): signed by the repository's `ci.yml` (the workflow the Release workflow runs), on main, on a GitHub-hosted runner, from the commit the release's tag names (owner, 2026-11-16: security review), with a pinned release of the GitHub CLI that the script downloads into the install's folder and checks against that release's published checksum on every run; the attestations come from GitHub's API, with no sign-in. If verification can't run or fails, nothing is installed and it tries again the next hour. The images Compose pulls must be the ones verified.
- **R84f. Backed up, upgraded, checked.** Before upgrading, the backup service's `now` (the same checked backup as the nightly one, R86a) is kept aside where a later backup can't replace it, with copies of `compose.yaml`, `.env`, `compose.override.yaml`, `deploy/` and the monitoring stack's files; the last 3 are kept. The upgrade installs the verified `compose.yaml` and archive, moves a client's major.minor tag in `compose.override.yaml` to the new minor version, and runs `docker compose pull && docker compose up -d`, and does the same for the example monitoring stack when the install names its folder. Then the **health check**: every container running; the API answering, running the new version, from the verified image (it answers only after its migrations have run); the install's own URLs answering, if it lists any; and **a page stored after the restart**, within a window (30 minutes by default), but only when pages were arriving before: at least 20 pages in the 4 windows before the upgrade, 5 a window on average, so a whole window without one would be very unusual. On a quieter network that check is skipped and the status says so: a quiet network never causes a rollback (owner, 2026-11-14).
- **R84g. Rolled back on failure.** If the upgrade or its health check fails, the previous release's files and the images that were running go back, with nothing pulled. If the new version changed either database (PagerArchive's migrations, Authentik's, or a PostGIS extension's version, compared before and after), the pre-upgrade backup is restored first, the documented way (R86b): into a new, empty database, with the stack stopped, before the old version starts. The release is **marked failed** and not tried again unless an admin says so on the server (`retry`). Each step (check, verify, backup, upgrade, health, rollback, restore) writes one structured line, with the versions and, on a failure, the reason as fixed text: never page text (P1). A rollback that fails leaves the stack as it is (stopped, if the restore failed) and says where.
- **R84h. Seen in Administration and Grafana** (owner, 2026-11-14; 2026-11-15: "If an automatic update fails I think we should be capturing that in Grafana also"). The script writes a status file in a folder the API mounts read-only, as the backup service's (R86a). **Administration → Upgrades** shows whether it's on ("off" when not), the last check and its result, the last upgrade, the history and the releases marked failed; Administration shows a notice when the last upgrade failed (rolled back, with or without a restore, or not), when one stopped part way, or when there's been no check for 3 hours. R52's metrics have whether it's on, the last check's time, the last successful upgrade's time and versions, failures and rollbacks as counters, whether it's failing and its current state. **A run in progress is shown as one** (owner, 2026-11-20: "we should make that dashboard reflect in progress upgrades too"): the status has when the run going now started and, once it knows, the release it's upgrading to, and the metrics have both (the start's time, and the target as an info metric's label, one series, none while idle) beside its step. **The last check** is when a run last checked for a release, which is when it started: during a run it's that run's start, with the result "in progress" until it ends, and a run's end doesn't move it. The example monitoring stack treats it as backups (R86d): its log lines in Loki (Alloy reads the script's log file from the same folder, read-only, keeping only its known fields), panels on the backups dashboard (at the top, a run going now, plainly: its target release, its step and the time since it started, or "No upgrade running"; and last upgrade, version history, failures and rollbacks, time since the last check) and an alert rule, **Upgrade failed**, through the same contact point as the others. There's no other alerting (owner: "alert is a strong word").
- **R84i. The API's own database role** (owner, 2026-11-15: security review, D1). The API connects to PostgreSQL as its own role, `pagerarchive`, never as the superuser. The role owns PagerArchive's tables, functions and types and may create new ones in its database's public schema (its migrations); it isn't a superuser, can't create roles or databases, is in no other role (so none that reads or writes the server's files or runs programs, such as `COPY … TO PROGRAM`), and can connect to no other database, Authentik's included. Extensions that need the superuser (PostGIS) are created for it before its first start. **A new install** gets it from `.env` (`PAGERARCHIVE_DB_USER`, `PAGERARCHIVE_DB_PASSWORD`, generated like the other secrets): the database's first-start script makes the role, and the locked-accounts metric's role and function (R52), which the API can then no longer make. **An install from before the role** keeps working unchanged after any upgrade, by hand or automatic: with neither setting in `.env`, the API connects as the superuser as before and logs one WARN on every start saying so and naming the fix. The fix is one script in the configuration archive, `deploy/postgres/api-role.sh`, run on the host by the operator (owner, 2026-11-15: one existing install, switched by hand, no automatic switch-over): it makes the role, hands it PagerArchive's existing objects and takes away what it mustn't have in one transaction, sets a new random password in `.env` without printing it, recreates the API only, checks the API connects as the role (not a superuser, no connection to Authentik's database, no programs) and that every table still has its rows, and puts `.env` back if the API doesn't come back as the role. Run again, it changes nothing; `undo` returns the API to the superuser. A rollback to a release from before the role needs no undo: its `compose.yaml` ignores the settings. The backup service keeps the superuser (it dumps and restores both databases), and a restore gives the roles their rights again (R86b).
- **R84j. The reverse proxy example keeps its LAN-only promises** (owner, 2026-11-16: security review, D2, D3, D8). `docs/deploy.md`'s nginx example (section 5) keeps Authentik's admin interface (`/if/admin/`) LAN-only, and both hostnames LAN-only until the first admin is set up, and that holds in both layouts it gives: **direct**, where the internet reaches this proxy, and **chained**, where another proxy or a tunnel's connector on the LAN forwards internet traffic to it. For the chained layout the docs say plainly that the LAN-only lines alone let every internet request in, and give two fixes: refuse those paths on the proxy the internet reaches first, or have this proxy take the client's address from the forwarder's header (`set_real_ip_from` the forwarder's own address only, never a range) and refuse the forwarder's own address where only the LAN is allowed, so a request without the header fails closed. The example passes Authentik `X-Forwarded-For` set to the address the request came from, never the client's own header, and refuses `/metrics` (scraped on the LAN at `API_BIND`, never through the proxy). The docs give a check from outside the LAN. Every snippet is valid nginx, for SWAG's nginx too.
- **R84k. Versions are checked before use** (owner, 2026-11-16: security review). Every version and tag the automatic upgrades take in, from the running API, from GitHub's releases API, from the status file's backup set names and as an argument (`retry`, `verify`), is used only if the whole of it is one release's `X.Y.Z` (or its tag `vX.Y.Z`), on one line; anything else is refused, or the run is skipped, before it reaches a path, a file name or a command. Values go to a shell in a container as arguments, never inside its code, and old backup sets and file copies are removed one path at a time.

### 7.23 Maintenance (owner, 2026-11-03)
- **R85. Base images.** A daily check notices when a base image under PagerArchive's own images (the server's and the client's) has changed upstream, often for a security fix. A change waits until it's 3 days old by its registry's record, so a broken or withdrawn image has time to be noticed, as the libraries' do (R85a; owner, 2026-11-15; ADR 0032); a fix for a known vulnerability (Renovate's vulnerability alerts) doesn't wait. A change merges on its own, once CI passes, and goes out in the next release (section 12.1), so it reaches deployments at their next `docker compose pull` after that.
- **R85a. Libraries, monthly.** Once a month, PagerArchive's dependencies (Go modules, npm packages, GitHub Actions) are updated in two pull requests: one with every patch update, which merges on its own when CI passes and goes out in the next release (section 12.1), and one with everything larger, which waits for the owner's review.
- **R85b. Third-party versions, weekly.** A weekly check opens a pull request when a third-party image in `compose.yaml` or the monitoring stack has a new major or minor version (such as Authentik 2026.5 to 2026.8, or PostGIS 18 to 19): one pull request for all of them, except Authentik and PostGIS, which each get their own (owner, 2026-11-12). It always waits for the owner's review, as these can need "Upgrade steps" (R84a). An image with no tag that moves within a minor version (R84; the ADR lists them) gets a weekly pull request for its patches too, which merges on its own when CI passes (owner, 2026-11-03).
- **R85c. Every automatic update follows 12.1:** every check its change affects passes before it merges, and it goes out in the next release. An update that fails CI, after CI's own retry (12.1), is left open, not merged, and the owner is told.

### 7.24 Backups (owner, 2026-11-03)
- **R86. Nightly backups.** Every night, PagerArchive's database and Authentik's are each dumped to a folder the deployment mounts, with nothing to install or schedule by hand: the stack in `compose.yaml` does it. Dumps are kept for **14 days** by default (a setting), and older ones are deleted. A dump is written under a temporary name and renamed when complete, so a file backup tool copying the folder at any time never takes a partial one.
- **R86a. Checked, and failures are seen.** Each night's dumps are restored into a throwaway database with no network and compared (tables and row counts). The time of the last good backup is in R52's metrics, and an admin sees in Administration when the last backup failed or is more than 36 hours old. The example monitoring stack alerts on it. **Back up now** (owner, 2026-11-14): an admin can start the same backup and check at once, from Administration → Backups or the PowerShell module (`Start-PagerArchiveBackup`, with `-Wait` for the result; `Get-PagerArchiveBackup` for the state). The page shows it asked for, then running, then its result, with times. The API never runs it and never reaches the dumps or Docker: it writes a request on a volume of its own, and the backup service, which checks every minute, runs the backup and check and then deletes the request. One at a time: a request while one is asked for or running (the nightly one too) is refused, saying since when. The extra backup is that day's, under the same retention (R86): it replaces one made earlier that day, and after a good one the nightly backup doesn't run again that day.
- **R86b. Restore.** One documented command restores a chosen night's dumps into an empty install, after which everything is as it was then: pages, aliases, templates and icons, integrations, users and their sign-ins.
- **R86d. Backups on the dashboard** (owner, 2026-11-07; M18). The example monitoring stack shows backups on a dashboard: time since the last good backup (coloured by age), whether the last one is failing, and each night's dump size, dump time and check time. The backup job reports those three as metrics (R52), so the check's growth with the archive can be seen.
- **R86c. Off the host.** Copying the backup folder to another machine (a NAS, cloud storage) is the deployment's job. The docs give an example. The dumps hold only what the databases hold, so P1 holds: no redacted detail is in a backup.

### 7.25 Large events (owner, 2026-11-12)
- **R87. Large events.** PagerArchive notices when something big is happening on the network and groups the pages into a **large event**. It's meant only to alert users that something big is happening, so they know where to look; for more they listen to the radio or look at other systems. An event is simply a large event: it has no levels or kinds (owner, 2026-11-13). Only **Emergency** pages to capcodes with an alias count (not heartbeats, not unaliased capcodes), and not pages to an alias marked **ignored** (R27): those are usually the network's own traffic, unrelated to emergencies, so they neither open, join nor count towards an event, live or rebuilt (owner, 2026-11-14). Imported pages (R83) don't count either: they form no events (owner, 2026-11-14). An event is **opened** by any of:
  - **a code:** an Emergency page carrying a code that matches the network profile's pattern (R5), such as one naming a pre-formed group of appliances sent together (no roster of groups or members is kept, as groups change each season);
  - **a field's value** (owner, 2026-11-14): an Emergency page whose field holds a value its agency profile lists (R7), such as an alarm level high enough to mean something big (some agencies dispatch with a level on each page: a first alarm sends two or three appliances, and each level above sends more). It opens or joins an event exactly as a page with a code does, and is otherwise silent: the app shows no level and doesn't say what opened an event (R87b);
  - **a job's Emergency pages:** one job (R23) with **20 or more Emergency pages** that count (above: an ignored alias's pages are not among them; owner, 2026-11-14, before which they were). Each stored message counts once: a copy from a second receiver is the same message (R19), while the same page to two aliased capcodes is two (R20). What the pages say, appliances included, doesn't matter. An admin can change the 20 (owner, 2026-11-13; before, it was 20 distinct units).
- **R87a. Grouping by time.** An Emergency page that would open an event, arriving within **12 hours** of an open event's latest page, joins that event instead, and so do the other pages of its job. An event **ends** after 12 hours with no page joining it. After that, a page that would open an event opens a new one, even one on a job the ended event holds (a long job heard again after 12 quiet hours), and the new event is told to large-event integrations (R87d) as any other is (owner, 2026-11-14: "After 12 quiet hours just open a new event"). Pages carry no reliable link to one incident (each dispatch gets its own job), so on a busy day several incidents may share one event; that's accepted.
- **R87b. No levels** (owner, 2026-11-13). Events aren't tagged with levels or with what opened them. (Before, an event recorded the levels "deployment", "several deployments" and "big job", with when each was met.) A profile's level fields (R7) don't change this (owner, 2026-11-18): their levels are shown only in the integration form, to choose a level filter (R49a); pages, the job view, events and notifications still show no level list. A profile may still label a level field's values in its `labels`, as any field's (P3), and those labels show wherever labels do, on pages and in payloads (owner, 2026-11-18, of an agency's first and second alarm labels: "keep them and strengthen that to identify the others"); events still aren't tagged with them.
- **R87c. Large events in the app.** A **Large events** page under Tools lists events, newest first: start and end (its first and last pages' times; never "ongoing" or "ended": the app can't know whether an incident is over, and the 12-hour window only decides which pages join; owner, 2026-11-13), and its numbers of jobs and Emergency pages. An event's view shows those, its **job numbers** (each a link to its job's view) and its pages like the message list (P2, P1), with the scrubber (R81b). Users see jobs and job numbers: the app never shows a count or list of the codes in an event's pages, never calls them "deployment codes" and never counts appliances (owner, 2026-11-13). Every signed-in user sees events, as they see the pages.
- **R87d. Large-event integrations.** An integration (R47) may select **large events** instead of capcodes or aliases (R48), with nothing more to choose. It fires **once** per event, when the event opens, and never again for that event: not as more pages, codes or jobs join it, and not when events merge (each was told of when it opened). It sends a **summary**: the event's id and start, the page that opened it (its id and sent time), its job numbers and number of Emergency pages so far, and a link to the event's view; never page text, appliances or codes (owner, 2026-11-13). Destinations, safety and delivery as R50-R51b (on time: within 5 seconds of the page that opened the event).
- **R87e. Kept and deleted.** Events are derived from pages: retention (R45) deletes an event when its last page goes, and an event's numbers follow the pages it still holds. A rebuild (R87f) groups the pages still kept, so an event that retention has thinned may be regrouped from what is left (a job below the threshold no longer holds one open).
- **R87f. Rebuilt when pages are re-parsed** (owner, 2026-11-14: "Re-parsing should regroup"). When pages are re-parsed (R23a: an alias added, changed, deleted or marked ignored or not, a template's agency profile changed or an agency profile itself, such as gaining or changing its `large_event_fields`, or the network profile changed, such as gaining or changing its code pattern), the large events those pages belong to, or could now belong to, are **rebuilt**, so they are what live ingest of the same pages, in the order they were sent, would have made. It's bounded and cheap: only the time around the re-parsed pages (their sent times and 12 hours either side, extended over any event pages there could join and over every page of their jobs, while those chain), in batches, in the background like the re-parse itself. A rebuild **never sends anything** (R87d), even for an event it forms: like an import (R83b), only live ingest tells integrations. Deliveries already made stay, each with whichever event now holds the page that carried it (none, if no event does). An event's ID may change: the event that keeps most of an old event's pages keeps its ID, and a link to an ID that no event keeps finds nothing (404), as one to an event merged into another does. The threshold is the one set now.

### 7.26 Areas (owner, 2026-11-16)
- **R88. Areas** (owner, 2026-11-16: on a large job the owner needed the job's district at a glance, to pick the radio channel; "position-based district and map layer first"; several layers, owner, 2026-11-17: a second agency's fire districts too). The network profile may name one or more **layers** of **areas**: named polygons, such as the districts a network's agencies are organised in, and a second agency's districts over them. Each layer has an **id** (a machine name, unique in the profile), a GeoJSON file, what one is called (its **label**, shown before each name: "District" makes "District 08", "Metro" makes "Metro Central"), the feature property that names each one, the data's **attribution** (R5), and how the map outlines it (**solid**, **dashed** or **dotted**; by default the first layer solid, the second dashed, the third dotted). They're shown in the order the profile lists them. Each file is GeoJSON, in WGS84 longitude and latitude, of Polygon and MultiPolygon features; features with the same name are one area (one district's land and its water, say). Layers may overlap each other; areas within one layer shouldn't (R88a). The repo ships only the example's made-up ones (section 10): a deployment's own belong in its private profile repository, with their attribution. `validate-profile` fails on a problem with a layer's file, naming the layer, the file, where and what (R10): a file that's missing, isn't a GeoJSON FeatureCollection, has no features, or says it's in another coordinate system; a feature whose geometry isn't a Polygon or MultiPolygon, has a ring of fewer than 4 positions or a position outside WGS84's ranges; a feature without the name property, with an empty one, or one longer than 40 characters. The server doesn't stop for one (R88d). A number names an area as the file writes it. Two layers with one id, or an outline other than the three, are a profile error (R1).
  - **R88a. A page's areas.** A page with a location (R24, R25) is in the area of each layer containing its point: at most one per layer, so a page can be in "District 08" and "Metro Central" at once. A point in no area of a layer, on an area's edge (between two areas, or at the edge of one) or in two of its areas at once is in none of that layer. It's derived from the location, not parsed (P3): it isn't a field, and isn't searched, exported or sent to integrations. It's kept beside the page, a row per layer, worked out when the page is stored and again whenever the page is placed again (a re-parse, R23a, or retroactive redaction), and it goes with the page (R45). Pages stored before a layer was added, or before its areas changed (R88d), get theirs of that layer in the background, a batch at a time, resuming after a restart; the other layers aren't worked out again. Until then a page shows the area it had, or none.
  - **R88b. Shown.** Each as its layer's label and its name ("District 08"), the layers in the profile's order. A **job's view** (R34) shows, above its pages, every area of every layer its pages are in (a job paging two districts, both in one of the other agency's, shows all three), each tag edged as its layer is outlined, and follows new pages; a **message's detail view** (R35c) shows each layer's area beside its location, under the layer's label; and the **map's list** of located and selected messages (R35) shows each one's. A page with no location, or in no area, shows none, and a job none of whose pages is in one shows nothing. (A page with no location getting its area from its alias is a later item.)
  - **R88c. On the map.** Every map (the map page, R35; a message's detail view, R35c; a report's map, R38c; owner, 2026-11-17: "The map on each individual page should also show the layer controls") outlines each layer's areas, each labelled with its label and name, over the background map and under what the map shows (the messages, the page's marker or ring, the heat layer), each layer in its outline style and colour (tokens, R82c), the layers telling apart in light and dark (R36) and at 1,280 and 375 px (R80, R81). One **"Map layers"** control (a layers icon, a target's size, under the full-screen button in the map's top-left corner; owner, 2026-11-17: a button per layer was "too intrusive", "like google maps does") opens a small panel beside it, inside the map, listing every layer: a checkbox for each, "<label> outlines" with a sample of its line, that hides and shows that layer alone, in full screen too (R35f). **One choice per browser for every map** (owner, 2026-11-17: "The user's layer settings should carry to every map in the system", remembered by "this browser", not the account): a layer hidden on one map is hidden on every map in that browser, on later visits and in its other tabs already open, and shown on one it's shown on all; the installed app (R90) keeps the choice its browser or device keeps for it. The panel is closed when the map opens; Esc (focus back on the control), a click or focus outside it, or the control again closes it. The control has `aria-expanded` and `aria-controls`, and opening it moves focus to the first checkbox. At 375 px it's the same control, and the panel, as wide as its labels and no wider than the map leaves, covers well under half the map; with more layers than fit, it scrolls. On a message's small map with the panel open, the page's marker (or ring) stays in sight beside it, at 1,280 and 375 px; on a report's heat map the heat and the outlines stay told apart, in light and dark. A profile with no layers has no control. Each shown layer's attribution is in the map's credits (R35g). The browser gets each layer's outlines simplified, at a tolerance that keeps them under 400 KB of GeoJSON (two layers together well under 1 MB) and gzipped, and keeps them until that layer's areas change: opening another map, or another message's, doesn't fetch them again.
  - **R88d. Changed.** A layer's areas are loaded again when its file or the property naming them changes, at start-up, and every located page's area of that layer is then worked out again in the background (R88a); the other layers are left as they are. Changing the areas, or their label, attribution or outline, doesn't re-parse a single page (R23a): they don't change what a page says, so the network profile's `areas` key is left out of what decides a re-parse. Removing a layer from the profile removes every page's area of it. **A layer's file that's missing or broken, or fails to load, doesn't stop the server** (owner, 2026-11-17: an install whose API won't start after an automatic upgrade is worse than one without its districts): the API starts, logs an error naming the layer and the problem, and Administration says the layer didn't load and why; a layer loaded before keeps its areas, shown as they were, until its file is put right, and one never loaded shows none. The other layers load as ever. R1 still holds for the profile itself.
  - **R88e. Administration** says, on its start page (R44b), for each layer: its label and outline, how many areas, the file they came from, their names and attribution, whether stored pages' areas of it are still being worked out, and, when its file didn't load, why, and whether the areas loaded before are shown meanwhile.

### 7.27 Failures and Authentik in Grafana (owner, 2026-11-17)
The owner: "a failures dashboard would be good"; "Authentik dashboards and monitoring ... a possible gap in our observability right now".
- **R89. A Failures dashboard.** The example monitoring stack (R76) has a **Failures** dashboard that answers "is anything failing, and what?" in one place: the alerts firing now; the API's server errors by route; pages refused (a bad client key, a malformed page, a clock ahead); clients not receiving, radios stalled or not decoding (R74a, R74b), clients' failed sends, retries, dropped pages and pages waiting to be sent (R15, R74); failed integration deliveries by kind; the last nightly run; backups (R86a); automatic upgrades and their failed steps (R84h); accounts locked (R44a); Authentik down, its failed sign-ins and its errors (R89a, R89b); and the API's and clients' ERROR and WARN log lines counted by message, with the lines (each opening its trace). It shows only what's measured: a log line's message is a fixed text, never page text, search terms, names or addresses (R70), so counting by it is safe. Each panel says how to read it. Dashboard titles are plain ("Failures", "Authentik"), with no "PagerArchive:" prefix: the folder says that (owner, 2026-11-17).
- **R89a. Authentik in the stack.** The stack scrapes Authentik's server and worker (their Prometheus metrics, which have no credentials) without exposing them: over a Docker network of their own that only the collector and those two containers are on, with no way out and nothing published on the host, which PagerArchive's `compose.override.yaml` joins them to (ADR 0036). The reverse proxy forwards only Authentik's own port, which serves no metrics (R84j). The collector keeps only the series the dashboard and alerts use, and only known labels: nothing that can hold a username, an email address or an IP address (P1, R70). An **Authentik** dashboard shows whether the server and worker are up, sign-ins that worked and failed (by reason, R89b), accounts locked, its errors, requests by status, server errors and the slowest requests by view, flows started, worker tasks (run, failed, retried, given up) and the tasks that failed, the queue, and database connections and errors. Three alert rules, through the same contact point as the others: **Authentik down** (a part can't be scraped for a minute; one alert per part), **Failed sign-ins** (more than 10 in 5 minutes; the threshold is a setting) and **Authentik tasks failing** (any in the last 5 minutes). Authentik's own container logs aren't collected: that would give the collector the Docker socket (root on the host), and Authentik's lines carry usernames, addresses and IPs. The docs say what an install that already runs the stack does to add it, and how to turn it off.
- **R89b. Sign-ins and Authentik's errors, counted.** Authentik's metrics have no sign-in counts, so R52's metrics add them from Authentik's event log, through the locked-accounts role (R84i), which may call a second function and still reads nothing: how many sign-ins worked, how many failed by where they failed (the password, the second factor, other), and Authentik's errors by kind (its exceptions, failed worker tasks, configuration errors, failing policies and property mappings), each over the last 5 minutes, every kind every time. Only counts leave the database: never a username, an address or an event's text (P1).

### 7.28 Installable on a phone (owner, 2026-11-17)
The owner: "do the installable part, hold off on notifications"; "the PWA must work on Android as well as iPhone, with Android an equal target". No notifications: see section 4.
- **R90. Installable.** The browser app can be installed on the home screen of an Android phone and an iPhone alike (and on a desktop), and then opens full screen (standalone), without the browser's bar. It has a web app manifest, `/manifest.webmanifest`, that loads with no session, as the favicon does (R82e): name and short name "PagerArchive", ID, start URL and scope `/`, and icons made from the favicon (R82e) at 192 and 512 pixels, both plain and **maskable** (the green to every edge, the pager inside the middle 80% a launcher's mask always keeps). Its colours are Harbour's tokens (R82c): the top bar's (`--surface`) for the title and status bar, and the page's (`--bg`) for the splash screen. A manifest holds one of each, so they're the light theme's; on a dark screen the page's theme-color lines give the dark one, and once it has started the app's title and status bar follow the look and theme it's shown in. iPhone's own tags show it full screen under the name "PagerArchive", with a 180-pixel touch icon that has the green to every edge for iOS to round. On Android, Chrome's install criteria are met (HTTPS, the manifest with its 192, 512 and maskable icons, and a service worker that handles fetches), so Chrome offers to **install** it as an app, not only to add a shortcut to the home screen. Installing needs the deployment's HTTPS (section 5).
- **R90a. The service worker keeps the app shell, and nothing else** (P1). It keeps the build's own files (its JavaScript and CSS, each named by its content), the icons, the manifest and the offline page, in one cache per build, and never anything else: no API answer, page text, search or search result, map tile, map glyph, the app's page itself, or anything about the person. A request for anything that isn't a shell file isn't touched: it goes to the network as if there were no service worker. Every navigation goes to the network; when the network can't be reached, a small **"You're offline"** page says so, in Harbour's look, with nothing from the archive and a "Try again" link. Signing in and out (`/auth/`) are left to the browser. The page's Content-Security-Policy isn't loosened for it.
- **R90b. Releases reach an installed app.** Upgrading the server (R84a) is all it takes. A release's service worker replaces the previous one's at the app's next navigation after the upgrade (the browser checks the worker then, and the server sends it with `no-cache`), takes over at once and deletes the earlier build's cache; the app's page always comes from the network, so it's the new release's. An app left open across a release finds out when it's brought back to the front, or within the hour, and loads the next page opened in it whole, with the new release's code.
- **R90c. Signing in and out when installed.** Sign-in and sign-out work in the installed app on Android and on iPhone. Authentik is on its own host, so its pages open over the app (a Chrome Custom Tab, or Chrome's in-app view, on Android; on iPhone, the app's own browser view) and sign-in comes back to the app, signed in, at the page asked for (R40a). Signing out ends the app's session and the person's Authentik session, as in a browser (R40b), and ends on the app's own sign-in page, saying they've signed out, so going back into the app asks them to sign in again. An app installed on an iPhone keeps its own cookies, apart from Safari's, so it's signed in on its own; the docs say so.

### 7.29 Long-running work (owner, 2026-11-18)
The owner: "for any process, data migrations, reparsing, etc that can take more than 30 minutes, the process should be observable (in Grafana stack), restartable, resumable pauseable and stoppable." On 2026-11-17 and 18 a profile change re-parsed about 3.2 million pages at about 1,400 a minute, for about a day and a half, with no progress shown; a restart part-way (a release, say) would have lost it (ADR 0042).
- **R91. Long jobs.** A process that could take more than **30 minutes** on a production-sized archive (R33b's 10 years at 1,250 pages a day: A75's 4,562,500 pages) is a **long job**, and must be:
  - **Observable.** The example monitoring stack (R76) shows whether it's running, how much it has done of its total, its rate and its estimated finish. It logs a start line (why it started, and how much it has to do), progress lines at a steady interval, and a finish line with how long it took. Counts only (P1-P3): never a page's text, capcode, address or locality.
  - **Restartable.** An admin can run it again from the beginning on demand.
  - **Resumable.** After a crash, a restart of the app or an upgrade, it carries on from where it got to, with its progress kept in the database, not from the start.
  - **Pauseable.** An admin can pause it and later carry on without losing progress.
  - **Stoppable.** An admin can cancel it, and the data stays consistent: each unit of work (a page, a batch) is done or not done, never half done.
- **R91a. Migrations stay quick.** A migration run when the API starts (R84a) makes only changes that are quick at that size: a rename, or adding a column or an index that is quick to add (an index built `CONCURRENTLY`, as the search index was: 132 s on a spinning disk, ADR 0017). A change that rewrites or backfills many rows runs after the start, in the background, as a long job under R91.
- **R91b. What it governs, and where each stands** (2026-11-18; the audit, with times, is in ADR 0042). Re-parsing and retroactive redaction meet all of R91. Each of the others is brought up to it when it's next worked on, and anything new that could pass 30 minutes is built to it.
  - **Re-parsing** (R23a, with its large-event rebuild, R87f): meets R91 (2026-11-18). Observable (R23b); restartable, resumable, pauseable and stoppable (R23c, ADR 0043).
  - **The import** (R83): its progress is on the command's own output, not in Grafana. Running the file again finishes it (R83c), but nothing carries on by itself. It can't be paused, and only restarting the API stops it (each batch is whole).
  - **Retroactive redaction** (P1, in the nightly run, R45): meets R91 (2026-11-18). Restartable, resumable, pauseable, stoppable and observable (R45a, ADR 0044), and each changed page's new text and its re-parse are one unit (ADR 0042's note 3).
  - **Report counts** (R38a): counting every job at once takes about 8 minutes at that size (ADR 0031), under the rule; but after an import or a re-parse of every page, the queue of jobs to count again holds every job, over an hour's counting. Resumable (the queue is in the database); the reports say their numbers are incomplete, and Grafana doesn't.
  - **Backfills**: derived localities (R24) and each layer's areas (R88a). Logged, with a percent, every 30 seconds, and resumed after a restart; not in Grafana's metrics, and not restartable, pauseable or stoppable by an admin.
  - **Retention** (R45): the first nightly run after the period is shortened (R46) may delete millions of pages. Each batch is whole and the next run carries on; only the nightly run's finish line.

## 8. Constraints

| Constraint | Because |
|---|---|
| Docker Compose on a home Linux server; API and frontend may be separate containers | Simple installs and upgrades for self-hosters |
| All dependencies inside images | Install and maintenance stay easy |
| Linux only. **Server** images (API, frontend, database) for **amd64 only**; **client** images for **amd64 and arm64** | Servers are x86 PCs, so official amd64 images (e.g. PostGIS) can be used; receivers may be Raspberry Pis |
| **Resource budget:** the app's containers (API, frontend, PostgreSQL; Authentik excluded) ≤ **1 GB RAM** total in steady state; API ≤ **256 MB** with 20 viewers at 1,500 pages/day; idle CPU < 5% of one core | Target host: an old small-form-factor PC (e.g. 15 GB RAM, spinning HDD) shared with other self-hosted apps |
| **PostgreSQL + PostGIS**; **no separate message queue** | Best fit for map data and search; ~1 page/minute doesn't justify a queue |
| **Authentik** for identity | Invitations, email codes and domain rules out of the box |
| Profiles in **JSON**, not YAML | Not whitespace-sensitive; easy to auto-format and validate |
| Geocoding only against a **local** address dataset | Public geocoders are rate-limited, often restrict automated use, and would receive incident addresses |
| **No paid services** | Hobby-scale self-hosting |
| Language and frameworks: chosen in an ADR (see "How to use") against these constraints | Delegated by the owner |
| CI on **GitHub Actions**; multi-arch images published to **GHCR** | Free for public repos |
| Accessibility: **WCAG 2.1 AA** | Usable by everyone, including on phones in poor light |
| Runs behind an **external reverse proxy**; the compose file doesn't include one | Self-hosters already run one (the owner uses linuxserver/swag) |
| Licence: **MIT** | Open source |
| The repo names **no real agency, network or other project**; test data uses made-up formats and addresses | Generic tool; privacy (P1) |

## 9. Acceptance checks

All checks use the **example profile** and the **standard test fixture** (section 10) unless stated. "An empty database" means no messages; the fixture's aliases and template are present. Capcodes, addresses and phone numbers are made up.

- **A1. Every call sign's copy, one job.** **Given** an empty database, **when** a client posts `@@EX0000004 HSF1 SMOKE FROM SHED @ 3 FICTION ST, MADEUPTON #STN<n>` on capcodes `0100001`…`0100004` (with `<n>` = 1…4), **then** 4 messages are stored, each with its own call sign, **and** the job view shows 1 job with 4 messages.
- **A2. ## 11. End-to-end verification

On a clean Linux host with Docker:
1. `docker compose up -d` starts the whole stack (including Authentik) from the documented `.env.example`, with the example profile mounted.

4. All acceptance checks A1–A15 and every golden row (network and agency) pass in CI.
5. Evidence is provided: commands run and their output.

### 12.1 Releases (owner, 2026-11-01; revised 2026-11-12)
- **Merge freely, release deliberately** (owner, 2026-11-12). A merge into main runs every check and, once they pass, publishes the images tagged `main` and `sha-<commit>` only: no tag, no GitHub release, no version. A build that isn't a release reports `<next>-dev+<commit>` as its version (such as `1.7.6-dev+3f2c1ab`): the version a release of that commit would get, marked as not one. Branches don't set a version: `VERSION` in the repository says `0.0.0-dev`, and CI fails a branch that changes it (ADR 0024).
- **A release is cut by the Release workflow**: every Saturday (18:17 UTC on Friday), ahead of the owner's weekly upgrade; whenever the owner presses "Release now"; and when a security update (a pull request labelled `security`, from Renovate's vulnerability alerts) merges: 30 minutes after it (owner, 2026-11-12, raised from 15), and a second security merge within those 30 minutes starts the wait again, so security updates that merge close together go out as one release (owner, 2026-11-12; ADR 0024). It releases main's newest commit, and only if main changed since the previous release in something other than documentation (what CI checks nothing for: `SPEC.md`, `docs/**` and other Markdown); otherwise it says "nothing to release". Two releases never run at once.
- **The version is worked out from the previous release** (the newest `v*` tag in the commit's history; owner, 2026-11-14). It's the **next minor version** if, since that release, any of these happened: a file a deployment downloads changed (`compose.yaml` other than our own image's tag, or the configuration archive's files); a database migration was added; or a pull request labelled `feature` merged (`.github/release.yml` says when to use the label). Otherwise it's the **next patch**: fixes, CI, documentation, dependency and security updates. There's no major version except by hand. A deployment's `compose.yaml` names our image by `MAJOR.MINOR`, so `docker compose pull` gets patches only, and every minor release needs its own `compose.yaml` and archive downloaded (docs/deploy.md). Before a release, the next version and the rules that fired show in every build of main (`pagerarchive version` reports `<next>-dev+<commit>`) and in the Release workflow's notice, in a dry run too (ADR 0024). It's written into the build, never committed: the release's tag holds it.
- The release runs every check on the commit it releases, then tags it `v<version>`, creates the GitHub release with the client binaries and their checksums and GitHub's generated notes, publishes the images tagged with the version, its `MAJOR.MINOR` (such as `0.12`) and `latest`, attaches the files a deployment downloads (R84), makes the release the latest, and publishes the PowerShell module if it changed since the previous release (R63). It attests the client binaries, the attached files and both images with GitHub artifact attestations, the images' attestations pushed to GHCR beside them, so `gh attestation verify <file or oci://image> --repo RIKIKU/PagerArchive` checks a download (owner, 2026-11-13; ADR 0024). A dry run attests nothing.
- Nothing is released by hand: v0.12.0 is the last tag made by hand. A dry run of the Release workflow does everything but tag and publish.
- If part of a release fails to publish, that job is re-run; a version is never reused.
- **What CI runs** (owner, 2026-11-12; ADR 0025). A pull request runs only the checks its changed files can affect, and a change of documentation alone runs none, so "All checks passed" reports at once; and a file CI doesn't know, CI's own files or a shared test fixture runs every check; main (unless only documentation changed) and every release run every check, so nothing is released that a check was skipped for. A failure that isn't the change's is retried: network steps try again by themselves, a failed test runs once more in its job, and a failed run of a pull request or main has its failed jobs re-run once, unless what failed is always the change's or is a security or privacy finding. Whatever passed only on a retry is reported as flaky on the run, never hidden. A check's times on the shared runners (A75's, and A76's import) are reported in a gate, never failed; a weekly benchmark fails them at twice their limits, a big slowdown (owner, 2026-11-18; ADR 0046). CI also reports the known vulnerabilities the Go code can reach (govulncheck), and fails for one it calls that has a fix.

## 14. Accepted defaults

Settled by the owner after the second cold read (2026-10-09):
- Priority markers are case-sensitive and exactly 2 characters. With no known marker (priority `null`), the full text is shown unchanged.
- An Emergency page on a profiled capcode that matches no format, and any `null`-priority page that matches none, is `parse_failed`.
- Extracted values are trimmed, and empty matches become `null`. Extra fields are strings or lists of strings.
- Each redaction match is replaced by one `REDACTED`. Dedup runs on redacted text. A redaction rule that alters one of its own must-not-match examples stops the server at startup.
- If retroactive redaction removes the text a field came from, the message is re-parsed and may leave its job.
- The POCSAG function code and baud rate are stored but not used. The client accepts `Alpha:` and `Numeric:` lines, drops other lines silently, and trims only multimon's separator.
- Control tokens such as `<NUL>` are removed; `<LF>`/`<CR>` become a space.
- The dedup window is symmetric: a late copy whose receive time is within 10 s of the first copy, either side, is the same transmission, and sent time becomes the earliest.
- The client drops the oldest buffered pages when its buffer is full, and rejects receive times more than 60 s in the future (logged without page text). The client ID comes from configuration (see R14).
- Profiles are read at start-up. A change is detected by comparing file hashes, which then triggers re-parsing (R23a); the hashes leave out what changes nothing a page says (R23a, R88d). A template pointing at a missing agency profile makes its pages text-only and is reported to admins.
- Re-parsing runs as soon as a change is detected. Retroactive redaction waits for the nightly run.
- The message list is sorted by sent time, newest first, with infinite scroll. Late buffered pages appear in their sorted position.
- Text search is case-insensitive substring search across the text and extra fields, with every term required (R33a's text terms).
- The map shows the last 24 hours by default, follows the active filters, and has one point per located message. A tile server, if one is used, counts toward the resource budget.
- No house number: the street's centroid is used and marked approximate. Grid references resolve to the centre of the 100 m cell. Address matching normalises common abbreviations (ST/STREET) but isn't fuzzy.
- The example address dataset places MADEUPTON at a neutral location. No real map tiles are needed for tests.
- A template still used by aliases can't be deleted (R64). Icons are images stored with the template (R65).
- Unmapped report codes are listed one row per raw code inside "Other". Report date ranges are inclusive, in the deployment time zone. Reports are per capcode or per alias (R38).
- Jobs left with no messages, per-client receive records and geocode results are deleted along with their messages.
- Only client images are multi-arch; server images are amd64 only (owner correction, 2026-10-09). WCAG 2.1 AA is checked with automated accessibility tests plus a manual checklist.
- A12 and A13 use a controllable clock and a test-only trigger for the nightly job. The §11 "clean host" is a GitHub Actions Ubuntu runner, with a local mail catcher (e.g. Mailpit) and `example.test` as the allowed domain.
- For A15, "20 viewers" means 20 live-update connections, and the page stream is generated from the example formats. The test runs once by hand with evidence, plus a short version in CI.
