**Status:** Draft 0.2 (2026-10-09), not yet approved for implementation
**Owner:** Kyle

## How to use this spec (implementing agent: read first)

1. Read this whole document and `CLAUDE.md` before doing anything.
2. **Principles (section 1) override every other section.** Where two principles conflict, the lower-numbered one wins.
3. **`OPEN` means undecided.** Don't guess. Stop and ask the owner. Work that doesn't depend on an OPEN item can continue.
4. **Before writing any code**, write `docs/adr/0001-technology-stack.md` recommending the stack against the constraints in section 8, and wait for the owner to approve it.
5. Golden tables (`profiles/**/golden-*.json`, in this repo and in any private profile repo) are **owned by the owner**. You may propose new rows, but never change an expected value to make a test pass.
6. "Done" means every acceptance check in section 9 passes, plus the end-to-end verification in section 11, with evidence (commands run and their output).
7. **Implementer discretion.** Where this spec is silent, choose the simplest option consistent with the principles, constraints and requirements, and record it in an ADR (`docs/adr/`). Ask the owner only when the choice changes what users see, what data is kept, privacy or security. **UI presentation details** (date and time formats, layouts, icon sets, the design of admin screens) are the implementer's choice within the requirements. The defaults in section 14 apply.
8. **ADR approval:** an ADR is approved when its status reads `Status: Accepted`, set by the owner or by Claude at the owner's explicit instruction, and committed.
9. **Repos:** this repo is `github.com/RIKIKU/PagerArchive`. The owner's private profile repo is checked out next to it at `../PagerArchive-profiles` on the build machine.
10. **Golden row status:** rows marked `"status": "proposed"` run in CI and are reported, but don't fail the build until the owner changes them to `"confirmed"`.

## 1. Principles

- **P1. Sensitive personal details are never stored.** Details matched by the network profile's redaction rules (for example patient age and gender, phone numbers, access codes) are removed before anything is stored, logged or shown. Retroactive redaction also covers derived data (dedup hashes, parsed fields, job links, search indexes), followed by routine database vacuuming. Database write-ahead logs and backups are out of scope. **No server-side log line, and no client error or diagnostic output, ever contains page text** (application, web server, reverse proxy, database or error logs, and OpenTelemetry traces, metrics and logs: R70). When a redaction rule is added or changed, it's applied to already-stored messages at the next nightly run. The one exception is the client's optional console output (R13a), which is never written to a file by the client.
- **P2. The full message is always shown.** Every page is stored and displayed in full, after the removals in P1. Parsed fields are extra metadata for search, filters, grouping, the map and reports. They never replace or hide the text. A parse failure, a missing alias or a wrong template can make a page harder to find, but never harder to read.
- **P3. The parser extracts; the display interprets.** Parsed fields hold the literal text from the page. Turning codes into labels is a separate display step driven by profiles.

## 2. Problem and users

Many emergency and organisational paging networks broadcast **POCSAG** pages that can be received with an inexpensive RTL-SDR dongle and decoded with `multimon-ng`. People who follow a network want to archive those pages, browse them live, search them, see them on a map, and look up what a given pager group has received.

PagerArchive is a self-hosted, resource-light archive for any POCSAG network. Network-specific knowledge (page formats, which capcodes to ignore, what must be redacted, how event types group into categories) lives in **configuration profiles**, not in code.

PagerArchive is for **people interested in what's happening on their network. It is not a tool for harassment.**

## 3. Glossary

| Term | Meaning |
|---|---|
| Page / message | One POCSAG transmission to one capcode |
| Capcode | The pager address a page was sent to, stored zero-padded to 7 digits (`0579064`) |
| Client / receiver | A machine with an RTL-SDR dongle that decodes pages and posts them to the server |
| Priority marker | The first 2 characters of a page's text, which some networks use to signal its priority (the receiving pager typically doesn't display them). Defined by the network profile |
| Priority | Emergency, Non-emergency, Admin, or `null`, derived from the priority marker |
| Network profile | One JSON file per deployment: rules that apply to every page on the network (section 6.3) |
| Agency profile | A JSON file describing one agency's page formats (section 6.4). Attached to alias templates |
| Alias | A human-readable name for a capcode or capcode pattern, linked to a template |
| Template | Shared alias settings: agency name, icon, colour, and optionally an agency profile |
| Job number | An identifier, extracted by a profile, that links pages about the same incident |
| Group | The pager group a copy was sent to, when the page names it (often a short code at the end) |
| Heartbeat | A periodic page the network sends to show it's alive. Its capcodes are listed in the network profile |
| Golden table | A JSON file of real-format raw lines and the exact fields they must parse to |
| Album | A named list of messages one user keeps for later (R82), with an optional description and a note on each message (R82f). Only its creator sees it |
| Look | A named style for the whole UI: colours, type, spacing, corners and how priority is shown, each in light and dark (R82c). Harbour is the default |

## 4. Scope

### In scope for v1
Receiving clients, ingest and redaction, profile-driven parsing, job grouping, map locations, aliases and templates, the browser UI with live updates and multi-criteria search, a per-group report, client liveness, invite-only accounts and retention.

### Out of scope
- **Incident state or resource tracking.** The app never infers or shows whether an incident is active, cancelled or finished, or where resources are. Pages carry too little information for that. Follow-up pages (cancellations, updates) are stored and grouped like any other page and never interpreted.
- **Operational alerting** (owner, 2026-10-16). PagerArchive is not critical infrastructure and must not replace issued pagers or an agency's official alerting. Integrations are a convenience: delivery is best-effort, and the app doesn't add features whose purpose is guaranteed alerting (e.g. repeat-until-acknowledged alarms, delivery receipts, escalation).
- **A native mobile app.** The browser UI must work well on phones instead.
- **Automatic client updates** (wanted later). v1 publishes multi-arch images and documents manual updates.
- **Managing clients in the browser** (wanted later, owner 2026-10-13). Until then they are changed by CLI. Aliases are managed in the browser from M6 (section 7.12, owner 2026-10-16), and templates from M10 (section 7.14, owner 2026-10-20).
- **API keys** (owner, 2026-10-20). Command-line work signs in as a person (R60). Unattended jobs, if ever wanted, would be a worker inside PagerArchive, not a script.
- **PowerShell access for users** (wanted later, owner 2026-10-20). Users would request access and an admin would grant it. The module would then work for them with their own role's permissions (R60).
- **Writing an identity provider.**
- **Linking several email addresses to one person.** Accepted risk: one person may hold more than one account. Invite attribution and invite-tree deactivation (section 7.9) are the remedy.
- **Public geocoding services** (section 8).
- **Code plugins.** Network knowledge is configuration (JSON profiles), not code.
- **System monitoring and alerting** (uptime, performance, a receiver going quiet). The app exposes metrics (R52) and telemetry (section 7.16) for an external stack to alert on, such as the example Grafana stack in `deploy/` (R76). The app itself sends no system alerts. Forwarding **pages** to users' own systems is in scope (section 7.11).
- **Anti-harassment features beyond invite-only access** (for example an audit log of searches) in v1.

## 5. Architecture (decided)

```
RTL-SDR → rtl_fm → multimon-ng → [client] ──HTTPS──▶ [server API] ──▶ PostgreSQL + PostGIS
                                                    ▲        │    ▲
                                       Authentik ───┘        │    └── network + agency profiles (JSON, mounted read-only)
                                                             └── live updates ──▶ browser UI
```

Many clients post to one server. Each client records its own receive time. The server sits behind the deployment's **own reverse proxy** (which handles TLS) and is reachable by remote clients. The docs include a working example configuration for a common nginx-based proxy (e.g. linuxserver/swag), including whatever live updates need. Profiles are files mounted into the server container. They aren't stored in the database, so a deployment can keep them in its own (private) repository.

## 6. Profiles

### 6.1 Format
- **R1.** Profiles are **JSON** files, validated against JSON Schemas shipped in the repo. An invalid profile stops the server from starting, with an error naming the file, path and problem.
- **R2.** The repo ships a complete **example profile** for a made-up network (`profiles/example/`), with golden tables. It's the documentation and the default test fixture. The implementer writes the example network and agency profile JSON, the JSON Schemas and a small example address dataset; they must pass the owner's example golden tables.

### 6.2 How a page finds its rules
- **R3.** capcode → alias (section 7.5) → template → agency profile. The agency profile's **formats are tried in order**. The first format that matches parses the page.
- **R4.** If the capcode has no alias, its template has no agency profile, or no format matches, the page is still stored and shown in full (P2). No format matching → flagged `parse_failed`. No alias or no agency profile → **text only**, not flagged. There is no default agency profile. Network-level rules (priority, redaction, job number patterns) still apply to every page.

### 6.3 Network profile (one per deployment)
- **R5.** Defines:
  - **priority markers**: which 2-character prefixes mean Emergency, Non-emergency and Admin
  - **ignored capcodes**: capcodes or ranges whose pages are dropped and never stored (network housekeeping traffic)
  - **heartbeat capcodes** (kept and shown; used for liveness)
  - **redaction rules**: ordered patterns, each with a name, replaced by `REDACTED` (P1), plus **must-not-match examples** that must survive unchanged
  - **event categories**: a table mapping event-type codes to report categories, with "Other" for unmapped codes
  - **address dataset**: the local open-data file used for geocoding, and how grid references are interpreted (section 7.4)
  - **job number patterns** that apply to every agency (e.g. a prefix letter plus digits)
  - **deployment code pattern** (optional; owner, 2026-11-12): a code in a page that opens a large event (R87), such as one naming a pre-formed group of appliances sent together; with no pattern, only a job's number of Emergency pages opens events. The key stays `deployment_code_pattern` (a machine name), but the app never calls these codes "deployment codes" and never counts or lists them (owner, 2026-11-13)
- **R6.** The network profile has its own golden table covering priority markers, ignored capcodes and every redaction rule, including the must-not-match examples.

### 6.4 Agency profile (attached to templates)
- **R7.** Defines an ordered list of **formats**. Each format has a name, optionally the **priorities it applies to**, a match rule and extraction rules for fields. A format may extract nothing ("text-only format", e.g. freeform admin pages), which counts as a match, not a failure. Formats run on the redacted text with the priority marker removed. Optionally, **field values that open a large event** (R87; owner, 2026-11-14): one of the agency's text fields and the values of it that do, each listed, such as an alarm level high enough to mean something big (`large_event_fields`).
- **R8.** Standard fields that core features rely on: `job_number` (grouping), `event_type` (reports), `description`, `address`, `locality` and `grid_ref` (map), `units` (list: the appliances a page names), `group`. A format may also define **extra fields** with any name; they're stored, searchable and shown. Fields not present in a page are `null`. Values are literal (P3). The app calls `units` **Appliances** wherever people see it (a message's detail, the PowerShell module's display and help, the docs); its machine name stays `units` in profiles, golden tables, schemas, the API's JSON and the database, so existing and private profiles keep working (owner, 2026-11-13).
- **R9.** Optional **label tables** map codes to display labels (e.g. an event-type code to a readable name).
- **R10.** Each agency profile ships a **golden table**: raw lines and their exact expected fields, one row per format variant. Every row must pass in CI. The repo ships a `validate-profile` command that runs any profile's golden tables, so private profile repos can test themselves. `validate-profile` runs without a database and pairs agency tables with a named network profile.
- **R11.** **Decided** (ADR 0001, accepted by the owner 2026-10-09): RE2 regular expressions with named groups, plus `address_split` anchored on the address dataset's street list. Original question: the extraction language. The ADR proposes one that can express ordered alternatives and optional segments. Regular expressions with named groups are the obvious candidate, but the hardest real format has unmarked boundaries between a description, an optional premises name and an address, so the ADR must show it can handle the private profile's golden rows. Those can't be copied into this repo: build sessions run on the owner's machine with the private profile repo checked out alongside (path given by the owner), and the ADR may describe its rows only in general terms.

## 7. Requirements

### 7.1 Clients
- **R12.** The client reads `multimon-ng` output lines on stdin, e.g. `POCSAG512: Address:  579064  Function: 0  Alpha:   <text>`, and posts each page to the server with: capcode (zero-padded to 7 digits), raw text, receive time (UTC) and client ID. POCSAG at 512, 1200 and 2400 baud. Numeric pages are stored as text. Tone-only pages (no text) are ignored. The client turns decoder output into an internal record (capcode, function code, baud rate, text, receive time) through a **decoder adapter**; v1 ships only the `multimon-ng` adapter, so other decoders can be added later without redesign.
- **R13.** Clients run as a Docker container with the USB dongle mapped through, or natively on a Raspberry Pi (arm64). The client container **runs the radio pipeline itself** (`rtl_fm` and `multimon-ng` in v1, configured by settings: frequency, gain, PPM, baud rates); reading lines from stdin stays supported. Clients must keep their clocks in sync with NTP.
- **R13a.** The client may print decoded page text to its console (stdout) for troubleshooting. This is **off by default** (setting `PRINT_PAGES=true`). The client never writes page text to a file. The docs warn that Docker's default logging driver stores container output on disk, and show how to limit or disable that.
- **R14.** Each client authenticates with **its own API key**, issued and revoked by an admin; the key determines the client ID (owner decision, 2026-10-09; details in ADR 0002).
- **R15.** When the server is unreachable, the client buffers pages **in memory only** (never on disk, because client-side text isn't redacted) and retries with backoff, keeping the original receive times. The buffer is capped (implementer's choice), and its contents are lost if the client restarts.

### 7.2 Ingest (in this order, before storing)
- **R16.** Pages to the network profile's **ignored capcodes** are dropped. They still update the receiving client's last-seen time (no text is recorded).
- **R17.** Control tokens printed by `multimon-ng` (e.g. `<NUL>`) are removed.
- **R18.** The network profile's **redaction rules** are applied (P1).
- **R19.** **Deduplication:** the key is a hash of capcode + cleaned text. A page whose key was first stored no more than **10 seconds** earlier (by receive time, measured from the first copy) is the same transmission, whether it comes from another client or the same one (networks often repeat pages deliberately). It isn't stored again, but the extra client's receive time is recorded.
- **R20.** Every capcode's copy is stored as its own message, even when the text is otherwise identical.
- **R21.** A message's **sent time** is the earliest receive time among the clients that heard it.
- **R22.** The **raw text** (after R17–R18) is stored, including the priority marker. Priority comes from the marker (R5).

### 7.3 Job grouping
- **R23.** Messages with the same job number are grouped into one job, on a best-effort basis (one incident may have several job numbers; that's acceptable). **Any page containing a job number joins that job**, including follow-ups and admin pages that mention it. Pages without a job number are never grouped. If a format extracts a job number, that one is used; otherwise the first match of the network job pattern is written to `job_number`. Job numbers are grouped for all time (no time window).
- **R23a.** When an alias, template or profile changes, affected messages are **re-parsed (and re-geocoded) in the background**. Parsed fields are stored. Aliases are always shown as they are *now*, not as they were when a page arrived. Marking an alias ignored or not re-parses its pages too, and a re-parse rebuilds the large events around the pages it touched (R87f; owner, 2026-11-14).

### 7.4 Location
- **R24.** The address (with its locality) is geocoded **locally** against the address dataset named in the network profile. If a profile doesn't extract `locality` separately, the geocoder matches the end of the address against the dataset's localities. The dataset's attribution is shown.
- **R25.** If the address can't be geocoded and the page has a grid reference, the grid reference is resolved as the network profile describes. For the case that motivated this: a 6-digit MGRS easting/northing without zone or 100 km square, completed from the zone and square containing the page's locality, giving a point accurate to 100 m.
- **R26.** If both exist and are more than **1 km** apart (owner, 2026-10-13), the message is flagged `location_mismatch` (admins only, R35c). When the address has no house number and is placed at its street's centroid (section 14), the distance is from the grid reference's point to the **nearest address point on that street in that locality**, so a long road isn't flagged just for being long (owner, 2026-10-13).

### 7.5 Aliases and templates
- **R27.** An alias maps a capcode or capcode pattern to a name and a template. Patterns use `%` (any run of characters) and `_` (one character). Precedence: an exact capcode wins, then fewer wildcards; patterns starting with a wildcard come last. An alias can be marked **ignored**: its pages are still stored and shown in full (P2), but hidden from the default message list and live updates; a search filter shows them. They never count towards large events (R87; owner, 2026-11-14). Dropping pages stays the network profile's job (R16). (Owner decision, 2026-10-10.)
- **R27a.** Each capcode or pattern has **at most one alias** (owner, 2026-10-11). Capcodes are compared after zero-padding to 7 digits (`240241` and `0240241` are the same); patterns with wildcards are compared as written. The database enforces this with a unique constraint on the normalised value, not just the UI or CLI. Creating an alias for a capcode that already has one is rejected, with a message naming the existing alias and suggesting an edit instead. A wildcard pattern that overlaps an exact capcode (`0100%` and `0100001`) is not a duplicate; precedence (R27) decides. The same alias **name** on different capcodes is allowed (a brigade can have several pagers), but the import report lists repeated names for checking. The import (R30) never silently picks between CSV rows for the same capcode. If rows for the same capcode differ, the import stops, changes nothing and lists them, and the admin fixes the data and imports again. From M8, the fix happens in the PowerShell pipeline or the CSV, and there's no overrides file (owner, 2026-10-20). Rows identical in every imported field (name, agency, colour, ignore) are not a conflict: they are squashed automatically, keeping the first. By default an import doesn't change aliases that already exist: it adds new ones and reports how existing ones differ from the CSV, and applies those differences only with the update option (R58) (owner, 2026-10-11).
- **R28.** A **template** holds a name, agency name, icon (an image, R65), colour and optionally an agency profile. Aliases are **linked** to their template: editing the template updates every alias that uses it.
- **R29.** Templates enable parsing but never gate storage or display (P2).
- **R30.** Aliases can be **imported from a CSV file** in v1 (owner decision, 2026-10-10). The import creates one template per distinct agency name and attaches agency profiles from a mapping of agency name to profile name, which the admin supplies. From M8 the mapping is a hashtable, which can be loaded from a JSON file the deployment owns (R63). Unmapped agencies are text only. An ignore flag in the CSV marks the alias ignored (R27). The CSV's `icon` column (an icon name, as some older systems export) is accepted but ignored, because icons are images added to templates afterwards (R65). Export leaves it empty (owner, 2026-10-20).

### 7.6 Browser UI
- **R31.** The message list shows, for every message: the text **without the priority marker** (as a pager displays it), a priority badge, date and time, alias (or capcode), and group. On phone-width screens (375 px), date, time and alias stay visible with no horizontal scrolling.
- **R32.** **Live updates:** a new message appears in every open browser within **2 seconds** of a client posting it, with no refresh. Any mechanism is fine. A message that doesn't match a viewer's current filter isn't added to their list.
- **R33.** **Search** combines any of: text, capcode, alias, agency, group, priority, event category, job number, date range, and **"capcodes with no alias"**. The last one also lists each unknown capcode with its message count and last-seen time, so it can be identified and aliased. **Admins** can also filter by flag: `parse_failed`, `address_unsplit`, `location_mismatch`. (List confirmed by the owner, 2026-10-10.)
- **R33a. One search box** (owner, 2026-10-20; built with the UI redesign). The search criteria (R33) are typed into one box. The date range is chosen beside it (Dates, below).
  - **Filters and text:** a word that starts with a known key is a filter. The keys are `alias:`, `agency:`, `capcode:`, `group:`, `priority:`, `category:`, `job:`, `is:` (`unaliased`, `ignored`), `or:` (see Or, below) and, for admins only, `flag:`. Everything else is text search, including quoted text and words with any other colon. That way page text full of colons (`ADDR:`, `14:05`) still searches as text. A value with spaces is quoted (`alias:"Station 1"`).
  - **Text terms** (owner, 2026-11-02): the text is split into terms, and a page must contain **every** term, anywhere in its text or extra fields. Text in double quotes is one term, matched as typed: the same words in the same order (`"Check hoses"`). Each word outside quotes is a term of its own. So `"Check hoses" "Smoke"` finds pages holding both "Check hoses" and "Smoke", and `"Check hoses" smoke truck` pages holding all three. As for all text search, case is ignored and a term can be part of a longer word (section 14). A quote left open runs to the end of the box.
  - **Or:** a term written `or:` (a word, `or:fire`, or a quoted phrase, `or:"structure fire"`) is an alternative to all the other text terms together. A page matches if it holds every ordinary term, or any one `or:` term. So `"Smoke showing" or:fire` finds pages with "Smoke showing" or with "fire"; `"Smoke showing" or:fire or:alarm` any of the three; and `"Check hoses" "Smoke" or:fire` pages with both "Check hoses" and "Smoke", or with "fire". Filters still apply to every page listed: `alias:"Station 1" "Smoke showing" or:fire` lists only Station 1's pages. `or:` is a key (it's suggested and in the help, with no value suggestions), so page text that contains `or:` is searched by quoting it. The API applies the same rule to its text parameter, so the PowerShell module's text search does the same.
  - **Combining:** the same key more than once means any of those values; different keys must all match. The API accepts several values per filter. The PowerShell module's array parameters use the same thing (R63a).
  - **Partial values:** a typed `alias:`, `agency:`, `group:` or `category:` value matches every value containing it, ignoring case (`alias:hill` matches "Hillside North" and "Hillside South"). Picking a suggestion matches exactly that value. `capcode:` and `job:` match exactly, with capcodes zero-padded as in R27a.
  - **Suggestions** (owner, 2026-11-09; M21). Clicking into the box opens a list under it of every key, each with a few words; picking a key puts it in the box at the cursor (`alias:`), ready for its value. As a value is typed after a key, matching values are suggested for `alias:`, `agency:`, `group:`, `priority:`, `category:`, `is:` and `flag:`. There are none for `capcode:` or `job:`, which are too many to list and are only typed by someone who knows them (owner, 2026-10-20). A word typed **without a key** suggests, first, searching it as text (what Enter does), then the alias, agency, group and category values that contain it, with their key: typing `hill` suggests `alias:"Hillside North"`. Picking one replaces the word with the filter, quoted when the value has a space, and matches exactly that value. Plain words never suggest capcodes or job numbers.
  - **Help** (owner, 2026-11-09; M21). A help control lists every key with an example and explains text terms, quotes and `or:`. It's an icon only, with the accessible name "Search help" and a tooltip, placed straight after the search box, between it and the dates.
  - **Clear all** (owner, 2026-11-09; M21). One control resets the box and both dates and shows the plain message list; it's shown only when something is set. It's an icon only, with the accessible name "Clear all" and a tooltip. Clearing is a search change like any other, kept in the page's address, so Back restores it.
  - **Dates** (owner, 2026-11-09; M21). A calendar icon opens one month's calendar. The first day clicked is From, the second To; the days between are joined by a bar, previewed as the pointer moves. A second day before the first swaps them, the same day twice is one day, and a third click starts again. Whole days, as before. The chosen range shows as text beside the icon. Keyboard: arrow keys move the day, Enter picks, Escape closes. The capcode report's dates are the same control. The calendar's month-and-year title is a button (owner, 2026-11-12): it switches to that year's 12 months, with arrows that move a year, and the year there switches to a grid of years. Picking a year shows its months, and picking a month its days. Years with no pages (before the archive's first page or after its last) and months after this one are greyed out and can't be picked. The keys and accessible names work in the months and the years as in the days.
  - **Accessibility:** the box follows the ARIA combobox pattern. Arrow keys move through suggestions, Enter picks one, Escape closes the list, and the number of suggestions is announced.
  - **Where it applies:** the search is kept in the page's address (back button, bookmarks, shared links). The map, the alias and capcode views and the job view follow it. Its look is part of the redesign.
- **R33b. Search speed** (owner, 2026-11-02). With 10 years of pages at 1,250 a day (the default retention, R45; owner, 2026-11-02, sized to the archive being migrated), a search shows its first results within **1 second**. That includes a search that finds little or nothing, a search with several terms or `or:` terms (R33a), and a term found only in an extra field. This holds within the resource budget (section 8).
- **R34.** A **job view** shows all messages for a job number.
- **R35.** A **map** shows located messages, using **self-hosted map tiles** (e.g. an OpenStreetMap extract), so no third party sees what users view.
- **R35a.** **Times** are stored in UTC and shown in the deployment's time zone (setting `TZ`, e.g. `Australia/Melbourne`), with en-AU style dates. English only. Report days and the retention cut-off use the same time zone. (Showing times in each browser's own time zone may come later.)
- **R35b.** Heartbeat pages are shown with a **heartbeat badge** and are excluded from reports. They appear in the default message list.
- **R35c.** A **message detail view** shows all parsed and extra fields and every client's receive time. The `parse_failed`, `location_mismatch` and `address_unsplit` flags are shown **to admins only**. (`address_unsplit`: a format matched, but no street from the address dataset ended the address text, so `address` is `null`; see ADR 0001.) If the message has a location, the detail view also shows a small map centred on it, using the same self-hosted tiles (R35). An approximate location (street only, no house number) is drawn as a ring, as on the main map. On phones the map comes below the message text, so the full text stays first (P2). A message with no location says so instead, with no empty map. The "Show on map" link stays. (owner, 2026-10-15)
- **R35d. Navigation from a message** (owner, 2026-10-12). Tapping a **message** (anywhere on
  its row except the links below) opens its **detail view** (R35c). Tapping the **alias**
  opens the **alias view** (R35e); if the capcode has no alias, tapping the capcode opens it.
  Tapping the **job number** opens the **job view** (R34). The whole row is the tap target.
- **R35e. Alias view** (owner, 2026-10-12). Shows the alias name, its capcode or pattern,
  agency, icon, colour and whether it's ignored, then the messages from the capcodes it
  covers, newest first, with live updates and the same filters as the main list. For a
  capcode with no alias: the capcode, its message count, and first and last seen (as in
  R33). From M6 it also shows, for a signed-in user, a way to request a change (R54); admins
  edit it directly (R53) and also see its history (R57).
- **R36.** Supports current Chrome, Firefox, Brave and Safari on desktop and mobile; dark and light mode; layout adapts to screen orientation.
- **R37.** **Per-user integrations** forward pages to a user's own systems: see section 7.11 (milestone M5).

### 7.7 Reports
- **R38.** A report shows, for a **capcode** or an **alias** and date range, the number of Emergency **messages** per **event category** (network profile, R5). Unmapped codes and parse failures are counted under "Other" (with the raw code shown where there is one). The alias or capcode is picked with the search box's suggestion control (R33a): typing part of an alias name or a capcode suggests them (owner, 2026-11-12). An alias's report counts every capcode it covers: for a pattern, each capcode that matches it and has no alias of its own (R27). One alias or capcode at a time. Picking an alias picks it by name, so aliases sharing that name (A19) are reported together. The report's address names what was picked (`?alias=…` or `?capcode=…`), so it can be bookmarked; addresses naming a capcode from before keep working.

### 7.8 Client liveness
- **R39.** A client is flagged **not receiving** after **30 minutes with no message of any kind**, heartbeats included. (Networks may only send heartbeats at certain hours, so missing heartbeats alone must not raise an alarm.) The flag is **shown on screen** and exposed as a metric (R52), so an external monitoring stack can alert on it. The app doesn't send system alerts itself. Client status is visible **to admins only** (client names may reveal where receivers are).

### 7.9 Accounts and access
- **R40.** Sign-in is handled by **Authentik** (self-hosted, in the same compose file) via **OIDC**. The app never handles passwords. Authentik runs on **its own subdomain**, shares the app's PostgreSQL container (its own database), and is configured automatically from **blueprints** shipped in the repo.
- **R41.** New users can only enrol with an **invitation** from an existing user **and** by verifying a code sent to an email address in one of the **allowed domains** (deployment setting `ALLOWED_EMAIL_DOMAINS`).
- **R42.** The app records **who invited whom**. Admins can deactivate any user, or a user **and everyone in their invite tree** (recursively).
- **R42a. Invite tree view** (owner, 2026-10-17). Each user's page in Administration shows their **invite tree** as an indented list: who invited them, and everyone they invited, recursively. Each person shows name, email, role, the date they joined, and whether they're deactivated. Deactivated people are greyed out, and the tree continues through them.
- **R42b. Preview before deactivating a tree** (owner, 2026-10-17). Deactivating a user and their tree first shows the tree with a tick beside everyone who will be deactivated, and totals ("12 people will be deactivated and 3 unused invitations cancelled"). The admin can **untick** anyone (which spares only that person) or use **"spare this branch"** (which unticks that person and everyone below them). Already-deactivated people and the last active admin (R44) can't be ticked. An optional **reason** can be entered. Confirming deactivates exactly the ticked people and cancels their unused invitations; spared people's invitations stay. If the tree changed since the preview (anyone joined, or anyone's status or trusted mark changed), confirming is **refused** and the updated preview is shown.
- **R42c. Trusted users** (owner, 2026-10-17). An admin can mark a user **trusted**, and remove the mark; who set it and when is recorded. Trusted users start **unticked** in every preview, though an admin can still tick one deliberately. The mark doesn't prevent deactivating that person on their own. Only admins see it.
- **R42d. Deactivation record** (owner, 2026-10-17). Each tree deactivation is recorded: who did it, when, the reason, who was deactivated and who was spared. Admins see the record on the affected users' pages. Spared people keep their recorded inviter.
- **R43.** A deactivated user can't be re-invited except by an admin. A non-admin who tries is told why: the person was deactivated and only an admin can re-invite them (owner, 2026-10-13).
- **R43a.** Invitations are created **in the app** (which records who invited whom, and creates them through Authentik's API) and are **single-use**, expiring after **7 days**. The inviter enters the invitee's email address, which must be in an allowed domain (admins included). The emailed link only works for that address. An invitation is **used up only when enrolment finishes** (the emailed code verified and the account made), never by opening the link (owner, 2026-11-08): mail providers' link scanners open links and run their pages before the invitee does, and that must neither use up nor spoil the invitation. A link opened but not finished still works until it expires, is cancelled or is used.
- **R43d. Resending an invitation** (owner, 2026-11-08). The inviter, or any admin, can **resend** an invitation that is waiting or expired, from the inviter's list of invitations (R43a) or, for admins, the user's page in Administration. Resending sends a new link to the same address and starts a new 7 days; the old link stops working. It is still the same invitation: the recorded inviter doesn't change, and it isn't a second pending invitation to that address. A resend follows the same rules as a new invitation (allowed domain, R43's re-invite block, and R43b and R43c's cancelling). A used or cancelled invitation can't be resent; the inviter invites again instead.
- **R43b.** Deactivation takes effect **immediately**: the user is disabled in Authentik and their live sessions and connections are closed. Admins can reactivate users one at a time (reactivating doesn't reactivate their invite tree). The re-invite block (R43) goes by email address. A deactivated user's unused invitations are cancelled (owner, 2026-10-13).
- **R43c.** Users can delete their own account. People they invited keep their accounts, credited to "deleted user". Their unused invitations are cancelled (owner, 2026-10-13).
- **R44. Roles and the first admin** (owner, 2026-10-12). Two roles: `user` and `admin`. Users browse, search and invite (R41). Admins can also manage aliases, templates, users, clients and retention, and see flags (R35c) and receiver status (R39). The deployment setting `INITIAL_ADMIN_EMAIL` names the first admin: **while no admin exists**, that address may enrol without an invitation, still verifying the emailed code, and is exempt from `ALLOWED_EMAIL_DOMAINS`; it becomes admin. While that set-up is available, a signed-out visitor is sent to the app's sign-in page, which offers it, rather than straight to the identity provider (owner, 2026-10-13). Once any admin exists, the setting is ignored. That is the only exception to the allowed-domain rule: every invitation made in the app is to an allowed domain. Admins can promote users to admin and demote admins. The **last active admin** can't be demoted, deactivated or deleted, including through deactivating an invite tree that contains them.
- **R44a. Guessing protection** (owner, 2026-10-13). Sign-in passwords, enrolment codes and password-reset codes are protected against guessing: after 5 wrong attempts for one account, further attempts for it are refused for 15 minutes, even if the flow is restarted or a new code is requested. An invitation's enrolment sends at most **5 code emails an hour** (owner, 2026-11-08); a run past that is told to wait, with the time, and sends nothing. They are counted per invitation, across runs, restarts and addresses, and a resend doesn't reset the count.
- **R44c. The first admin's address and Authentik's administrator's differ** (owner, 2026-11-05). `INITIAL_ADMIN_EMAIL` and `AUTHENTIK_ADMIN_EMAIL` must be different addresses, because Authentik's sign-in and password-reset forms find one account per address, the older one, so a first admin sharing `akadmin`'s address could never sign in with a password or reset it. The API asks Authentik on every start whether another account holds `INITIAL_ADMIN_EMAIL` (ignoring case, as the forms match) and, if so, logs a warning saying what to do, without the address (R73). A failure to ask doesn't stop the API. While another account holds the address, first-admin set-up is refused with the reason, so enrolment doesn't make the duplicate.
- **R44b. Administration** (owner, 2026-10-16). Admin-only screens are grouped in one **Administration** area, reached by a single **Admin** link in the header that only admins see (from M13, the **Administration** group in the side menu, R77, which also carries R55's count). Its start page links to every admin screen. A signed-in user who isn't an admin sees no Admin link, and the admin pages refuse them. Each user's page in Administration lists their integrations (name, type, status, last delivery, Pause or Resume), never destinations or secrets. There is no list of every user's integrations. The users list shows each user's number of integrations and marks any that are paused for failing.

### 7.10 Retention
- **R45.** Messages are kept for a configurable period, set **in days** in the admin UI (default **3,650 days**, minimum 30), then deleted completely (text, metadata and everything linked to them) by a nightly job. **Backups are out of scope.** The docs must say that deleted messages may survive in a deployment's own backups. The cut-off is a **calendar date** in the deployment time zone. The nightly job runs at **03:00** (configurable).
- **R46.** Shortening the period requires confirming the cut-off date ("All messages older than 9 October 2024 will be deleted at the next nightly run. Confirm?"). No row count is shown. Deletion happens at the next nightly run.

### 7.11 Integrations (per user) and metrics
- **R47.** Each user can create their own **integrations**. An integration is a **selection**, a **filter** and a **destination**. Integrations belong to their owner: other users can't see them, and admins can see that they exist (and pause them) but never their secrets. A user can have several integrations for the same capcodes, for example one webhook for emergency pages and another for the rest; each page goes to every integration it matches (owner, 2026-10-16). The integrations screen and the integration docs say, in one line, that integrations are a convenience and not a replacement for a pager (see Out of scope: Operational alerting).
- **R48.** **Selection (required):** one or more capcodes and/or aliases. An integration with no selection can't be saved, so nobody forwards the whole network by accident. The selection is **one field** (owner, 2026-10-16): the user types an alias name or a capcode, and the suggestions show both. A capcode that has its own alias is selected as that alias. A capcode covered only by a range (pattern) alias stays a capcode, with the range alias's name shown beside it, so typing one capcode never selects a range.
- **R49.** **Filter (user-defined):** which **event types** to send, chosen by event category (R5) or by raw event-type code, optionally narrowed by priority and by any other search criterion (R33). Only **new** pages are sent (no backfill), after redaction (P1), and never including admin-only fields unless the owner is an admin.
- **R50.** **Destinations in v1:** a **webhook** (HTTP POST of a documented JSON payload: text without the marker, priority, parsed and extra fields, alias, capcode, sent time, job number; optional custom auth header) and **MQTT publish** (broker URL, topic, optional username/password, TLS). Together these cover Home Assistant, Node-RED, n8n and most message queues. There are also **presets** for **Discord, Telegram, Pushover and ntfy**, each sending the message in that service's own format (owner, 2026-10-16). Detailed routing, such as quiet hours, is the receiver's job.
- **R50a. Content** (owner, 2026-10-16). Each integration chooses what it sends: **Full** (text and all fields, as in R50) or **Summary** (alias, capcode, event type and category, priority, sent time and job number; no page text, address, location or extra fields). Presets default to Summary, because those services are third parties; webhook and MQTT default to Full.
- **R50b. Home Assistant** (owner, 2026-10-16). An MQTT integration can turn on **Home Assistant discovery**: Home Assistant then shows a PagerArchive device with one **event entity** per integration, and each matching page fires it. The docs include an example Home Assistant automation for both the webhook and MQTT.
- **R51.** **Safety:** by default an integration may not reach private, loopback or link-local addresses (protection against server-side request forgery). An admin can allow specific hosts or ranges (e.g. the owner's Home Assistant). Secrets are encrypted when stored and never shown again after saving. Failed deliveries retry with backoff. An integration that keeps failing is **paused**, and its owner sees its status and last error (without page text). Deactivating a user stops their integrations.
- **R51a. On time or not at all** (owner, 2026-10-16). Delivery is attempted within **5 seconds** of the first client receiving the page. Failed deliveries retry until **5 minutes** after that; then the page is skipped for that integration and recorded as "skipped: too old". A page that arrives at the server already older than 5 minutes (e.g. stored by a client while offline) is not sent. A late automation, such as a gate opening long after the page, is worse than none.
- **R51b. No double firing.** Each delivery carries the page's ID. Once a page has been delivered to an integration, it is never sent to that integration again, even if several clients received it.
- **R51c. Send test.** An integration's owner can send a test delivery, marked `"test": true`, and sees what the endpoint answered.
- **R52.** **Metrics for external monitoring:** a Prometheus-format endpoint (access-controlled, no page text) exposing at least: each client's last-seen time and "not receiving" / "clock ahead" state, pages received and stored, `parse_failed` and `address_unsplit` counts, integration delivery successes, failures and "too old" skips, the number of accounts currently locked by guessing protection (R44a), and nightly-job results. System alerting (e.g. via Grafana) is the deployment's job, not the app's.

### 7.12 Aliases in the browser (owner, 2026-10-16)
- **R53. Admins manage aliases** in Administration: add, edit (name, capcode or pattern, template, ignored) and delete. The same rules apply as for import (R27, R27a). Admins' changes take effect at once, with no review. When an alias for one capcode is deleted, integrations that selected it select that capcode instead; a deleted range alias is removed from selections. The delete confirmation says how many integrations select the alias (owner, 2026-10-16).
- **R54. Change requests.** Any signed-in user can request a new alias, a change to an existing alias's name, template or ignored flag, or the deletion of an alias. A request can't change an alias's capcode or pattern (that's a deletion plus a new alias). Users choose from existing templates; only admins manage templates. A request is checked when it's submitted (e.g. R27a) and can carry a note for the admins.
- **R55. Review.** Admins see waiting requests in Administration (R44b), with a count on the Admin link. Each shows the current value beside the proposed one. **Approving** applies the request exactly as submitted, after checking R27a again; if it would now break that rule, approval is refused with the reason. **Rejecting** requires one feedback text. Admins can't edit a request. A request whose alias has changed since it was submitted is marked **"changed since requested"**. Deleting an alias closes its waiting requests as "alias deleted".
- **R56. My requests.** Users see their requests' status (waiting, approved, rejected, withdrawn, alias deleted) and any feedback. They can edit or withdraw a request while it's waiting. A rejected request is final; they can submit a new one. Deactivating or deleting a user withdraws their waiting requests (as with invitations, R43b and R43c).
- **R57. History.** The alias view (R35e) lists the alias's changes **to admins only** (owner, 2026-10-16): what changed, who requested it, who approved or made it (as "name (email)"), and when. A deleted user shows as "deleted user" (R43c). Users see no history, and the API doesn't send it to them; they see their own requests in My requests (R56). When an alias is deleted, its history is kept, attached to its capcode or pattern, with no time limit.
- **R58. Import and export.** From M6, the database is the source of truth for aliases. Import (R30) only **adds** aliases for capcodes or patterns that have none; for existing ones, it lists the differences and changes nothing. The exception is the import's **update option** (R27a, A21), an admin's escape hatch that applies the differences and records them in the history. From M8 it's in the PowerShell module (R63); before that it was `alias import --update`. There's no import in the browser (owner, 2026-10-16). Admins can **export** all aliases as a CSV in the import format from the browser. From M8, `Get-PagerArchiveAlias | Export-Csv` writes the same format (R63).

### 7.13 PowerShell module (owner, 2026-10-20)
- **R59. Two command-line tools.** The `pagerarchive` program, run on the server, keeps only the jobs that need the server: running PagerArchive (`serve`), checking profiles (`validate-profile`), managing receiving clients (`client`) and `version`. Receiving clients stay there on purpose: a client key can post pages, and pages can fire integrations, so creating one needs a shell on the server, not a sign-in. Everything else an admin does from a command line goes through a **PowerShell module**. It uses PagerArchive's API, the same one the browser uses, so the same rules apply. The `template` and `alias` commands are removed from `pagerarchive`, so each job has one tool.
- **R60. Signing in.** `Connect-PagerArchive` with the app's URL opens the browser at the normal sign-in (Authentik, email and password). It uses OAuth's sign-in for native apps, with PKCE and a loopback redirect (RFC 8252). On a machine with no browser, a device-code option shows a code to enter on any device (RFC 8628). The module is its own public client in Authentik, with no client secret. The API accepts the module's access tokens alongside browser sessions, after checking their issuer, audience, signature and expiry. As for the browser, it checks the person's status and role on every request, so deactivating, deleting or demoting someone takes effect on their next command. There are **no API keys** (owner, 2026-10-20).
- **R61. Staying signed in.** The module renews access tokens automatically. The sign-in is saved so it carries across PowerShell windows and restarts (owner, 2026-10-20), with nothing to install or set up on Windows (owner, 2026-10-21):
  - **On Windows**, it's saved in a file in the user's profile, encrypted with Windows' data protection (DPAPI), so only that Windows account on that machine can read it.
  - **On Linux and macOS**, it's saved in the user's default Microsoft SecretManagement vault. With no vault registered, the sign-in lasts for that PowerShell session only, and the module warns how to set one up.
  - **Anywhere**, `-Vault` names a SecretManagement vault to use instead.

  Neither the module nor the API ever writes tokens unencrypted, shows them or logs them. Disconnecting revokes the sign-in in Authentik and removes the saved copy. A sign-in that isn't used for 30 days ends.
- **R62. Admins only** for now (owner, 2026-10-20). The API refuses the module's tokens for a user who isn't an admin, with a message saying PowerShell access is for admins.
- **R63. Commands** (M8, owner 2026-10-20).
  - **Names:** the module is named **PagerArchive**. Its nouns start with `PagerArchive` (`Get-PagerArchiveAlias`), and each command also has an alias that uses `Pa` instead (`Get-PaAlias`).
  - **What it covers:** what the removed `template` and `alias` commands did, i.e. listing, adding, changing and deleting templates and aliases, and importing aliases. Templates can also be renamed (`Rename-PagerArchiveTemplate`, matching `Rename-PagerArchiveAlias`; owner, 2026-10-23).
  - **Import input:** import takes alias objects from the pipeline (`Import-Csv aliases.csv | Import-PagerArchiveAlias`), not a file path, and accepts the import CSV's column names. It collects every row and applies them as one batch, so a conflict changes nothing (R27a).
  - **Import options:** the agency-to-profile mapping is a hashtable parameter (R30). `-WhatIf` is the dry run: it asks once for the whole batch and still outputs every row's result, marked as not applied, so the results can be filtered before the real import. `-Update` is the update option (R58) (owner, 2026-10-21).
  - **Import output:** a result object for each row (added, unchanged, different, squashed).
  - **No export command:** `Get-PagerArchiveAlias` outputs objects whose properties match the import's parameters, so `Get-PagerArchiveAlias | Export-Csv` writes the import format.
  - **Choosing records:** a template or alias piped from `Get-PagerArchiveTemplate` or `Get-PagerArchiveAlias` (or any object with an Id) is chosen by its Id, so `Remove-`, `Set-` and `Rename-` act on exactly that record, even when another template's name differs only in case or other aliases share its name (A19). Names typed or piped as text are matched as before (case-insensitively, with wildcards). Confirmations and `-WhatIf` name each record with its Id (owner, 2026-11-12).
  - **Rules and history:** the same rules apply as in the browser (R27, R27a, R30, R53, R58). Changes are recorded in the alias history (R57) as made by the signed-in admin.
  - **Guidelines and publishing:** the module follows [`docs/powershell-guidelines.md`](docs/powershell-guidelines.md). It has **its own version**, in its manifest, separate from PagerArchive's. A branch that changes the module (`powershell/PagerArchive/`) raises that version above the previous release's, and CI fails a branch that changes the module without it; branches that change it before the same release share one raise (owner, 2026-11-12). CI publishes the module to the PowerShell Gallery from a release (section 12.1) whose checks all passed, **only when that release changed the module**, and only if its version isn't on the Gallery yet. A release that didn't change the module says it kept the version already there. A failed publish is caught up by re-running it (owner, 2026-11-01).
- **R63a. Messages** (owner, 2026-10-20). `Get-PagerArchiveMessage` returns messages as objects, newest first.
  - **Filters:** the same as search (R33): text, capcode, alias, agency, group, priority, event category, job number, a time range, capcodes with no alias, and admin flags. They can be combined.
  - **Ignored aliases:** their pages are included only when asked, as in the browser (R27).
  - **Pipeline input:** aliases and capcodes can be piped in, e.g. `Get-PagerArchiveAlias -Name 'Station*' | Get-PagerArchiveMessage -After (Get-Date).AddDays(-7)`.
  - **What each message holds:** what the detail view shows (R35c): the full text (P2), priority, sent time, capcode, alias, agency, group, job number, event category, parsed fields, location, flags, and each client's receive time.
  - **Paging:** the command fetches messages from the API page by page, only as the pipeline asks for more, so `-First 10` or `Select-Object -First 10` stops after the first page. With no filter, it returns every message.
- **R63b. Watching** (M9, owner 2026-10-20). `Watch-PagerArchiveMessage` (alias `Watch-PaMessage`) outputs new messages as they arrive, in arrival order, until it's stopped (Ctrl+C).
  - **Filters:** the same as `Get-PagerArchiveMessage` (R63a), except the time range and paging. Only matching messages come out.
  - **Speed:** a message comes out within 2 seconds of a client posting it, as in the browser (R32).
  - **Lost connection:** it keeps retrying, with a warning. When it's back, a second warning says how long it was down and how many messages follow (owner, 2026-10-22). Like every other command, it uses the system's proxy settings. Once reconnected, it first outputs the matching messages that arrived while it was disconnected, so a short outage doesn't skip pages.
  - **Account changes:** if the signed-in user is deactivated or loses admin, it stops with an error.
  - **Best-effort:** like integrations, it's a convenience, not an alerting system (see Out of scope, "Operational alerting").

### 7.14 Templates in the browser (owner, 2026-10-20)
- **R64. Admins manage templates** in Administration (R44b). They see a list showing each template's name, agency, icon, colour, agency profile and how many aliases use it, and can add, edit (name, agency, icon, colour, agency profile) and delete templates. Changes take effect at once for every alias using the template (R28), with no change requests and no history. The agency profile is chosen from the profiles loaded at start-up, or none; changing it re-parses the affected messages (R23a). A template still used by aliases can't be deleted, and the refusal says how many use it. **Names are unique ignoring letter case** (owner, 2026-11-14): adding or renaming a template, in the browser, the PowerShell module, the API or the alias import, is refused for a name that differs from another template's only in case (`emv` while `EMV` exists), and the refusal names that template. A template may change its own name's case. Names like that from before this rule are kept: the upgrade neither fails nor renames them; the API logs them on every start, Administration lists them (on Templates, and as a tag on its start page), and no new name can match them, until all but one of each is renamed or deleted. Aliases are unchanged: they may share names (R27a, A19). Users choose from existing templates (R54) and can't change them; the API refuses them.
- **R65. Template icons.** A template's icon is an **image stored in PagerArchive's database** with the template, never a link to another site, so browsers only ever fetch it from PagerArchive. Admins upload it in the browser, or with the PowerShell module (R63) from a file or a URL. The module downloads a URL on the admin's own machine and uploads the image, so PagerArchive's server never fetches anything from another site. Accepted: PNG, ICO, GIF, JPEG and WebP files of at most 100 KB. SVG and anything else are refused with the reason. Every icon is converted to a 64×64 PNG when it's added, and nothing else from the uploaded file is kept. An animated GIF gives its first frame; an animated WebP is refused with the reason (owner, 2026-10-23). If the module adds a template and its icon is then refused, the template stays without an icon and the error says so (owner, 2026-10-23). Admins can replace or remove an icon. The API applies these checks and the conversion, whether the icon comes from the browser or the module.
- **R66. Showing icons.** Wherever a page's sender is shown, its template's icon appears beside the alias name: message rows (the list, live updates, search results, the job view), the alias view (R35e), the message detail view and the map's list of messages (owner, 2026-10-23). The icon sits on a light tile, so dark artwork stays visible in both themes, and its text alternative is the agency name. With no icon, the row looks as it did before (the colour stays). Each browser fetches an icon once and reuses it until it changes. The icon's exact size and position are part of the UI redesign.

### 7.15 Printing for training (owner, 2026-10-20)
- **R67. Print sheet.** Any signed-in user has a **print page**, with its own search (the same criteria as R33, under the same rules) and the user's **print sheet**. They tick messages in the print page's search results to add them to the sheet, and can untick them there or remove them on the sheet. Ticking happens only on the print page: the message list, search results, the job view and the alias view have no tick boxes (owner, 2026-10-30, after trying them in the list). The sheet keeps messages in the order they were added and shows how many it holds. It's kept in that browser until the user clears it, and it stores message IDs only, never message text.
- **R68. Printing.** The print sheet prints as a plain layout for teaching recruits to read pages. Each message shows its text exactly as a pager displays it (R31), in full, and nothing else (no time, alias or priority badge). Each message sits inside a heavy border, with space between messages, so it's clear where one page ends and the next begins. A message is never split across two paper pages. The printout has no header or navigation, is black on white, and can be saved as a PDF through the browser's print dialog. The user documentation notes that printed pages are outside PagerArchive's control: retention and deactivation don't reach paper.

### 7.16 Telemetry (owner, 2026-10-30)
For troubleshooting incidents: following a page from the receiver to the database, finding where time goes, tying high load to what users were doing, and being told when a client stops sending.
- **R69. OpenTelemetry, off by default.** The API server and the client can each export traces, metrics and logs over OTLP to the deployment's collector (such as Grafana Alloy). It's off unless configured, with the standard `OTEL_*` environment variables (endpoint, service name, resource attributes). Every trace is kept unless sampling is configured, in the same standard way. A collector that's missing, slow or down never delays or loses a page, a request or a delivery: the telemetry is dropped instead, and the API or client logs that it's dropping it, at most once a minute. With telemetry on, the app stays within the resource budget (section 8).
- **R70. What telemetry may contain** (P1; owner, 2026-10-30). Nothing exported contains page text, search terms or other query values, redacted details, tokens, cookies, client keys, secrets, email addresses or names. HTTP spans and metrics name the **route pattern** (`/api/v1/messages/{id}`), never the real path or query string. Database spans name the query, never its values. Errors carry their kind, not values from the request. A signed-in request's span carries the user's **numeric ID and role**, and nothing else about the person; spans for what users do never carry message, alias or job IDs. The API continues a trace sent with a request only from a client (R14); browser and PowerShell requests start their own.
- **R71. A page's trace, end to end.** With telemetry on in both, the client starts a trace when it decodes a page and sends the trace context with it (W3C `traceparent`), and the API continues it. One trace then shows each step with its duration: decoding, buffering while the server was unreachable (R15), the post, ingest's steps (redaction, parsing, dedup, location), the database write, the live update, and each integration delivery with its retries (R51a). The ingest span records the outcome (stored, duplicate or refused) and the stored message's ID.
- **R72. Requests and load.** Every API request is a span with its route, status and duration, and database calls under it are child spans. The nightly jobs and re-parsing are traced too. Long-lived connections (live updates, R63b's watch) don't become hours-long spans; the ADR says how they're recorded. Metrics on R52's endpoint add: requests by route and status with their durations, database pool use, open live-update connections, and the Go runtime's memory and CPU.
- **R73. Logs.** With telemetry on, the API's and the client's log lines are also exported, each carrying the trace and span ID of the work it belongs to. stdout logging is unchanged. The client's console page text (R13a) is never exported.
- **R74. Client telemetry.** The client's metrics, exported over OTLP, tell a stuck radio from a network problem: lines read from the decoder, pages decoded, pages sent, failed sends and retries, buffered and dropped pages (R15), the time of the last decoded line and of the last successful send, and whether the radio pipeline (R13) is running, plus radio health when it runs the radio itself (R74a). A client that's switched off can't report: the server's last-seen metric (R39, R52) is what raises the alarm.
- **R74a. Radio health** (owner, 2026-10-31). When the client runs `rtl_fm` and `multimon-ng` itself (R13), it passes the audio from one to the other and measures it on the way, without keeping or exporting any of it: **audio received per second** and the **audio level**. `rtl_fm` runs without squelch, so a working dongle always produces audio: audio stopping while `rtl_fm` keeps running means the dongle is stuck and needs a reset, whether or not the network is sending pages. `rtl_fm`'s status messages still go to the client's log as before, and are also **counted by kind** from a fixed list (no device found, device can't be opened, USB transfer failed, tuner not locked), with anything else counted as "other"; their text is never exported (R70). Measuring never slows or changes the audio multimon-ng gets. A client reading stdin reports no radio health.
- **R75. `/metrics` stays** (owner, 2026-10-30). The API's metrics stay on R52's endpoint, scraped by the collector with the metrics role's credentials, so a dead API shows up as a failed scrape. They aren't also pushed over OTLP.
- **R76. Example monitoring stack** (owner, 2026-10-30). `deploy/` has an example compose stack (Grafana Alloy, Tempo, Loki, Prometheus and Grafana) with pinned versions. It's LAN-only, with Grafana's anonymous access off and short retention by default (traces and logs 7 days, metrics 30 days). It's a separate application that other apps can use too: it owns a Docker network named `monitoring`, and PagerArchive (or anything else to be monitored) joins it through its own `compose.override.yaml` (owner, 2026-11-03; M19). It comes provisioned with:
  - a data source for each store, linked so a log line opens its trace;
  - dashboards: a page's path (time in each step), requests and load (by route, status and user ID), and clients (last seen, not receiving, the client metrics of R74 and radio health of R74a). A client that has stopped reporting still shows its last reported values and how long ago they came, rather than disappearing (owner, 2026-10-31);
  - alert rules: **a client not receiving** (R39's 30 minutes; the threshold is a setting), which clears when the client is heard again; **a radio stalled** (R74a: a client running the radio reports no audio, or its pipeline not running, for 2 minutes; the threshold is a setting), which clears when audio flows again (owner, 2026-10-31); and **the API unreachable** (failed scrapes). They go to a contact point the deployment sets up, such as email or Pushover, whose credentials live in Grafana, never in the repo.

  The docs explain how to run it alongside PagerArchive, how to point the API and client at it, and how much memory it uses. They also say that Grafana access is for the deployment's admins, because it shows client and user IDs. The stack isn't counted in the resource budget, like Authentik.

### 7.17 Layout and navigation (owner, 2026-11-01)
Reference apps chosen by the owner: Grafana (side menu, groups, breadcrumbs) and Immich (use of the width, phone layout). The look and palette are chosen from prototypes.

- **R77. Side menu.** On a desktop, a menu down the left side holds every page, each with an icon and a label, grouped under headings that open and close:
  - **Messages** (not in a group): the message list, with the map and the job view reached from it;
  - **Albums**: one entry per album the user has, growing as they add albums (R82); empty when they have none;
  - **Tools**: Print sheet (R67), Unknown capcodes (R78);
  - **Reports**: the group report (R38), with room for more;
  - **Account**: Profile, Integrations (R47), My requests (R56), Invite someone (R43a);
  - **Administration**, admins only (R44b): users, aliases, templates, clients, retention, waiting requests.

  Each group heading has its own icon too. The menu can shrink to icons only: then only the group icons show (Messages has its own), and hovering over one or giving it keyboard focus opens a small panel listing that group's pages. Any page is at most two clicks from any other. At the very bottom of the menu, open or shrunk, is the running version's tag and nothing else, muted and small: `v` and the version the API reports (12.1), such as `v1.9.0`, or for a build that isn't a release `v1.9.1-dev+abc1234` (owner, 2026-11-14). The tag is a link that opens in a new tab (`rel="noopener noreferrer"`), named "Release notes for v1.9.0": a release goes to its page on GitHub, `https://github.com/RIKIKU/PagerArchive/releases/tag/v<version>`, and a build that isn't a release (`0.0.0-dev`, `1.9.1-dev+abc1234`: anything but `MAJOR.MINOR.PATCH`) to the list of releases, `https://github.com/RIKIKU/PagerArchive/releases`. That address is in one place in the web app (`web/src/lib/release.ts`), so a fork changes it there (owner, 2026-11-15).
- **R77a. Icons.** Every icon comes from one icon set, in one style, chosen in M13's ADR, with a licence that fits MIT. An icon means the same thing everywhere it's used (the Albums icon is also on "Add to album"). Icons are served by PagerArchive itself, never fetched from another site (as R65). No icon stands alone: it has its label beside it, or, in the shrunk menu, a tooltip and an accessible name. The top bar keeps only the search box (R33a), the breadcrumbs (R79) and the account menu.
- **R78. Unknown capcodes page.** R33's "capcodes with no alias" list gets its own page under Tools. It lists the most messages first (counted over all time), then the latest seen. Capcodes with 5 or fewer messages are hidden: the page ends "and N more with 5 or fewer messages", with a control that lists them too, in the same order. The threshold is fixed at 5 (owner, 2026-11-12). The search filter `is:unaliased` stays, unchanged: it still finds every page to a capcode with no alias.
- **R79. Breadcrumbs show where a page is, not how you got there.** Every page below the top level shows its place in R77's tree (`Administration › Templates › Example Fire`). A page's breadcrumbs are the same whether it was reached from the menu, a search, a link or a bookmark. Each level above the current page is a link.
- **R80. Using the width.** At 1,280 px and wider, the page uses the full width: the side menu, the message list, and the selected message's detail view (R35c) in a pane beside the list instead of a page of its own. There's no fixed-width centre column with empty margins. The list keeps its place and filters while messages are opened in the pane. The detail view still has its own address, so it can be bookmarked and shared.
- **R81. Phones** (under 768 px wide). Phones get their own layout, not a squeezed desktop one:
  - a **bottom bar** with Messages, Map, Albums and More; More opens the rest of R77's menu;
  - **desktop-only pages** are left out of the phone menu: the print sheet and Administration. They still open from a link or bookmark, so nobody is locked out on a large phone or a tablet;
  - on phones, Integrations works as on a desktop (owner, 2026-11-14): setting one up, editing it, Send test, its deliveries and deleting it, with the same rules, checks and secrets (R47-R51c, R87d), in a form that fits the width and the finger; each integration's Pause/Resume is a **switch**;
  - R31's and R35c's phone rules still apply;
  - the version's tag (R77) is at the bottom of More (owner, 2026-11-14).

  Desktop or phone is decided by screen width, never by detecting the device.
- **R81a. Coming back to the list.** Leaving the message list and coming back (back button, breadcrumb or menu) restores its search, date range and scroll position.

### 7.18 Year scrubber (owner, 2026-11-01)
- **R81b. Scrubber** (owner, 2026-11-09; 2026-11-13). A strip down the right side of the message list (and the alias, capcode, job and large-event views) for **large jumps**; scrolling the list does the rest. **An album has none** (owner, 2026-11-13): an album is a hand-picked set, not a time range. It covers the **last 30 days**, or the **selected date range** when one is set, newest at the top: one mark per day, per week when the range is over 90 days, or per month when it's over a year. **Today and yesterday** are split into hours. It sits **over the list's right edge**, not in a column of its own, with nothing behind it, and the page's own scroll bar is hidden while it's there, so it owns the window's edge (nothing moves sideways between pages with and without one). **With a mouse it's hidden** until the pointer comes within **50 px of the window's right edge**, and while it's shown a line on it follows the list as it scrolls. Clicking jumps the list to that day, week, month or hour; holding the button and dragging moves the list as the pointer goes, naming the mark under the pointer; the strip stays shown until the button is let go. It never covers a row's links: they keep clear of the strip. **Keyboard:** Alt+J (Option+J on a Mac), or a skip link at the top of the page, goes to it and shows it; it's also in the tab order. Arrow keys move by one mark (by hour within today and yesterday), Page Up and Page Down by week; Escape goes back to the list. A window narrower than 768 px with a mouse has no scrubber.
- **R81c. How busy.** With a mouse, each mark on the scrubber shows how many messages it holds (more dots, more messages). The counts follow the current search and live updates, and working them out stays within the resource budget (section 8).
- **R81d. Zoom** (owner, 2026-11-09). With a mouse, when the list is at an hour of today or yesterday, a button at the top of the scrubber shows that hour as twelve **5-minute blocks**, each with its busy dots, with the hours before and after a click away. Clicking or dragging jumps the list to a block. Another button goes back. Older days have no zoom.
- **R81e. On a touch screen** (owner, 2026-11-13). A touch screen (no hover, or a coarse pointer), at any width, has no strip and no marks: a **grab tab** at the window's right edge appears while the list scrolls, placed by where the list is in time, and fades a moment after it stops. Dragging it moves the list as the finger goes, with a bubble naming the day it will land on; the tab stays under the finger, and the day doesn't flicker at a boundary. It covers the **last 7 days on a phone** (under 768 px) and the last 30 on a tablet, or the selected range; when a day would be too small for a thumb, it moves by weeks, months or years instead. The list scrolls on past the oldest day: the tab then waits at the bottom and says where the list is ("Earlier: Mon, 2 Nov"). The page's own scroll bar is hidden while the tab is there.

### 7.19 Albums (owner, 2026-11-01)
- **R82. Albums.** Any signed-in user can create albums, name and rename them, delete them, and add messages to them or remove them. An album is **private to its creator**: nobody else sees it, admins included, and the API refuses anyone else. Messages are added from the message detail view ("Add to album"); the message list keeps no tick boxes (R67). An album shows its messages newest first, as they are **now**: current aliases (R23a) and current redaction (P1), with no scrubber (R81b; owner, 2026-11-13).
- **R82a. Albums don't keep messages.** Retention (R45) deletes messages in albums like any others, and a deleted message leaves its albums. An album left with no messages is deleted too, unless it has a description (R82f): then it's kept, and says its messages have passed the retention period (owner, 2026-11-12). A message's note (R82f) goes with the message. The album screen says this in one line.
- **R82b. Albums and accounts.** A deactivated user's albums are kept, since they may be reactivated. Deleting an account deletes its albums (R43c).
- **R82f. Descriptions and notes** (owner, 2026-11-12). An album has an optional **description** (what it's for), up to 2,000 characters. Each message in an album has an optional **note** (why it was kept), up to 500 characters; the same message in two albums has a note in each. Both are plain text, set and changed by the album's owner, and shown in the album view: the description at the top, a note with its message. They're private like the album (R82). They're the user's own words, not page text, so the redaction rules (P1) don't apply to them: a user chooses what to write. They aren't searched by the search box (R33a).

### 7.20 Looks (owner, 2026-11-02)
- **R82c. Everything is a token.** From M13, every value that styles the UI is a token in one place: colours, type sizes, spacing, corner radii, target sizes, and how each priority is shown (edge, tint, dot or label). Components use tokens only, and CI fails a component with a hard-coded value. A look is one set of these tokens, in light and dark, so a look can be added or changed without touching a component. M13 builds Harbour only (ADR 0015).
- **R82d. Choosing a look.** Users choose between **Harbour** (the default) and **Console** (M13's second prototype, ADR 0015) in the account menu, beside Auto / Light / Dark. The look is **saved on the account**, so it follows the user to every browser and device. A change applies at once, without reloading, and a page never shows the default look first and then switches. Pages before sign-in use Harbour. Every look meets WCAG 2.1 AA in light and dark (section 8).
- **R82e. The favicon.** The app has a favicon, a white pager on a rounded square of Harbour's accent green, that's visible before sign-in: loading it needs no session (owner, 2026-11-05).

### 7.21 Importing messages (owner, 2026-11-02)
For moving an existing archive into PagerArchive. Users aren't imported; aliases come in through the alias import (R30, R63).
- **R83. The import.** A server-only command, `pagerarchive import-messages <file>`, reads pages from a JSON Lines file, one page per line: `received_at` (RFC 3339, with its offset), `capcode`, `text`, and optionally `source_id` (the page's ID in the archive it came from). The format is documented with an example.
- **R83a. The same path as a live page.** Each page goes through redaction (P1), cleaning (R17), parsing (R7), deduplication (R19) and job grouping, as if a client had sent it at its `received_at`. Duplicates in the file are merged by R19's 10-second rule, as live pages are. A page that fails to parse is still stored and shown in full (P2).
- **R83b. Quiet.** Imported pages set off no integration (R47), live update (R32) or alert, and don't count as a receiver being alive (R39). They're recorded as received by "import", not by a client.
- **R83c. Safe to repeat.** Importing the same file again stores nothing new: by `source_id` when it's given, otherwise by the dedup key and receive time. An import that stops part-way can be run again to finish.
- **R83d. Retention.** Pages older than the retention period (R45) are skipped and counted, not stored.
- **R83e. Dry run and report.** `--dry-run` reads and checks the whole file and stores nothing. Every run reports lines read, pages stored, duplicates merged, parse failures, pages skipped by retention, and refused lines by line number and reason. No report, log line or telemetry ever contains page text (P1, R70).
- **R83f. Speed and budget.** The import stores at least **500 pages a second** while the app keeps receiving and delivering live pages, within the resource budget (section 8). At that rate, 4.6 million pages take under 3 hours. An import is a one-off, so searches may be slower than R33b while it runs; it must not slow down live pages (owner, 2026-11-02).

### 7.22 Installing and upgrading (owner, 2026-11-02)
- **R84. No checkout.** Running PagerArchive needs no copy of the source repository. A deployment holds `compose.yaml` and an `.env` example, both attached to every GitHub release, plus its own data: its network profile (mounted at runtime, section 6) and its map tiles. PagerArchive's own images hold everything PagerArchive needs: given an empty database and a login with rights to it, the API creates its tables, roles and whatever else it needs on start. With no network profile mounted, it uses the example profile built into the image, and logs a warning on every start that the example's redaction rules aren't the network's (owner, 2026-11-03). Third-party services (PostGIS, Authentik, the optional monitoring stack) run their upstream images unchanged: the project never publishes its own builds of them (owner, 2026-11-03). `compose.yaml` names every image, PagerArchive's included, by its **major.minor** tag (such as `pagerarchive:0.15` or `postgis/postgis:18-3.6`), with no patch number and no digest, so `docker compose pull` gets every patch release. Keeping up with patches is the deployment's job (owner, 2026-11-03). Where an upstream image has no major.minor tag, the nearest tag that moves only within a minor version is used, and the ADR lists it. Their configuration (Authentik's blueprint and email templates, the database's first-start script for Authentik, the monitoring stack's configs, dashboards and alert rules) is attached to every release as one archive, unpacked next to `compose.yaml`. The optional example monitoring stack's `compose.yaml` and `.env` example are attached the same way.
- **R84a. Upgrading is installing the latest release.** Upgrading from any earlier release is getting the new `compose.yaml` and configuration archive and running `docker compose pull && docker compose up -d`, and nothing else:
  - migrations run when the API starts, and only go forward;
  - a new setting has a safe default, or the app creates it on first start (secrets included) and keeps it in its own volume, so `.env` never needs editing for an upgrade;
  - nothing is run by hand inside a container;
  - a changed third-party configuration file takes effect on `docker compose up -d`.

  A release that can't meet this (for example, a new major version of PostgreSQL) puts "Upgrade steps" at the top of its release notes, and needs the owner's approval.

  **Before 1.0.0** (owner, 2026-11-03), R84a and A77 bind loosely: a release may break the upgrade from an earlier one without the owner's approval, as long as its release notes give the "Upgrade steps" (which may be a fresh install). 1.0.0 is the first release after the existing archive's data is migrated and users are working on PagerArchive.
- **R84b. Docs.** The install is: download `compose.yaml`, the `.env` example and the configuration archive, unpack the archive, fill in `.env`, then `docker compose up -d`. The upgrade is the two commands above, and a patch release within the same minor version needs only those two commands, not a new `compose.yaml`; a minor release needs its own `compose.yaml` and archive first, and the docs say so plainly (12.1). The `git pull` instructions go.
- **R84c. PostGIS keeps up with its image** (owner, 2026-11-10). A newer `postgis/postgis` image updates PostGIS's library, but each database keeps the extension version it registered until `ALTER EXTENSION … UPDATE` runs, which the image does only for a new database. So on every start, after its migrations, the API updates each installed PostGIS extension whose version is behind the image's: `postgis` first, then whichever of `postgis_raster`, `postgis_topology`, `postgis_sfcgal` and `postgis_tiger_geocoder` are installed (it never creates one). One already at the image's version runs nothing. Each update is logged at INFO with the extension and its old and new versions. If one fails (for example, the API's role doesn't own it), a WARN names the extension and the fix (run `ALTER EXTENSION <name> UPDATE` as its owner), and the API starts anyway. One the image no longer provides (PostGIS 3.7 dropped `postgis_tiger_geocoder`) is left as it is, with a WARN saying so.
- **R84d. Automatic upgrades, if switched on** (owner, 2026-11-14; ADR 0030). A deployment installed with no checkout (R84) can upgrade itself. It's **off by default** and switched on per install, by a script in the configuration archive (`deploy/auto-upgrade/auto-upgrade.sh enable`), which runs on the host where the compose project lives, as the user who runs it, from that user's crontab (no root needed) or a systemd user timer. The API never runs Docker or upgrades anything (as R86a). Never two runs at once, and never while a backup is running or asked for (the backup service's own lock refuses it, and the run tries again the next hour). Switching it off (`disable`) stops the checks; a manual upgrade (R84a) works on or off.
- **R84e. What's installed, and verified first.** Every hour the script finds the newest **full** release on GitHub's releases API (not a draft, not a pre-release; no token, as the repository is public). It installs it only if it's newer than the version running, in the same major version, not marked failed (R84g), and its release notes don't start with "Upgrade steps" (R84a): those are left to the owner, and the status says why. First it **verifies** the release's attached files and PagerArchive's images (the server's, and the client's when the deployment's `compose.override.yaml` names it by a major.minor tag) by their attestations (12.1), with a pinned release of the GitHub CLI that the script downloads into the install's folder and checks against that release's published checksum on every run; the attestations come from GitHub's API, with no sign-in. If verification can't run or fails, nothing is installed and it tries again the next hour. The images Compose pulls must be the ones verified.
- **R84f. Backed up, upgraded, checked.** Before upgrading, the backup service's `now` (the same checked backup as the nightly one, R86a) is kept aside where a later backup can't replace it, with copies of `compose.yaml`, `.env`, `compose.override.yaml`, `deploy/` and the monitoring stack's files; the last 3 are kept. The upgrade installs the verified `compose.yaml` and archive, moves a client's major.minor tag in `compose.override.yaml` to the new minor version, and runs `docker compose pull && docker compose up -d`, and does the same for the example monitoring stack when the install names its folder. Then the **health check**: every container running; the API answering, running the new version, from the verified image (it answers only after its migrations have run); the install's own URLs answering, if it lists any; and **a page stored after the restart**, within a window (30 minutes by default), but only when pages were arriving before: at least 20 pages in the 4 windows before the upgrade, 5 a window on average, so a whole window without one would be very unusual. On a quieter network that check is skipped and the status says so: a quiet network never causes a rollback (owner, 2026-11-14).
- **R84g. Rolled back on failure.** If the upgrade or its health check fails, the previous release's files and the images that were running go back, with nothing pulled. If the new version changed either database (PagerArchive's migrations, Authentik's, or a PostGIS extension's version, compared before and after), the pre-upgrade backup is restored first, the documented way (R86b): into a new, empty database, with the stack stopped, before the old version starts. The release is **marked failed** and not tried again unless an admin says so on the server (`retry`). Each step (check, verify, backup, upgrade, health, rollback, restore) writes one structured line, with the versions and, on a failure, the reason as fixed text: never page text (P1). A rollback that fails leaves the stack as it is (stopped, if the restore failed) and says where.
- **R84h. Seen in Administration and Grafana** (owner, 2026-11-14; 2026-11-15: "If an automatic update fails I think we should be capturing that in Grafana also"). The script writes a status file in a folder the API mounts read-only, as the backup service's (R86a). **Administration → Upgrades** shows whether it's on ("off" when not), the last check and its result, the last upgrade, the history and the releases marked failed; Administration shows a notice when the last upgrade failed (rolled back, with or without a restore, or not), when one stopped part way, or when there's been no check for 3 hours. R52's metrics have whether it's on, the last check's time, the last successful upgrade's time and versions, failures and rollbacks as counters, whether it's failing and its current state. The example monitoring stack treats it as backups (R86d): its log lines in Loki (Alloy reads the script's log file from the same folder, read-only, keeping only its known fields), panels on the backups dashboard (last upgrade, version history, failures and rollbacks, time since the last check) and an alert rule, **Upgrade failed**, through the same contact point as the others. There's no other alerting (owner: "alert is a strong word").

### 7.23 Maintenance (owner, 2026-11-03)
- **R85. Base images.** A daily check notices when a base image under PagerArchive's own images (the server's and the client's) has changed upstream, often for a security fix. A change merges on its own, once CI passes, and goes out in the next release (section 12.1), so it reaches deployments at their next `docker compose pull` after that.
- **R85a. Libraries, monthly.** Once a month, PagerArchive's dependencies (Go modules, npm packages, GitHub Actions) are updated in two pull requests: one with every patch update, which merges on its own when CI passes and goes out in the next release (section 12.1), and one with everything larger, which waits for the owner's review.
- **R85b. Third-party versions, weekly.** A weekly check opens a pull request when a third-party image in `compose.yaml` or the monitoring stack has a new major or minor version (such as Authentik 2026.5 to 2026.8, or PostGIS 18 to 19): one pull request for all of them, except Authentik and PostGIS, which each get their own (owner, 2026-11-12). It always waits for the owner's review, as these can need "Upgrade steps" (R84a). An image with no tag that moves within a minor version (R84; the ADR lists them) gets a weekly pull request for its patches too, which merges on its own when CI passes (owner, 2026-11-03).
- **R85c. Every automatic update follows 12.1:** every check its change affects passes before it merges, and it goes out in the next release. An update that fails CI, after CI's own retry (12.1), is left open, not merged, and the owner is told.

### 7.24 Backups (owner, 2026-11-03)
- **R86. Nightly backups.** Every night, PagerArchive's database and Authentik's are each dumped to a folder the deployment mounts, with nothing to install or schedule by hand: the stack in `compose.yaml` does it. Dumps are kept for **14 days** by default (a setting), and older ones are deleted. A dump is written under a temporary name and renamed when complete, so a file backup tool copying the folder at any time never takes a partial one.
- **R86a. Checked, and failures are seen.** Each night's dumps are restored into a throwaway database with no network and compared (tables and row counts). The time of the last good backup is in R52's metrics, and an admin sees in Administration when the last backup failed or is more than 36 hours old. The example monitoring stack alerts on it. **Back up now** (owner, 2026-11-14): an admin can start the same backup and check at once, from Administration → Backups or the PowerShell module (`Start-PagerArchiveBackup`, with `-Wait` for the result; `Get-PagerArchiveBackup` for the state). The page shows it asked for, then running, then its result, with times. The API never runs it and never reaches the dumps or Docker: it writes a request on a volume of its own, and the backup service, which checks every minute, runs the backup and check and then deletes the request. One at a time: a request while one is asked for or running (the nightly one too) is refused, saying since when. The extra backup is that day's, under the same retention (R86): it replaces one made earlier that day, and after a good one the nightly backup doesn't run again that day.
- **R86b. Restore.** One documented command restores a chosen night's dumps into an empty install, after which everything is as it was then: pages, aliases, templates and icons, integrations, users and their sign-ins.
- **R86d. Backups on the dashboard** (owner, 2026-11-07; M18). The example monitoring stack shows backups on a dashboard: time since the last good backup (coloured by age), whether the last one is failing, and each night's dump size, dump time and check time. The backup job reports those three as metrics (R52), so the check's growth with the archive can be seen.
- **R86c. Off the host.** Copying the backup folder to another machine (a NAS, cloud storage) is the deployment's job. The docs give an example. The dumps hold only what the databases hold, so P1 holds: no redacted detail is in a backup.

### 7.25 Large events (owner, 2026-11-12)
- **R87. Large events.** PagerArchive notices when something big is happening on the network and groups the pages into a **large event**. It's meant only to alert users that something big is happening, so they know where to look; for more they listen to the radio or look at other systems. An event is simply a large event: it has no levels or kinds (owner, 2026-11-13). Only **Emergency** pages to capcodes with an alias count (not heartbeats, not unaliased capcodes), and not pages to an alias marked **ignored** (R27): those are usually the network's own traffic, unrelated to emergencies, so they neither open, join nor count towards an event, live or rebuilt (owner, 2026-11-14). Imported pages (R83) don't count either: they form no events (owner, 2026-11-14). An event is **opened** by any of:
  - **a code:** an Emergency page carrying a code that matches the network profile's pattern (R5), such as one naming a pre-formed group of appliances sent together (no roster of groups or members is kept, as groups change each season);
  - **a field's value** (owner, 2026-11-14): an Emergency page whose field holds a value its agency profile lists (R7), such as an alarm level high enough to mean something big (some agencies dispatch with a level on each page: a first alarm sends two or three appliances, and each level above sends more). It opens or joins an event exactly as a page with a code does, and is otherwise silent: the app shows no level and doesn't say what opened an event (R87b);
  - **a job's Emergency pages:** one job (R23) with **20 or more Emergency pages** that count (above: an ignored alias's pages are not among them; owner, 2026-11-14, before which they were). Each stored message counts once: a copy from a second receiver is the same message (R19), while the same page to two aliased capcodes is two (R20). What the pages say, appliances included, doesn't matter. An admin can change the 20 (owner, 2026-11-13; before, it was 20 distinct units).
- **R87a. Grouping by time.** An Emergency page that would open an event, arriving within **12 hours** of an open event's latest page, joins that event instead, and so do the other pages of its job. An event **ends** after 12 hours with no page joining it. After that, a page that would open an event opens a new one, even one on a job the ended event holds (a long job heard again after 12 quiet hours), and the new event is told to large-event integrations (R87d) as any other is (owner, 2026-11-14: "After 12 quiet hours just open a new event"). Pages carry no reliable link to one incident (each dispatch gets its own job), so on a busy day several incidents may share one event; that's accepted.
- **R87b. No levels** (owner, 2026-11-13). Events aren't tagged with levels or with what opened them. (Before, an event recorded the levels "deployment", "several deployments" and "big job", with when each was met.)
- **R87c. Large events in the app.** A **Large events** page under Tools lists events, newest first: start and end (its first and last pages' times; never "ongoing" or "ended": the app can't know whether an incident is over, and the 12-hour window only decides which pages join; owner, 2026-11-13), and its numbers of jobs and Emergency pages. An event's view shows those, its **job numbers** (each a link to its job's view) and its pages like the message list (P2, P1), with the scrubber (R81b). Users see jobs and job numbers: the app never shows a count or list of the codes in an event's pages, never calls them "deployment codes" and never counts appliances (owner, 2026-11-13). Every signed-in user sees events, as they see the pages.
- **R87d. Large-event integrations.** An integration (R47) may select **large events** instead of capcodes or aliases (R48), with nothing more to choose. It fires **once** per event, when the event opens, and never again for that event: not as more pages, codes or jobs join it, and not when events merge (each was told of when it opened). It sends a **summary**: the event's id and start, the page that opened it (its id and sent time), its job numbers and number of Emergency pages so far, and a link to the event's view; never page text, appliances or codes (owner, 2026-11-13). Destinations, safety and delivery as R50-R51b (on time: within 5 seconds of the page that opened the event).
- **R87e. Kept and deleted.** Events are derived from pages: retention (R45) deletes an event when its last page goes, and an event's numbers follow the pages it still holds. A rebuild (R87f) groups the pages still kept, so an event that retention has thinned may be regrouped from what is left (a job below the threshold no longer holds one open).
- **R87f. Rebuilt when pages are re-parsed** (owner, 2026-11-14: "Re-parsing should regroup"). When pages are re-parsed (R23a: an alias added, changed, deleted or marked ignored or not, a template's agency profile changed or an agency profile itself, such as gaining or changing its `large_event_fields`, or the network profile changed, such as gaining or changing its code pattern), the large events those pages belong to, or could now belong to, are **rebuilt**, so they are what live ingest of the same pages, in the order they were sent, would have made. It's bounded and cheap: only the time around the re-parsed pages (their sent times and 12 hours either side, extended over any event pages there could join and over every page of their jobs, while those chain), in batches, in the background like the re-parse itself. A rebuild **never sends anything** (R87d), even for an event it forms: like an import (R83b), only live ingest tells integrations. Deliveries already made stay, each with whichever event now holds the page that carried it (none, if no event does). An event's ID may change: the event that keeps most of an old event's pages keeps its ID, and a link to an ID that no event keeps finds nothing (404), as one to an event merged into another does. The threshold is the one set now.

## 8. Constraints

| Constraint | Because |
|---|---|
| Docker Compose on a home Linux server; API and frontend may be separate containers | Simple installs and upgrades for self-hosters |
| All dependencies inside images | Install and maintenance stay easy |
| Linux only. **Server** images (API, frontend, database) for **amd64 only**; **client** images for **amd64 and arm64** | Servers are x86 PCs, so official amd64 images (e.g. PostGIS) can be used; receivers may be Raspberry Pis |
| **Resource budget:** the app's containers (API, frontend, PostgreSQL; Authentik excluded) ≤ **1 GB RAM** total in steady state; API ≤ **256 MB** with 20 viewers at 1,500 pages/day; idle CPU < 5% of one core | Target host: an old small-form-factor PC (e.g. 15 GB RAM, spinning HDD) shared with other self-hosted apps |
| **PostgreSQL + PostGIS**; **no separate message queue** | Best fit for map data and search; ~1 page/minute doesn't justify a queue |
| **Authentik** for identity | Invitations, email codes and domain rules out of the box |
| Profiles in **JSON**, not YAML | Not whitespace-sensitive; easy to auto-format and validate |
| Geocoding only against a **local** address dataset | Public geocoders are rate-limited, often restrict automated use, and would receive incident addresses |
| **No paid services** | Hobby-scale self-hosting |
| Language and frameworks: chosen in an ADR (see "How to use") against these constraints | Delegated by the owner |
| CI on **GitHub Actions**; multi-arch images published to **GHCR** | Free for public repos |
| Accessibility: **WCAG 2.1 AA** | Usable by everyone, including on phones in poor light |
| Runs behind an **external reverse proxy**; the compose file doesn't include one | Self-hosters already run one (the owner uses linuxserver/swag) |
| Licence: **MIT** | Open source |
| The repo names **no real agency, network or other project**; test data uses made-up formats and addresses | Generic tool; privacy (P1) |

### 12.1 Releases (owner, 2026-11-01; revised 2026-11-12)
- **Merge freely, release deliberately** (owner, 2026-11-12). A merge into main runs every check and, once they pass, publishes the images tagged `main` and `sha-<commit>` only: no tag, no GitHub release, no version. A build that isn't a release reports `<next>-dev+<commit>` as its version (such as `1.7.6-dev+3f2c1ab`): the version a release of that commit would get, marked as not one. Branches don't set a version: `VERSION` in the repository says `0.0.0-dev`, and CI fails a branch that changes it (ADR 0024).
- **A release is cut by the Release workflow**: every Saturday (18:17 UTC on Friday), ahead of the owner's weekly upgrade; whenever the owner presses "Release now"; and when a security update (a pull request labelled `security`, from Renovate's vulnerability alerts) merges: 30 minutes after it (owner, 2026-11-12, raised from 15), and a second security merge within those 30 minutes starts the wait again, so security updates that merge close together go out as one release (owner, 2026-11-12; ADR 0024). It releases main's newest commit, and only if main changed since the previous release in something other than documentation (what CI checks nothing for: `SPEC.md`, `docs/**` and other Markdown); otherwise it says "nothing to release". Two releases never run at once.
- **The version is worked out from the previous release** (the newest `v*` tag in the commit's history; owner, 2026-11-14). It's the **next minor version** if, since that release, any of these happened: a file a deployment downloads changed (`compose.yaml` other than our own image's tag, or the configuration archive's files); a database migration was added; or a pull request labelled `feature` merged (`.github/release.yml` says when to use the label). Otherwise it's the **next patch**: fixes, CI, documentation, dependency and security updates. There's no major version except by hand. A deployment's `compose.yaml` names our image by `MAJOR.MINOR`, so `docker compose pull` gets patches only, and every minor release needs its own `compose.yaml` and archive downloaded (docs/deploy.md). Before a release, the next version and the rules that fired show in every build of main (`pagerarchive version` reports `<next>-dev+<commit>`) and in the Release workflow's notice, in a dry run too (ADR 0024). It's written into the build, never committed: the release's tag holds it.
- The release runs every check on the commit it releases, then tags it `v<version>`, creates the GitHub release with the client binaries and their checksums and GitHub's generated notes, publishes the images tagged with the version, its `MAJOR.MINOR` (such as `0.12`) and `latest`, attaches the files a deployment downloads (R84), makes the release the latest, and publishes the PowerShell module if it changed since the previous release (R63). It attests the client binaries, the attached files and both images with GitHub artifact attestations, the images' attestations pushed to GHCR beside them, so `gh attestation verify <file or oci://image> --repo RIKIKU/PagerArchive` checks a download (owner, 2026-11-13; ADR 0024). A dry run attests nothing.
- Nothing is released by hand: v0.12.0 is the last tag made by hand. A dry run of the Release workflow does everything but tag and publish.
- If part of a release fails to publish, that job is re-run; a version is never reused.
- **What CI runs** (owner, 2026-11-12; ADR 0025). A pull request runs only the checks its changed files can affect, and a change of documentation alone runs none, so "All checks passed" reports at once; and a file CI doesn't know, CI's own files or a shared test fixture runs every check; main (unless only documentation changed) and every release run every check, so nothing is released that a check was skipped for. A failure that isn't the change's is retried: network steps try again by themselves, a failed test runs once more in its job, and a failed run of a pull request or main has its failed jobs re-run once, unless what failed is always the change's or is a security or privacy finding. Whatever passed only on a retry is reported as flaky on the run, never hidden. CI also reports the known vulnerabilities the Go code can reach (govulncheck), and fails for one it calls that has a fix.

## 14. Accepted defaults

Settled by the owner after the second cold read (2026-10-09):
- Priority markers are case-sensitive and exactly 2 characters. With no known marker (priority `null`), the full text is shown unchanged.
- An Emergency page on a profiled capcode that matches no format, and any `null`-priority page that matches none, is `parse_failed`.
- Extracted values are trimmed, and empty matches become `null`. Extra fields are strings or lists of strings.
- Each redaction match is replaced by one `REDACTED`. Dedup runs on redacted text. A redaction rule that alters one of its own must-not-match examples stops the server at startup.
- If retroactive redaction removes the text a field came from, the message is re-parsed and may leave its job.
- The POCSAG function code and baud rate are stored but not used. The client accepts `Alpha:` and `Numeric:` lines, drops other lines silently, and trims only multimon's separator.
- Control tokens such as `<NUL>` are removed; `<LF>`/`<CR>` become a space.
- The dedup window is symmetric: a late copy whose receive time is within 10 s of the first copy, either side, is the same transmission, and sent time becomes the earliest.
- The client drops the oldest buffered pages when its buffer is full, and rejects receive times more than 60 s in the future (logged without page text). The client ID comes from configuration (see R14).
- Profiles are read at start-up. A change is detected by comparing file hashes, which then triggers re-parsing (R23a). A template pointing at a missing agency profile makes its pages text-only and is reported to admins.
- Re-parsing runs as soon as a change is detected. Retroactive redaction waits for the nightly run.
- The message list is sorted by sent time, newest first, with infinite scroll. Late buffered pages appear in their sorted position.
- Text search is case-insensitive substring search across the text and extra fields, with every term required (R33a's text terms).
- The map shows the last 24 hours by default, follows the active filters, and has one point per located message. A tile server, if one is used, counts toward the resource budget.
- No house number: the street's centroid is used and marked approximate. Grid references resolve to the centre of the 100 m cell. Address matching normalises common abbreviations (ST/STREET) but isn't fuzzy.
- The example address dataset places MADEUPTON at a neutral location. No real map tiles are needed for tests.
- A template still used by aliases can't be deleted (R64). Icons are images stored with the template (R65).
- Unmapped report codes are listed one row per raw code inside "Other". Report date ranges are inclusive, in the deployment time zone. Reports are per capcode or per alias (R38).
- Jobs left with no messages, per-client receive records and geocode results are deleted along with their messages.
- Only client images are multi-arch; server images are amd64 only (owner correction, 2026-10-09). WCAG 2.1 AA is checked with automated accessibility tests plus a manual checklist.
- A12 and A13 use a controllable clock and a test-only trigger for the nightly job. The §11 "clean host" is a GitHub Actions Ubuntu runner, with a local mail catcher (e.g. Mailpit) and `example.test` as the allowed domain.
- For A15, "20 viewers" means 20 live-update connections, and the page stream is generated from the example formats. The test runs once by hand with evidence, plus a short version in CI.
